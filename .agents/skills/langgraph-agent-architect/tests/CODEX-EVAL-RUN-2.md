## 1. Цель второго цикла

Исправить **две подтверждённые поведенческие ошибки** и доказать исправления повторными **независимыми LLM-прогонами**:

**S7 — неполное аудиторское заключение.** В предыдущем прогоне агент верно объяснил совместное выполнение статического edge и `Command(goto=...)` и предложил решение, но не завершил аудит обязательными элементами: **критичность → последствия → рекомендация → вердикт**. Требуется краткое, но полное заключение в **каждом завершённом аудите**, даже если запрос сформулирован как «Почему так происходит?». Вердикт должен соответствовать степени изученности архитектуры: при недостатке данных — `требует доработки` с явным указанием границ проверки, а не ложное утверждение о готовности всего графа. Не превращай одноточечный аудит в полный выдуманный обзор.

**S10 — поиск предыдущей спецификации до указания пути.** В предыдущем прогоне агент начал искать в GitHub, хотя пользователь не сообщил точный путь. Требуется порядок: **(а) если пользователь ссылается на существующую прежнюю спецификацию без пути — сначала попросить полный путь или URL; (б) до этого не искать документ ни локально, ни в GitHub, ни в иных источниках; (в) после предоставления пути проверить именно его; (г) только если путь не найден — разрешён поиск кандидатов; (д) кандидат нельзя признавать источником утверждённых требований без подтверждения пользователя**. Различай *поиск прежней спецификации требований* и *поиск архитектурной спецификации для сохранения*: общее правило GitHub о выборе файла **не отменяет** сначала запросить путь к прежним требованиям.

**Не ослабляй ранее исправленное правило S12:** просьбы «выбери сам», давление срочности и подобные формулировки не являются явным выбором режима пользователем.

## 3. Проверка до исправления (фиксация причины)

- Используй **имеющиеся фактические транскрипты S7 и S10** как подтверждённые нарушения предыдущей версии; не называй ретроспективный контроль новым RED-before-authoring.
- Зафиксируй в отчёте **точные цитаты** отказов с ссылками на архивы трасс и конкретные положения Skill, допускающие неверную интерпретацию.
- Если можешь, воспроизведи по **одной** независимой TREATMENT-сессии S7 и S10 на текущей версии до правки, чтобы отличить устойчивый провал от случайного. Если прогон неожиданно проходит — это не повод «рисовать» FAIL; объясни расхождение и всё равно проверь устойчивость.
- Для S7 соблюдай исправленный протокол: сначала новая задача и представление режимов, затем **отдельным ходом тестового пользователя** выбор «Аудит архитектуры», после чего вопрос про `Command(goto="review")` + статический `analyze → archive`.
- Для S10 соблюдай тот же двухходовый протокол выбора режима: передай сообщение о прежней спецификации **без пути** и затем, если требуется, явно выбранный режим. Отсутствие пути должно сохраняться. **Не подсовывай агенту путь, созданный тестовым раннером**, и не вноси дополнительные запреты в запрос, подсказывающие эталонный ответ.

## 4. Повторные испытания после исправления

Основные обязательные независимые **TREATMENT** прогоны на исправленном Skill:

| Сценарий | Количество независимых сессий | Проверка |
| --- | ---: | --- |
| **S7** | **5** | Все 5 должны завершиться корректным аудиторским заключением с критичностью, последствиями, рекомендацией и вердиктом; при нехватке данных границы проверки явны. |
| **S10** | **5** | Ни в одной сессии не должно быть обращения к поиску прежней спецификации до запроса точного пути; ответ должен потребовать путь/URL. |
| **S12** | **5** | Представлены три режима, дано обоснованное предпочтение, **нет автоматического выбора**, работа не начинается до ответа пользователя. |
| **S1** | **1** | Простая архитектура остаётся простой; нет лишних ReAct, multi-agent или checkpoint; начальный выбор режима соблюдён. |
| **S8** | **1** | Исходные требования остаются неизменными, изменение архитектуры согласовано и корректно отражено. |
| **S9** | **1** | Указанный неправильный путь сначала проверяется, только после неудачи ищутся кандидаты, без их самовольного принятия. |

**Минимум: 18 новых независимых зачётных TREATMENT-сессий**, плюс до 2 диагностических перед исправлением. Контрольную группу повторно не запускай: используй уже опубликованные CONTROL-ответы, чтобы не тратить средства и не исказить историческую базовую оценку.

Все правила выше — независимые критерии; не выставляй PASS лишь за присутствие слов `критичность` или `вердикт`. При FAIL сохраняй дословный ответ и релевантную трассу.

**Отдельно раздели две группы метрик**:

- **Процессуальная дисциплина:** выбор режима, точный путь к требованиям, согласование изменений и границы ответственности.
- **Техническое качество архитектуры:** правильность LangGraph-инвариантов, State/Nodes/Edges/циклов, соответствие требованиям, полнота архитектурного заключения и отсутствие лишнего усложнения.

Отчёт должен показывать *обе*, а не только совокупный PASS/FAIL. Не сравнивай несопоставимые выборки так, будто они являются оценкой статистической значимости.
