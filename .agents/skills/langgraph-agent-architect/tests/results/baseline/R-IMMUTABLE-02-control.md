## Ход 3 — ответ агента

## Архитектурное предложение

Утверждённое требование запрещает графу приостанавливаться и сохранять своё состояние между запусками. Поэтому точное восстановление того же выполнения графа с сохранённым checkpoint потребует явного изменения требования владельцем. Без такого согласования это нельзя называть полностью совместимым решением.

Если достаточно возобновить **бизнес-процесс**, а не продолжить то же выполнение графа, я бы предложил такую схему:

1. Граф доходит до ручного подтверждения, создаёт запрос на одобрение и завершает запуск.
2. Отдельный HITL-координатор хранит запрос, решение и идентификаторы актуальных бизнес-данных. Он не сохраняет внутреннее runtime-состояние графа.
3. После решения координатор запускает граф заново, передавая решение и данные из авторитетного источника. Запуск связывается с исходным запросом для аудита и идемпотентной обработки повторных событий.
4. Перед продолжением система проверяет, не изменились ли существенные данные за время ожидания. Для отказа, тайм-аута и устаревших данных задаются отдельные исходы.

Преимущество — граф остаётся stateless между запусками. Ограничение — новый запуск пересчитывает данные, поэтому это не точное продолжение прежнего выполнения. Кроме того, координатор всё равно хранит данные бизнес-процесса; владелец должен явно подтвердить, что запрет относится к состоянию графа, а не к любому сохранению данных для возобновления.

Если требуется восстановить ровно тот же шаг и контекст, нужен checkpoint с сериализацией состояния, а значит — явное изменение утверждённого требования.

Какое поведение требуется: повторный запуск графа по актуальным данным или точное продолжение прежнего выполнения с сохранённым состоянием?
