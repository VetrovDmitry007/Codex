## Архитектура процесса

Процесс принимает заявку в фиксированном структурированном формате, один раз проверяет наличие обязательных полей и возвращает вызывающей стороне итог. Каждая заявка обрабатывается независимо.

**Поток:** получение заявки → одна проверка заполненности → формирование результата → возврат результата.

| Компонент | Ответственность |
|---|---|
| Входной интерфейс | Принимает структурированную заявку и передаёт её на проверку |
| Проверка заполненности | Сверяет заявку с заданным перечнем обязательных полей |
| Формирователь ответа | Возвращает статус и, если нужно, список незаполненных полей |

Перечень обязательных полей задаётся в конфигурации процесса. Его состав пока не определён. Рекомендую считать незаполненными отсутствующие, `null` и пустые после удаления пробелов значения. Проверка формата, допустимости значений и бизнес-правил в этот процесс не входит.

**Результат проверки:**

| Ситуация | Ответ |
|---|---|
| Все обязательные поля заполнены | Статус «заявка заполнена», список пропусков пуст |
| Есть незаполненные поля | Статус «заявка заполнена не полностью», список пропусков |

Состояние не сохраняется: процесс не ведёт историю заявок, не запоминает предыдущие результаты и не использует LLM. Для такого объёма достаточно одного обработчика и статического перечня полей; отдельная база данных не нужна. Предполагаю, что интерфейс подачи заявки уже предоставляет данные в структурированном виде.
