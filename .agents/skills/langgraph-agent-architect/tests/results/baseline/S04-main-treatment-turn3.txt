## Предлагаемая архитектура

**Основа: LangGraph с центральным координатором и ограниченными циклами.** Координатор составляет план, направляет задачи специализированным агентам и оценивает собранные результаты. Агентам-исполнителям недоступен инструмент делегирования: они выполняют только назначенную работу и возвращают результат по заданному формату.

Такой граф позволяет явно задать маршруты и проверяемые условия остановки. Параллельную отправку задач можно организовать через `Send`; для результатов параллельных ветвей нужно определить правила объединения. Это соответствует рекомендациям официального материала по [основам LangGraph](https://github.com/langchain-ai/langchain-skills/blob/main/config/skills/langgraph-fundamentals/SKILL.md).

### Поток работы

```mermaid
flowchart TD
    S([Старт]) --> I[Принять цель и критерии результата]
    I --> P[Координатор строит план]
    P --> Q{План допустим и есть бюджет?}
    Q -- нет --> F[Вернуть статус: неполный результат или остановка]
    Q -- да --> D[Диспетчер выбирает готовые задачи]
    D --> A[Специализированные агенты]
    A --> G[Собрать результаты]
    G --> R{Есть ещё задачи плана?}
    R -- да --> D
    R -- нет --> V[Проверить результаты]
    V --> C{Критерии выполнены?}
    C -- да --> O[Сформировать итог]
    C -- нет --> B{Остался лимит на доработку?}
    B -- да --> D
    B -- нет --> F
    O --> E([Успех])
    F --> X([Остановка])
```

Диспетчер отправляет агентам независимые задачи параллельно. Зависимые задачи ждут завершения необходимых предшественников. После сбора результатов диспетчер проверяет готовность следующего этапа.

### Контракты компонентов

- **Координатор-планировщик** получает исходную цель и критерии успеха. Он создаёт конечный список задач: уникальный ID, требуемая специализация, входные данные, ожидаемый результат, критерии приёмки и зависимости. Планировщик вызывается один раз; его повторный запуск без изменения плана не допускается.
- **Диспетчер** выбирает зарегистрированного специалиста, проверяет лимиты и отправляет только задачи с выполненными зависимостями. Он же учитывает попытки и решает, разрешена ли одна доработка.
- **Специализированный агент** получает только назначенную задачу и нужный ей контекст. Он возвращает статус, результат, использованные основания и нерешённые вопросы. Запрос на передачу задачи другому агенту считается неподдерживаемым и возвращается координатору как ограничение.
- **Сборщик** фиксирует ответы по ID задачи и попытки. Он не выбирает «последний записанный» ответ при конфликте: дубликаты ID или несовпадающие результаты считаются ошибкой данных.
- **Проверяющий** сравнивает результаты с исходными критериями, проверяет полноту, формат, противоречия и наличие обоснований. При необходимости проверки фактами или инструментами она должна быть включена в критерии и иметь явно заданный способ проверки.
- **Формирователь ответа** выдаёт итог только после положительной проверки. При исчерпании бюджета возвращает неполный результат и явно перечисляет, что не проверено или не выполнено.

### Состояние графа

Предлагаемые поля:

| Поле | Назначение и правила записи |
|---|---|
| `goal`, `acceptance_criteria` | Исходная цель и критерии; задаются при приёме и далее не переписываются агентами. |
| `task_plan` | План с ID, исполнителями и зависимостями; записывается планировщиком один раз. |
| `dispatch_count`, `revision_count` | Счётчики попыток и доработок; обновляются диспетчером после сбора результата. |
| `results` | Результаты по уникальным ID задачи и попытки; параллельные записи объединяются по ключу, а не по порядку завершения. |
| `review` | Вердикт проверяющего, замечания и ссылки на проверяемые части результата. |
| `final_status`, `final_output`, `stop_reason` | Итог, статус завершения и причина остановки. Заполняются на конечной ветке. |

Состояние не должно зависеть от порядка завершения параллельных агентов. Счётчики обновляются централизованно после сбора результатов, а не каждым агентом параллельно.

### Ограничения делегации и завершение

В качестве стартовых настроек предлагаю:

- не более **8 вызовов исполнителей** на одну задачу верхнего уровня; в лимит входят повторные попытки и доработки;
- не более **4 параллельных задач**;
- не более **1 круга доработки** после проверки;
- повторная попытка разрешена только для временного сбоя, и тоже расходует общий бюджет;
- каждый исполнитель получает ограниченный размер задачи и предел вызовов инструментов;
- одинаковая задача с теми же входными данными и критериями не отправляется повторно без новых сведений или замечаний проверяющего.

**Успех** — все обязательные задачи завершены, а проверяющий подтвердил критерии результата. **Остановка с неполным результатом** — лимит исчерпан, план некорректен, обязательные данные отсутствуют или задача не может быть проверена. У этих исходов разные статусы; исчерпание лимита не маскируется под успех.

### Ошибки и восстановление

Временный сбой агента или инструмента допускает ограниченный повтор в рамках общего бюджета. Невалидный формат, отсутствие требуемого результата или противоречие передаются проверяющему и могут привести к единственной доработке. Недостающие исходные данные завершают проход с запросом уточнения или неполным статусом, а не запускают повторную делегацию.

Если позже понадобится сохранять выполнение между запусками, потребуется отдельно определить восстановление состояния и защиту от повторения внешних действий: checkpoint сам по себе не гарантирует однократность таких действий. В текущем предложении внешние действия не предполагаются.

### Архитектурная проверка и заключение

По описанному графу все штатные пути заканчиваются успехом или явной остановкой. Повторная делегация ограничена общим бюджетом и одним кругом доработки; рекурсивного делегирования нет. Параллельные результаты объединяются по ID, поэтому порядок выполнения не влияет на выбор результата.

**Вердикт: требует доработки перед реализацией.** Контур координации и защита от бесконечной делегации определены, но пока неизвестны предметная область, специализации агентов, реальные критерии приёмки и требуемая строгость проверки. Без них нельзя проверить, что разбиение задач и проверяющий действительно подтверждают нужный пользователю результат. Числа лимитов выше — начальные архитектурные значения для настройки, не утверждённые требования. Это архитектурная оценка, не результат тестирования.
