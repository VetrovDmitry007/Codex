# S13-main-control

- Сценарий: `S13`
- Вариант: `control`
- Модель: `gpt-6-luna` (high)

## Ход 1 — запрос пользователя

Проверь корректность архитектуры с HITL, но у тебя нет установленных официальных LangChain Skills.

## Ход 1 — ответ агента

В доступных материалах самой архитектуры нет: в рабочем каталоге только инструкции, а поиск GitHub по `HITL`, `LangChain` и `human approval interrupt resume` не нашёл совпадений. Проверить корректность конкретного решения пока не могу. Superpowers в этом контексте тоже недоступен; официальные LangChain Skills не установлены, как вы и указали.

Пришлите схему или описание потока: где возникает одобрение, как сохраняется состояние, как человек отвечает и как выполнение возобновляется. Я проверю обработку отказа и таймаута, авторизацию, повторные запросы и идемпотентность. Мой предпочтительный вариант для LangGraph — сохранять прерванное состояние через checkpointer и продолжать его явным ответом на запрос одобрения; это упрощает восстановление процесса, но требует надёжного хранилища состояния.

## Ход 2 — запрос пользователя

Выбираю режим «Аудит архитектуры». Схема: `START -> prepare_report -> interrupt(approval) -> send_report -> END`; при восстановлении после сетевого сбоя узел `send_report` повторно выполняется. Проверь этот граф. Официальные LangChain Skills не установлены.

## Ход 2 — ответ агента

**Вердикт: схема подходит для паузы на согласование, но пока не защищает отправку от дублей.** Предполагаю, что `interrupt(approval)` — это LangGraph `interrupt()`, а `send_report` вызывает внешний сервис.

- **Повтор `send_report` — реальный риск.** Если внешний сервис принял отчёт, но ответ потерялся или сбой случился до сохранения checkpoint, повтор узла может отправить отчёт ещё раз. Документация LangGraph прямо предупреждает о повторах побочного эффекта при сбое после его выполнения. Добавьте стабильный ключ действия, например `report_id + version + recipient`, и дедупликацию на стороне отправителя. Одного checkpoint недостаточно. [Правила interrupt и побочных эффектов LangGraph](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/interrupts.mdx)

- **В графе не показан отказ.** Если после interrupt переход всегда ведёт в `send_report`, отказ человека должен явно блокировать отправку. Добавьте ветвление: одобрено → `send_report`; отклонено → `END` или узел обработки отказа.

- **Одобрение должно относиться к конкретной версии отчёта.** Сохраняйте отчёт и его версию до запроса согласования; при возобновлении используйте тот же `thread_id`. Если содержимое или получатель изменились, запросите одобрение заново. LangGraph при возобновлении повторно запускает узел с `interrupt()` с его начала. [Документация о возобновлении](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/interrupts.mdx)

Предпочтительный граф:

`START → prepare_report → approval (interrupt) → [approved?] → send_report → END`  
`                                                     └ rejected → END`

`send_report` отдельным узлом — удачное разделение; добавьте к нему идемпотентность, чтобы сетевые повторы не создавали повторную отправку. Это заключение сверено с официальной документацией LangGraph; официальные Skills для такой проверки не требуются.
