## Предлагаемое изменение

Утверждённые требования из [спецификации](<[LOCAL_PATH_REDACTED]>) остаются без изменений. В [текущей архитектуре](<[LOCAL_PATH_REDACTED]>) добавляется обязательная пауза между созданием отчёта и его передачей.

Рекомендованный вариант — `interrupt()` в том же графе. Альтернатива — обрабатывать подтверждение отдельным внешним оркестратором; для описанной последовательной схемы это добавило бы лишнюю координацию.

```mermaid
flowchart LR
    START --> create_report --> request_approval
    request_approval -->|явное одобрение| send_report
    request_approval -->|отказ| cancelled([Завершено: отмена])
    request_approval -.->|нет решения или неверный ответ| request_approval
    send_report -->|сервис подтвердил приём| completed([Завершено: успешно])
    send_report -->|ошибка| delivery_error([Ошибка или сверка])
```

## Контракты изменения

**State**

| Поле | Роль и тип | Читатели и писатели | Сохранение |
|---|---|---|---|
| `report` | Отчёт с неизменной схемой `{summary, source_ids, generated_at}` | Пишет `create_report`; читают `request_approval` и `send_report`. После создания не меняется | Checkpoint при паузе и возобновлении |
| `approval_decision` | Внутренний статус: `pending`, `approved` или `rejected` | Пишет `request_approval`; читает маршрутизация | Checkpoint; не включать в тело отчёта |
| `delivery_key` | Внутренний стабильный ключ операции | Создаётся до подтверждения; использует `send_report` | Checkpoint; повторная попытка использует тот же ключ |
| `delivery_status` | `not_started`, `sent`, `failed` или `unknown` | Пишет `send_report`; читают завершение и сверка | Сохранять результат и квитанцию сервиса, если она есть |

Для этих полей достаточно одного писателя на поле; reducer для объединения параллельных записей не нужен. В утверждённую схему отчёта новые поля не добавляются.

**Nodes и маршруты**

- `create_report` формирует существующий отчёт. Его текущие зависимости в исходном описании не указаны.
- `request_approval` передаёт пользователю для проверки точный отчёт и запрашивает явное решение. До `interrupt()` узел не выполняет внешних действий. Решение проверяется; отсутствие или некорректный ответ не трактуется как одобрение.
- По `approved` граф переходит к `send_report`. По `rejected` — завершает операцию без передачи.
- `send_report` отправляет только утверждённый отчёт и фиксирует результат. Прямого ребра от `create_report` к отправке нет.

LangGraph требует checkpointer и идентификатор потока для паузы и возобновления. После `Command(resume=...)` узел с `interrupt()` начинает выполняться заново, поэтому побочные эффекты должны находиться после подтверждения. Возобновлять нужно тот же поток по тому же `thread_id`. [Официальная документация LangGraph](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph)

**Execution, завершение и ошибки**

При начальном запуске граф создаёт отчёт и сохраняет checkpoint на подтверждении. Приложение показывает пользователю отчёт и возобновляет тот же поток с решением. Успех — только подтверждённый приём внешним сервисом; отказ — завершение без отправки. Пока решения нет, граф остаётся на паузе. Некорректное решение оставляет операцию неподтверждённой; исчерпание настроенного лимита попыток или срока ожидания должно завершать её без отправки.

Сбой генерации завершает операцию до запроса подтверждения. Временную ошибку передачи можно повторять с тем же `delivery_key`; при неопределённом результате таймаута нужна проверка результата в сервисе или ручная сверка, а не слепая повторная отправка. Checkpoint сам по себе не гарантирует однократность внешнего действия; ключ идемпотентности или проверка результата должны поддерживаться интеграцией. [Инструкция LangGraph по HITL и повторам](https://github.com/langchain-ai/langchain-skills/blob/main/config/skills/langgraph-human-in-the-loop/SKILL.md)

## Архитектурное заключение

- **Проблема:** текущий граф отправляет отчёт без подтверждения.
- **Критичность:** высокая — нарушено явное требование о согласии пользователя до внешней операции.
- **Последствие:** отчёт может быть передан без одобрения.
- **Рекомендация:** добавить паузу `interrupt()` и разрешать переход к отправке только после явного `approved`; отказ завершает поток без передачи.
- **Вердикт:** **требует доработки перед реализацией**. В предоставленном описании не указано, поддерживает ли внешний сервис идемпотентный ключ или проверку результата, как идентифицируется уполномоченный подтверждающий и где хранится checkpointer. Эти зависимости нужно подтвердить; без них нельзя надёжно проверить повторы отправки и право возобновления потока.
