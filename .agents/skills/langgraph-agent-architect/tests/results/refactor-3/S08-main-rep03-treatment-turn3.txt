## Изменение архитектуры

Изменение сохраняет требования из [approved-requirements.md](specs/approved-requirements.md) без правок. Оно добавляет обязательную паузу после формирования отчёта и до его передачи.

**Выбранный подход:** приостановить существующий граф через LangGraph `interrupt()`, сохранить checkpoint и возобновить граф с ответом пользователя. Альтернатива — управлять ожиданием и подтверждением во внешнем приложении, сохраняя статус операции отдельно. Она потребует дополнительного слоя оркестрации; для описанного линейного графа рекомендую `interrupt()`.

Текущая архитектура называет «граф», но не фиксирует фреймворк и его версию. Ниже предполагается, что это LangGraph `StateGraph`. Для `interrupt()` необходимы checkpointer и стабильный `thread_id`; при возобновлении узел с прерыванием запускается заново с начала. [Официальные инструкции LangGraph по HITL](https://raw.githubusercontent.com/langchain-ai/langchain-skills/main/config/skills/langgraph-human-in-the-loop/SKILL.md) · [Инструкции по persistence и checkpoints](https://raw.githubusercontent.com/langchain-ai/langchain-skills/main/config/skills/langgraph-persistence/SKILL.md)

### Схема

```mermaid
flowchart TD
    START --> generate_report
    generate_report --> approval_gate
    approval_gate -->|interrupt: ждёт ответа| PAUSED[Ожидание подтверждения]
    PAUSED -. "Command(resume), тот же thread_id" .-> approval_gate
    approval_gate -->|approved| send_report
    approval_gate -->|rejected| cancelled
    approval_gate -->|invalid| invalid_decision
    send_report --> END
    cancelled --> END
    invalid_decision --> END
```

`PAUSED` — приостановленное выполнение, а не отдельный узел графа. Приложение показывает пользователю содержимое отчёта и передаёт решение обратно графу.

### State

| Поле | Тип и роль | Читатели и писатели | Обновление и хранение |
|---|---|---|---|
| `report` | Объект с `summary: string`, `source_ids: string[]`, `generated_at: string` в ISO 8601 | Пишет `generate_report`; читают `approval_gate` и `send_report` | Записывается один раз и остаётся неизменным до завершения; хранится в checkpoint |
| `approval_status` | `awaiting_confirmation \| approved \| rejected \| invalid` | Начальный статус пишет `generate_report`; решение записывает `approval_gate`; статус читает условная маршрутизация | Последовательная перезапись, без reducer; сохраняется между паузой и resume |
| `delivery_status` | `not_attempted \| sent \| failed` | Инициализирует `generate_report`; обновляет `send_report` | Последовательная перезапись, без reducer; сохраняется в checkpoint |
| `thread_id` | Строка в конфигурации запуска, идентификатор одной операции | Передаёт контроллер приложения при запуске и resume | Не поле State; используется checkpointer для сохранения и восстановления выполнения |

Пользователь подтверждает именно сохранённый объект `report`. Отчёт после показа не редактируется. Если продукту понадобится редактирование, это будет отдельное изменение требований.

### Узлы и маршруты

- **`generate_report`** формирует отчёт существующим механизмом генерации; конкретная LLM или источник данных в текущей архитектуре не указаны. Записывает отчёт, `approval_status=awaiting_confirmation` и `delivery_status=not_attempted`. Ошибка генерации завершает операцию без отправки.
- **`approval_gate`** передаёт пользователю действие и все три поля отчёта через `interrupt()`. После resume проверяет решение и записывает `approved`, `rejected` или `invalid`. До прерывания узел выполняет только подготовку данных в памяти — внешних действий в нём нет.
- **Условная маршрутизация** ведёт `approved` к отправке, `rejected` к отмене, `invalid` к безопасному завершению. Используется условный маршрут; отдельный `Command(goto=...)` здесь не нужен.
- **`send_report`** вызывается только после `approved`, отправляет тот же сохранённый объект и обновляет `delivery_status`. В графе нет прямого маршрута от создания отчёта к этому узлу.
- **`cancelled`** завершает операцию после отказа, не вызывая внешний сервис.
- **`invalid_decision`** завершает операцию без отправки, если ответ не распознан как явное подтверждение или отказ.

### Выполнение, завершение и ошибки

Граф работает последовательно: сформировать отчёт → дождаться решения → отправить или завершить без передачи. ReAct-цикла, параллельных ветвей и многоагентной делегации здесь не требуется.

Успех — внешний сервис принял отчёт, а `delivery_status=sent`. Отказ — `approval_status=rejected`, отправки нет. Некорректный ответ, сбой генерации или исчерпание ограниченных повторов отправки завершают операцию без ложного успеха. Повторять следует только временные ошибки и только в пределах заданного конечного лимита; постоянные ошибки не повторяются. Отсутствие ответа не должно трактоваться как подтверждение: операция остаётся приостановленной либо завершается по явно заданной политике срока ожидания.

Контроллер приложения обязан показать interrupt пользователю, передавать ответ в тот же `thread_id` и проверять, что пользователь вправе возобновить эту операцию. Повторное или устаревшее подтверждение не должно запускать отправку второй раз.

Checkpoint сам по себе не гарантирует однократность внешней операции. Узел отправки должен использовать поддерживаемый внешним сервисом idempotency key либо проверять результат уже выполненной отправки перед повтором. Иначе сбой после принятия отчёта сервисом, но до сохранения checkpoint, может привести к дубликату.

### Проверка архитектуры и заключение

Поток достижим и маршруты не пересекаются: отправка возможна только после подтверждения; отказ и некорректный ответ заканчиваются без внешнего вызова. Пауза восстанавливает состояние по `thread_id`; запись отчёта и решение согласованы через один checkpoint. В текущем описании не указаны LangGraph и его версия, вид долговременного checkpointer, срок хранения ожидающих подтверждения, проверка прав пользователя, политика истечения ожидания и механизм защиты от повторной отправки.

**Проблема:** в текущей архитектуре отправка происходит сразу, без подтверждения.  
**Критичность:** высокая — нарушается явное требование пользователя.  
**Последствие:** отчёт может быть передан без согласия.  
**Рекомендация:** вставить checkpointed approval gate перед узлом отправки и разрешать маршрут к нему только при явном `approved`.  
**Вердикт:** **требует доработки** — архитектурное решение описано, но перед реализацией нужно подтвердить поддержку idempotency или проверки результата внешним сервисом, а также выбрать production checkpointer. Это архитектурное заключение, не результат тестирования кода.
