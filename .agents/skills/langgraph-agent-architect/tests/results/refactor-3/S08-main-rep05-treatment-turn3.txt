Подтверждение трактую как выбор рекомендованного варианта: **пауза внутри графа через `interrupt()`**. Ниже — обновлённая архитектура для чата; утверждённые требования не менял, в файлы и GitHub ничего не записывал.

## Architecture

Сохраняем последовательный `StateGraph`: он формирует отчёт, приостанавливается для решения человека и только после подтверждения отправляет отчёт. Отказ ведёт к завершению без вызова внешнего сервиса. Два отдельных запуска графа здесь не нужны: исходная схема уже представляет один последовательный процесс.

## State

Все поля сохраняются в checkpoint по отдельному `thread_id` для операции. Для простых полей используется замена значения, без reducer.

| Поле | Роль и тип | Читатели и писатели |
|---|---|---|
| `request_context` | Входные данные запроса; точная структура в текущей архитектуре не описана | Читает `generate_report`; источник и тип требуют уточнения |
| `report` | Объект `{summary: string, source_ids: string[], generated_at: string}` | Записывает `generate_report`; читают `request_approval` и `send_report` |
| `operation_id` | Стабильный идентификатор отправки | Создаёт `generate_report`; использует `send_report` для сверки результата и защиты от дублей |
| `approval_decision` | `pending | approved | rejected` | Инициализирует `generate_report`; после возобновления обновляет `request_approval`; читает маршрутизатор |
| `delivery_attempts` | Счётчик попыток отправки | Читает и обновляет `send_report` |
| `delivery_status` | `awaiting_approval | cancelled | sent | failed | outcome_unknown` | Обновляют узлы подтверждения, отмены и отправки |
| `delivery_receipt` | Необязательная квитанция внешнего сервиса | Записывает `send_report` после подтверждённой отправки |

Утверждённая схема самого отчёта остаётся неизменной; идентификатор операции и состояние отправки — служебные поля графа.

## Nodes и Edges

```mermaid
flowchart TD
    START --> generate_report
    generate_report --> request_approval
    request_approval -->|approved| send_report
    request_approval -->|rejected| cancel_delivery
    send_report -->|успех| END
    send_report -->|повторяемая ошибка, лимит не исчерпан| send_report
    send_report -->|ошибка или исчерпан лимит| delivery_failed
    send_report -->|неизвестен результат операции| delivery_outcome_unknown
    cancel_delivery --> END
    delivery_failed --> END
    delivery_outcome_unknown --> END
```

- **`generate_report`** читает запрос и формирует отчёт строго с тремя утверждёнными полями. Инициализирует `approval_decision=pending`, `delivery_attempts=0` и стабильный `operation_id`. При ошибке генерации завершает поток ошибкой; отправка не вызывается.
- **`request_approval`** показывает человеку сформированный отчёт и вызывает `interrupt()`. При возобновлении принимает только явное `approved` или `rejected`; некорректный ответ остаётся на шаге подтверждения. До `interrupt()` узел не выполняет внешних побочных действий.
- **Маршрутизация после подтверждения** — условный переход: `approved` направляет в `send_report`, `rejected` — в `cancel_delivery`. Отсутствие или некорректность решения не может попасть в ветку отправки.
- **`send_report`** передаёт неизменённый после подтверждения отчёт внешнему сервису, используя `operation_id` как ключ идемпотентности. Повтор допускается только для повторяемой ошибки и в заданном лимите. При неоднозначном ответе сначала сверяется результат операции по `operation_id`; если его нельзя установить, поток завершается с `outcome_unknown`, без слепой повторной отправки.
- **`cancel_delivery`** фиксирует отказ и `delivery_status=cancelled`; внешних вызовов не делает. Ошибочные или исчерпавшие лимит отправки завершаются с `failed`.

## Execution и Termination

Старт → генерация отчёта → ожидание решения → условная отправка или отмена. Успех — внешний сервис подтвердил приём отчёта. Отказ — операция отменена. Ошибка генерации, постоянная ошибка отправки или исчерпание лимита — неуспешное завершение. Неопределённый результат отправки отдельно помечается `outcome_unknown`. Пока человек не ответил, граф остаётся приостановленным; срок ожидания требованиями не задан.

Для `interrupt()` нужны checkpoint и `thread_id`; возобновление передаёт решение через `Command(resume=...)`. При возобновлении узел с `interrupt()` начинается заново, поэтому отправка вынесена в отдельный узел после подтверждения. Checkpoint сам по себе не защищает внешний вызов от дублей; нужна идемпотентность или сверка результата у сервиса. [Официальное руководство по HITL](https://github.com/langchain-ai/langchain-skills/blob/main/config/skills/langgraph-human-in-the-loop/SKILL.md) описывает паузу и возобновление, а также повторный запуск узла; [руководство по persistence](https://github.com/langchain-ai/langchain-skills/blob/main/config/skills/langgraph-persistence/SKILL.md) — роль checkpoint и `thread_id`.

## Архитектурное заключение

**Проблема:** исходная схема отправляет отчёт сразу, без подтверждения; также неизвестно, умеет ли внешний сервис дедуплицировать отправки или проверять их результат.

**Критичность:** отсутствие подтверждения — высокая, поскольку нарушает утверждённое требование; отсутствие гарантии идемпотентности — высокая при возобновлении и сетевых сбоях.

**Последствие:** отчёт может уйти без согласия либо отправиться повторно после неоднозначного ответа сервиса.

**Рекомендация:** поставить `interrupt()` перед отправкой и привязать решение к `thread_id` и `operation_id`; до реализации проверить поддержку идемпотентного ключа или поиска результата во внешнем сервисе, а также авторизацию пользователя, который возобновляет поток.

**Вердикт: требует доработки перед реализацией** — контракт подтверждения спроектирован, но свойства внешнего сервиса и проверка полномочий подтверждающего пока неизвестны.
