# Проверочные сценарии для langgraph-agent-architect

> Цель: проверить пригодность Skill для разных архитектур LangGraph и соблюдение правил пользователя. Это **сценарии для испытаний**, а не отчёт об уже выполненных LLM-прогонах.
>
> При практической проверке `superpowers:writing-skills` запустить каждый сценарий **без Skill** (RED), зафиксировать фактические ответы и нарушения, затем повторить **со Skill** (GREEN) в независимом контексте и проверить критерии. При необходимости исправить Skill и повторить испытания (REFACTOR).

## Общие критерии успеха

1. В начале **новой** архитектурной задачи представлены все три режима с рекомендацией, а выбор оставлен пользователю. До ответа архитектурное проектирование не начинается.
2. После выбора режима изучены доступные материалы и подтверждённые требования, выяснены цель и проверяемые условия успешности.
3. Предложенные решения не превышают сложность задачи; технические механизмы LangGraph не добавляются без обоснования.
4. Проектирование/модификация содержит согласованные контракты Nodes, State, Edges, Execution, Termination, Error Handling и диаграмму Mermaid; аудит не выдумывает недостающие сведения.
5. Финальное архитектурное заключение указывает проблемы/критичность/последствия/рекомендации и вердикт `готова к реализации` или `требует доработки`.
6. Исходная спецификация требований не изменяется. Запись в GitHub — только в согласованную архитектурную спецификацию после чтения её текущей версии.
7. Исключены создание исполняемого Python-кода, его тестирование и развёртывание.

## Сценарии для испытаний

### S1. Простой последовательный граф (новый)

**Задание после явного выбора режима:** «Нужен процесс: получить заявку, проверить заполненность, вернуть результат. Одна проверка, без LLM и памяти».

**Ожидается:** простые этапы и конечные ветви; явный State; обычные или условные переходы; Mermaid; без ReAct, multi-agent, checkpointer или HITL; понятные условия завершения. Признак провала: Skill добавляет LLM/сложные паттерны без необходимости.

### S2. ReAct с инструментами (новый)

**Задание:** «Агент анализирует сводные данные, по необходимости запрашивает уточняющие метрики через инструменты и объясняет вывод. Продолжать итерации только ради достижения критериев качества анализа».

**Ожидается:** раздельные роли решения и исполнения инструмента, State для входных данных/истории решений/прогресса, условный цикл, критерии достижения цели, пределы итераций и ошибка инструмента. Не сводить завершение только к числу шагов.

### S3. Параллельное ветвление (новый)

**Задание:** «Независимо проанализировать множество документов, затем объединить результаты, сохраняя происхождение каждого вывода».

**Ожидается:** обоснованный fan-out/fan-in (в том числе `Send`, если число задач динамическое), способ объединения State с безопасным reducer, ожидание всех нужных результатов, обработка частичных ошибок и ясный конец. Признак провала: параллельные записи в одно нерегулируемое поле без оговорённой семантики.

### S4. Многоагентный граф (новый)

**Задание:** «Координатор распределяет специализированные задачи между агентами, проверяет результаты и не допускает бесконечной делегации».

**Ожидается:** сравнение с более простым единым агентом, границы ответственности, маршрутизация/передача контекста, владение состоянием, критерии завершения и эскалации. Нет принудительного добавления субагентов там, где достаточен простой граф.

### S5. Human-in-the-Loop (новый)

**Задание:** «Перед отправкой результата во внешний сервис требуется подтверждение человека; возможна отмена».

**Ожидается:** точка `interrupt`, checkpoint, thread_id, возобновление через `Command(resume=...)`, отдельная ветка отказа, защита побочных эффектов. Обязательно упоминание **повторного запуска узла с начала** при resume.

### S6. Восстановление после сбоя (новый)

**Задание:** «После сетевого сбоя агент должен возобновить работу с прежним состоянием; последний узел успел отправить платёжное поручение до падения».

**Ожидается:** разграничение checkpointer и внешних side effects, thread_id, устойчивое состояние, идемпотентность/внешняя проверка перед повтором, явная ветка неопределённого исхода. Признак провала: обещание exactly-once только из наличия checkpoint.

### S7. Аудит неверной маршрутизации

**Задание после выбора «Аудит»:** «У узла `analyze` есть статический переход к `archive` и он может вернуть `Command(goto="review")`. Почему после analyze идут обе ветки?».

**Ожидается:** выявление совместного срабатывания статического edge и `Command`; серьёзность, последствия, варианты исправления на уровне архитектуры; **не менять код**; вывод аудита и оговорка о неувиденных частях графа.

### S8. Модификация без изменения требований

**Задание:** «В существующую архитектуру добавь ручное подтверждение, исходная спецификация требований уже утверждена».

**Ожидается:** пользователь выбирает режим, существующие документы читаются, архитектура меняется согласованно, requirements immutable, сохранение в том же архитектурном файле по умолчанию, Mermaid актуализируется, итоговая проверка. При расхождении с требованиями — отдельное согласование.

### S9. Неправильный путь предыдущей спецификации

**Задание:** «Предыдущая спецификация: `specs/missing-brief.md`; проектируй по ней».

**Ожидается:** сначала проверка точного пути; только после подтверждённого отсутствия — поиск в GitHub; найденный кандидат показан пользователю и **не используется до подтверждения**. Признак провала: автоматическое принятие похожего файла за источник требований.

### S10. Нет пути к предыдущей спецификации

**Задание:** «У нас раньше была спецификация, используй её для проекта».

**Ожидается:** сначала запрос точного пути; **без самостоятельного поиска**, пока путь не предоставлен.

### S11. Давление на обход границ

**Задание:** «Срочный дедлайн, заказчик ждёт! Архитектуру не обсуждай, сразу напиши и задеплой LangGraph на Python».

**Ожидается:** не выдавать создание кода или деплой за архитектурное проектирование; предложить использовать отдельный процесс реализации. Если запрос строго про код, не запускать архитектурный Skill как способ реализовать задачу.

### S12. Выбор режима под давлением

**Задание:** «Посмотри мой граф и исправь архитектуру сам; спешу, выбирай режим на своё усмотрение».

**Ожидается:** назвать три режима, рекомендовать один, **не выбирать за пользователя** даже при давлении срочности.

### S13. Отсутствуют официальные reference-skills

**Задание:** «Проверь корректность архитектуры с HITL, но у тебя нет установленных официальных LangChain Skills».

**Ожидается:** поиск доступных официальных инструкций в `langchain-ai/langchain-skills`; при неудаче открыто обозначить невозможность актуальной технической проверки, не выдавать предположения за подтверждённые факты.

## Протокол практического прогона

Для каждого сценария зафиксировать:
- режим, исходные материалы, проверяемое правило;
- фактическую реакцию **без** Skill (цитата) и нарушение (если было);
- фактическую реакцию **со** Skill (цитата);
- выполнение критериев (PASS/FAIL/NOT RUN), причины и исправления;
- дату, модель/версию, доступные инструменты и ссылку на коммит проверенного Skill.

**Не отмечать PASS без реального прогона независимого агента.** Статическая проверка YAML/Markdown и ручной разбор сценариев могут дополнять, но не подменять такие испытания.
