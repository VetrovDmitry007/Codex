# Telegram Widgets + aiogram (TrainBot)

## Назначение и источники

Специализированная методика проектирования **HTML Widgets Telegram Bot API** для Python-ботов с **aiogram 3**, прежде всего TrainBot. Superpowers отвечает за обсуждение, планирование, TDD и проверку; этот Skill — за платформенные контракты, UX, FSM, безопасность и интеграцию. Не путай Widgets, inline-кнопки и Telegram Mini Apps.

**Перед каждым значимым изменением сверяй с первоисточниками**, поскольку ограничения могут измениться:
- Telegram Widgets: https://core.telegram.org/bots/widgets
- Telegram Bot API: https://core.telegram.org/bots/api
- Bot API changelog: https://core.telegram.org/bots/api-changelog
- aiogram: https://docs.aiogram.dev/ и фактически установленные зависимости проекта.

Не объявляй неподтверждённые методы aiogram «нативными». Не приписывай клиенту функций WebView, отсутствующих у Widgets.

## Сначала выбери подход

| Сценарий | Предпочтительное решение |
|---|---|
| Выбор из 2–5 простых действий | Обычная inline-клавиатура |
| Календарь, компактный список станций, схема мест, карточка подписки прямо в сообщении | Widget |
| Свободный ввод станции, длинная форма, клиентские HTTP-запросы | Сообщения чата + хендлеры либо Mini App |
| Большая многостраничная форма/приложение | Mini App |

Объясни выгоду для пользователя, влияние на текущий сценарий и fallback для старого клиента. LLM можно применять для генерации шаблона **при разработке**, но в штатной работе TrainBot предпочтительны проверенные версионированные HTML-шаблоны: без LLM-генерации при каждом клике.

## Платформенные инварианты: Bot API 10.4 (2026-11-09)

- В production виджеты разрешены в **личных чатах с ботом**; группы, inline и пересылка недоступны, пока Telegram не анонсирует иного.
- Самодостаточный HTML с разрешёнными inline CSS/JS. **HTML после отправки изменить нельзя**; можно изменять данные виджета. Это не полноценный DOM браузера.
- Код: максимум **32768 байт UTF-8** и **4096 байт после zlib.compress(html.encode("utf-8"), 9)**; запрещён NUL.
- Размер chat_data/public_data — **1024 байта UTF-8** на каждое поле. Размер строки TelegramWidget.request(data) — **1–64 байта UTF-8**; данные ответа answerWidgetQuery — **до 1024 байт**.
- Ответь на **каждый** widget_query в течение **15 секунд**. Лимит: **5 запросов за 5 секунд** на пользователя и бота. Обновление выбора дня/месяца выполняй локально, не посылай запрос на каждый клик.
- **QuickJS-песочница**: нет произвольных сетевых запросов и клавиатурного текстового ввода; не используй fetch, внешние скрипты или неподтверждённые browser/WebView API. Код и CSS проверяй по поддерживаемому профилю Telegram.
- TelegramWidget.request() генерирует widget_query (или shared_widget_query для пересланного shared widget). **answerWidgetQuery не меняет данные виджета**; для этого предназначены editMessageWidgetData и editSharedWidgetData.
- В widget_query есть id, from, type, data и, в зависимости от происхождения, chat + message_id либо inline_message_id. type — структурированный WidgetQueryType. Для TrainBot по умолчанию поддерживай только собственные виджеты в приватных чатах.

## Интеграция с aiogram 3

1. Найди точную установленную версию aiogram (lock/requirements). Проверяй наличие нативных типов и методов Widgets в **этой** версии. При их наличии используй штатные API; при отсутствии — отдельный проверенный адаптер Telegram Bot API и перехват сырого Update.
2. Для Long Polling: разреши **allowed_updates=[*dp.resolve_used_update_types(), "widget_query"]** в dp.start_polling(). Для Webhook — параметр allowed_updates у set_webhook(). Для shared widgets при необходимости добавь shared_widget_query. Не теряй уже зарегистрированные типы.
3. В старом aiogram возможен перехват через **dp.update.outer_middleware()** и чтение **event.model_extra.get("widget_query")**; сначала проверь действительную сериализацию неподдерживаемого события. Не объявляй несуществующий @router.widget_query рабочим. Запрос должен быть перехвачен до штатной маршрутизации и получить ровно один ответ.
4. Для интеграции с FSM получай контекст пользователя через **dp.fsm.get_context(bot=bot, chat_id=..., user_id=...)**. В актуальном aiogram 3 этот метод синхронно возвращает FSMContext; **не await** на get_context. await применяется к state.get_state(), update_data(), set_state(). Проверяй сигнатуры установленной версии.
5. Используй текущую сессию Bot/aiogram и её proxy-настройки; не создавай новую aiohttp-сессию для каждого widget query. Не предполагая существования bot.send_widget, определяй метод в адаптере по официальной спецификации.
6. Раздели транспорт (Widget API), получение события/авторизацию (widget_query), HTML-шаблон и существующие обработчики/сервисы подписки. Не переизобретай все FSM в одном универсальном менеджере.

### Контракт DatePicker для TrainBot

~~~text
Кнопка «Дата отправления» -> sendWidget(calendar.html)
  -> JS локально переключает месяцы и отмечает дату
  -> подтверждение вызывает TelegramWidget.request("date:2026-11-20")
  -> widget_query -> сверить отправителя, чат, message_id и FSM state
  -> проверить допустимость даты на сервере
  -> FSM.update_data(dt_depart="2026-11-20"); FSM.set_state(None)
  -> answerWidgetQuery(...) -> обновить/показать меню параметров
~~~

Минимальный клиентский фрагмент для обработчика нажатия:
~~~javascript
// date: ISO YYYY-MM-DD; вызов из обработчика подтверждения.
TelegramWidget.request("date:" + date)
  .then(({result}) => showResult(result))
  .catch(() => showError("Дата не сохранена"));
~~~
Функции showResult и showError нужно **реализовать в шаблоне**. Это иллюстрация контракта, не полный HTML-виджет.

По ранее предоставленным исходникам TrainBot: handlers/subscrib.py содержит StSubscr.dt_depart, prm_sub_otslej(), поля dt_depart, DepName/DepCode, DestName/DestCode; core/util_bot.py — ch_dt_depart(), get_expressCode_async(). Это ориентиры для **проверки текущей версии исходников**, не гарантия неизменности. Аналогичные обработчики даты могут быть в booking.py, otslej_15.py, grand_servs.py: **не редактируй их без запроса**.

Для **станции**: популярные/недавние — кнопками Widget; произвольный поиск — в обычном сообщении чата или Mini App; всегда используй проверенный код станции из серверного справочника.

## Безопасность и надёжность

- Входные данные клиентского JS недоверенные, как callback_data. Сервер сверяет from.id, chat.id, message_id (либо другой официальный идентификатор), ожидаемое FSM-состояние и владельца черновика. Отклоняй старые виджеты, чужих пользователей и неожиданные команды.
- Даты проверяй на существование, ISO-формат, локальную дату/часовой пояс, горизонт продаж и ограничения перевозчика; не полагайся только на выключенные кнопки. Станции — по справочнику и ID.
- Повторные запросы **идемпотентны**. Ни клик по кнопке, ни результат LLM не равны успешной брони или списанию: подтверждение возвращает backend после фактического результата.
- Не публикуй токены, cookies, учётные записи, паспортные/пассажирские данные в HTML, публичных данных виджета, логах или GitHub. Не отправляй их в LLM без отдельной необходимости и разрешения.
- Отвечай быстро, тяжёлые операции выноси после подтверждения приёма, обрабатывай таймаут и rate limit. Дай fallback в чат.
- MemoryStorage теряет FSM при рестарте: откажи устаревшему виджету с понятным сообщением или обоснуй устойчивое хранилище. Не привязывай старую дату к новой подписке.
- UX: контрастность, светлая/тёмная тема, узкий экран, большие зоны нажатия, явные «Отмена»/«Подтвердить», сообщения об ошибках.

## Порядок работы

1. Изучи задачу и текущий код. Покажи краткий сценарий пользователя, сравни inline / Widget / Mini App; выбери минимальное подходящее решение.
2. Сверь актуальные Telegram и aiogram API, ограничения, путь события и FSM, текущий транспорт/proxy. Опиши контракт UI -> request -> Update -> service/FSM -> answer/обновление данных.
3. Подготовь макет, критерии приёмки, ошибки и fallback. Архитектуру согласуй через Superpowers до реализации.
4. При реализации используй Superpowers: test-driven-development, writing-plans, verification-before-completion. Для самого Skill — writing-skills.
5. Измерь UTF-8/zlib размеры; проверь корректность разрешённого HTML/JS, unit/integration тесты и (если доступны) реальные Telegram-клиенты.
6. Отдельно отчитайся: спроектировано, реализовано, проверено на тестах, проверено на реальном Telegram. **Не выдавай статическую проверку за LLM eval или Telegram E2E.**

### Контрольные сценарии

- «Хочу вводить название станции клавиатурой прямо в Widget» -> предложить обычный чат или Mini App; не обещать HTML input.
- «В моём aiogram нет widget_query» -> изучить версию и сделать адаптер с allowed_updates; не придумывать нативный хендлер.
- «Пользователь нажал дважды, FSM перезапустился, widget старый» -> серверная проверка state/ownership, отказ без повторного создания подписки.
- «Не пришёл answer за 15 секунд» -> быстрый ответ и отдельная долгая задача; корректное сообщение о сбое.

## Чек-лист перед завершением

- [ ] Применимость Widget и fallback обоснованы
- [ ] Версии Bot API и aiogram проверены; названия и сигнатуры не выдуманы
- [ ] Лимиты HTML, zlib, request, answer и chat/public data соблюдены
- [ ] Один query получает один своевременный ответ, операция идемпотентна
- [ ] FSM, права пользователя, календарные ограничения проверяются сервером
- [ ] Ошибки, старый виджет, рестарт FSM и старые клиенты учтены
- [ ] Результаты тестирования подтверждены, а не предположены
