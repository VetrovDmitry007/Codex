# TrainBot — оптимизация привлечения посетителей через Яндекс Директ

## Цель и границы

Специализированный Skill для https://trainbot.ru/. **Главная метрика — число уникальных посетителей сайта из Яндекс Директа за согласованный период** при заданном рекламном бюджете и ограничениях. Не подменять её показами, кликами, CTR, визитами или переходами в Telegram. Качество и релевантность трафика — обязательные ограничения, а не повод подменить пользовательскую цель конверсиями.

Результат работы — **обоснованное техническое задание**, а не самостоятельное изменение рекламного кабинета. Органическое SEO рассматривается только в той части, которая помогает рекламным посадочным страницам.

## Перед началом

1. Прочитать `instructions/trainbot-skill-development.md` и `instructions/interaction-rules.md` из репозитория `VetrovDmitry007/Codex` с помощью подключённого GitHub. Искать согласованные спецификации в `specs/`; не создавать новую без согласования выбора файла.
2. Проверить факты о TrainBot на самом сайте, в согласованном описании продукта и актуальных материалах. Не приписывать сервису функции, условия или гарантии без подтверждения.
3. Проверить согласованность цели, периода, определения «посетителя», бюджета, регионов и возможных ограничений. Неизвестные значения оставлять неизвестными. Если данные недоступны, выполнить только доступную часть и явно показать пробелы.
4. Для анализа Яндекс Директа и посадочных страниц использовать методики внешних специализированных Skills, перечисленных в инструкции проекта: `Silverov/yandex-direct-skill`, `Horosheff/google-yandex-seo-skill`, `coreyhaines31/marketingskills`. Это **справочные проекты**, а не заведомо подключённые инструменты; проверять их текущее содержание и официальную документацию Яндекса.

## Последовательность анализа

1. **Измерение:** установить, есть ли счетчик Метрики, определён ли источник «Яндекс Директ», сохранены ли рекламные метки/идентификаторы переходов и можно ли доверять данным. Различать клики Директа, визиты Метрики и уникальных посетителей. Уникальных посетителей по отдельным кампаниям нельзя механически суммировать без проверки дедупликации.
2. **Исходный уровень:** получить период и сопоставимый период сравнения; оценить число посетителей из Директа, расход и стоимость привлечённого посетителя (`расход / посетители`) при ненулевом знаменателе. Отмечать способ атрибуции и полноту данных. При отсутствии статистики не придумывать показатели.
3. **Диагностика рекламы:** проверить поисковые запросы и релевантность, географию, расписание, сеть (поиск/РСЯ), кампании/группы, таргетинги, бюджетные ограничения, объявления и посадочные страницы. Не советовать масштабирование дешёвого, но нерелевантного трафика.
4. **Диагностика сайта:** сопоставить рекламные обещания с содержанием страниц TrainBot; проверить доступность посадочных страниц, мобильный сценарий и путь к Telegram-боту. SEO-аудит выполнять целенаправленно, а не вместо анализа Директа.
5. **Гипотезы:** для каждого выявленного ограничения связать наблюдение → возможную причину → требуемую проверку → предложение изменения → измеримый ожидаемый эффект. Отделять подтверждённые факты от гипотез, учитывать риск ухудшения и объем данных.
6. **Задание:** выдать приоритетный список конкретных изменений по шаблону `references/optimization-task-template.md`. Если нет данных для доказательных изменений, сформировать задачу на измерение/сбор статистики, не выдавая предположения за готовые решения.

## Жёсткие правила

- Никаких команд изменения рекламного кабинета (создание, пауза, удаление, ставки, бюджет, таргетинг, объявления, фразы) без отдельного явного согласования **конкретных** действий.
- Не выдавать обещание роста посетителей за гарантированный результат; отдельно фиксировать риски и план проверки.
- Не публиковать в GitHub токены, идентифицирующие пользователей данные и непубличные отчёты без согласования.
- Перед изменениями самого Skill использовать **Superpowers**: `brainstorming`, `writing-skills`, `test-driven-development`, `verification-before-completion`; хранить согласованные правки через GitHub.
- Для тестирования Skill использовать `tests/evaluation-cases.md`; не утверждать, что LLM-тестирование прошло, пока независимые прогоны не выполнены.

## Результат

Краткое резюме → фактологическая база с источниками и периодом → ключевые ограничения роста → приоритизированное ТЗ → критерии приемки и последующего измерения. Шаблон: `references/optimization-task-template.md`.
