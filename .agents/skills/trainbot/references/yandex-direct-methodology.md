# Методика применения SEO/PPC Skills к TrainBot

**Цель:** максимизировать количество **уникальных посетителей trainbot.ru из Яндекс Директа** за согласованный период и бюджет. SEO — вспомогательный аудит посадочной страницы, а не цель органического ранжирования. Дата обзора источников: **2026-11-04**.

## Источники и границы применимости

1. [Silverov/yandex-direct-skill — SKILL.md](https://github.com/Silverov/yandex-direct-skill/blob/master/SKILL.md) и [yandex-audit.md](https://github.com/Silverov/yandex-direct-skill/blob/master/references/yandex-audit.md): перечень проверок кампаний ЕПК, поисковых фраз, стратегии, отчётов и Метрики. **Переносить только проверки, релевантные цели «посетители»**. Не использовать CPA/ROAS как обязательные критерии без соответствующей бизнес-цели. Не считать фиксированные пороги/баллы доказанными.
2. [Horosheff/google-yandex-seo-skill — IndexLift](https://github.com/Horosheff/google-yandex-seo-skill/tree/main/.agents/skills/indexlift-seo-auditor): аудит технического состояния и контентной релевантности посадочной страницы, CTA и mobile UX. Для Директа приоритетны рабочая страница и соответствие объявлению; поисковые позиции и обратные ссылки не являются главными KPI.

4. **Официальные источники для проверки актуальных правил:** [Метрика: «Директ, сводка»](https://yandex.ru/support/metrica/ru/sources/direct-summary), [Директ: поисковые запросы](https://yandex.ru/support/direct/ru/statistics/library/search-queries), [Директ: оценка эффективности через Метрику](https://yandex.ru/support/direct/ru/statistics/metrika). При конфликте с внешними Skills опираться на официальную документацию.

## Применение к TrainBot

### Метрика сначала

- Основной KPI: **уникальные посетители сайта из Яндекс Директа**. Зафиксировать период, фильтр источника, модель атрибуции и ограничения бюджета; не складывать уникальных пользователей кампаний без дедупликации.
- Из отчёта Метрики **«Директ, сводка»** получить посетителей по выбранному периоду, если корректно связаны счетчик Директа и сайт. Проверить счетчик кампании, `yclid` и посадочные страницы; наличие счетчика по публичной странице не доказывает корректность атрибуции.
- Расходы брать из сопоставимого отчёта Директа/Метрики и рассчитывать **стоимость посетителя = расход / посетители** (только при ненулевом количестве и сопоставимых периодах). Это диагностическая метрика, не заменяющая целевой показатель объёма уникальных посетителей.
- Клики, визиты, посетители, переходы в Telegram и старты бота **не взаимозаменяемы**. Переход в Telegram — полезный вторичный контроль качества, если событие измеряется; он не заменяет основную цель.
- При недостатке данных ставить `MISSING` и готовить план измерения вместо вымышленных выводов.

### Аудит рекламы

- Поиск / РСЯ: сравнить источники отдельно, бюджеты, темпы расходования, количество посетителей и стоимость посетителя. Не предполагать, что ЕПК разделена на кампании по сетям.
- Семантика: отчёт Директа **«Поисковые запросы»** (в официальной документации доступность за последние 180 дней); сравнить фактические запросы с функциональностью TrainBot и ожиданиями посетителя.
- Проверить автотаргетинг, соответствие креативов посадочной странице, ограничения показов, регионы и активность кампаний. Предлагать минус-фразы **только из подтверждённого отчёта**, с проверкой риска блокировки релевантных запросов.
- Проверить историю изменений, объем статистики и ограничения текущей стратегии, прежде чем рекомендовать смену ставок/бюджета/структуры.
- Не применять из сторонних Skills без адаптации «отключить при CPA > N», обязательную доходность/ROAS, нормы CTR или рекомендацию «конверсионная стратегия нужна всегда»: это не соответствует безусловно выбранной цели трафика.

### Аудит посадочной страницы TrainBot

- Основная страница ведёт в Telegram @best_train_bot. Проверить: страница открывается из объявления с параметрами `yclid`/UTM, корректно загружается на мобильных устройствах и объясняет, что TrainBot — **сервис**, а не железнодорожная касса.
- Для групп объявлений об отслеживании, наличии мест, нижних полках и совместной поездке сверять, что объявление не обещает то, чего нет в опубликованных функциях/условиях.
- Проверить понятность CTA «Перейти к боту» и измерение перехода в Telegram как **дополнительного** события.
- Отдельно проверять тарифы, акции, гарантии наличия мест, условия привязки РЖД — они могут изменяться.
- Техническое SEO (robots, sitemap, canonical, заголовки, региональность) проверять по реальному HTML и фактическим ответам сервера; невозможность проверить ≠ ошибка сайта.

## Формат решения

После анализа каждое предложение отнести к:
- **FIX** — подтверждённая проблема с установленной причиной;
- **TEST** — гипотеза, нуждающаяся в эксперименте;
- **INVESTIGATE** — пробелы/конфликт аналитики и доказательств;
- **HOLD** — изменений пока не требуется.

В каждом задании указывать источник, период, фактические значения либо `MISSING`, объект изменения, риск, критерий сравнения по **уникальным посетителям** и запрет на внесение изменений без согласования владельца.

## Источники не являются инструментами

Указанные GitHub-проекты — **внешняя методическая база**, а не автоматически доступные исполнительные инструменты. Доступ к API Директа/Метрики и полномочия на запись не предполагаются. Не копировать скрипты и правила без проверки лицензий, прав и актуальной документации.
