## История решений

### 2026-11-12 — Пункт 01: исключение PDF

**Статус: полностью согласовано; реализация не начата.**

Согласовано изменить только слой `data_sources/additional_news`:

1. В `service.py` отфильтровывать URL, чей путь заканчивается на `.pdf` без учёта регистра (query и fragment не влияют), **до** дедупликации по домену. PDF не должен занимать слот HTML-статьи с того же сайта.
2. В `reader.py` проверять URL до GET при прямом вызове `read_sources`; каждый адрес перенаправления проверять до следующего GET.
3. Если сервер возвращает `Content-Type: application/pdf` или заголовок `Content-Disposition` явно указывает PDF, прекращать обработку **до чтения тела**. Для PDF по URL без расширения начальный запрос заголовков неизбежен.
4. Исключённые PDF не включать в `sources`, не передавать в `prepare_sources` и `analyze_result`, не считать технической ошибкой. Добавить агрегированное количество пропусков в лог.
5. Сохранить публичные контракты `AdditionalSearchResult`, `AdditionalSource`, `search_additional_news`, лимит пяти успешно загруженных HTML-источников и существующую обработку остальных HTTP-ошибок. Другие расширения (`.docx`, `.xlsx`) не входят в задачу.

**Приёмка:** тесты на `.pdf`, `.PDF`, query и fragment, PDF-редирект, PDF MIME, `Content-Disposition` и HTML-страницу с того же домена; для очевидного PDF URL GET не выполняется, для PDF MIME тело ответа не читается. После реализации запустить `pytest` и зафиксировать результат.

**Отдельное разрешение на изменение кода пока не дано.**

### 2026-11-12 — Пункт 02: метод проверки релевантности

**Статус: частично согласовано; пункт 02 ещё обсуждается, реализация не начата.**

Выбран **комбинированный подход Python + LLM**:

- Python выполняет быстрые структурные проверки (например, нормализацию URL, выявление дубликатов, проверку доступных идентификаторов и дат), не требующие смысловой оценки.
- LLM используется для оценки семантической релевантности неоднозначных публикаций, когда формальных правил недостаточно.
- Конкретные условия жёсткого исключения, влияние даты публикации на релевантность события и формат решения **ещё не согласованы**; лимиты числа источников согласованы ниже.
- Пока это решение **не означает** согласования всей схемы отбора источников и не разрешает правку исходного кода.

**Дополнительное согласование от 2026-11-12 — расположение и порядок обработки:**

1. В `data_sources/additional_news` **не добавлять LLM**: оставляем поиск SearXNG, техническую фильтрацию URL/PDF и извлечение HTML.
2. **Увеличить количество кандидатов для чтения**; отказаться от отбора только одной публикации с каждого домена. Разные статьи одного сайта не считать дубликатами по домену. Точные дубликаты URL продолжить исключать.
3. **Увеличить количество успешно прочитанных HTML-публикаций**, передаваемых в `prepare_sources`: ограничение пяти загрузок до проверки релевантности может потерять полезные статьи.
4. В существующем `agents/analysis_news.prepare_sources` использовать LLM для проверки релевантности событию/эмитенту/дате и суммаризации, без добавления самостоятельного LLM-узла. В `analyze_result` отправлять только релевантные источники.
5. Независимость подтверждения от первоисточника не определять по одному лишь домену; правила этой оценки обсуждаются отдельно.

**Дополнительно согласовано 2026-11-12 — числовые лимиты:**

- Не более **20 кандидатов** после фильтрации PDF и устранения точных дубликатов URL; правило «один домен — одна статья» не применять.
- Не более **10 успешно прочитанных HTML-статей** для обработки в `prepare_sources`.
- Не более **5 публикаций, признанных релевантными**, передавать в `analyze_result`; если релевантных меньше пяти, не дополнять нерелевантными.
- Значения 20 → 10 → 5 являются согласованными начальными лимитами. Правила выбора лучших кандидатов при превышении лимита и критерии релевантности будут обсуждаться отдельно. Лимит пяти загрузок из изолированной PDF-правки пункта 01 при совместной реализации уступает утверждённому для пункта 02 лимиту десяти HTML-загрузок.

**Дополнительно согласовано 2026-11-12 — категории релевантности `prepare_sources`:**

1. **Прямое подтверждение** — публикация описывает исходное событие; передавать в `analyze_result` как доказательство, не подменяя независимость источников количеством URL.
2. **Полезный контекст** — значимая информация об эмитенте, не подтверждающая непосредственно исходное событие; передавать аналитику как контекст без статуса подтверждения.
3. **Нерелевантная публикация** — не относится ни к событию, ни к значимому контексту; исключать из входа `analyze_result`.

Из первых двух категорий передавать в `analyze_result` не более пяти статей суммарно. **Согласованные значения `category` на русском:** `"прямое подтверждение"`, `"полезный контекст"`, `"нерелевантная"`. Технический механизм выбора пяти публикаций, приоритизация и классификация смешанных публикаций ещё обсуждаются.

**Согласовано 2026-11-12:** добавить отдельный LLM-узел `validate_search_query` перед `additional_search` для смысловой проверки поискового запроса на соответствие проверяемому факту, эмитенту, дате события и поисковой задаче. Это относится и к первоначальному, и к повторному поиску.

**Согласовано 2026-11-12:** удалить генерацию поискового запроса из `extract_facts_and_query` (узел оставить для извлечения фактов; новое имя `extract_facts` допустимо как проектное обозначение). Для первоначального и повторного поиска использовать один узел `build_search_query` с разными шаблонами, выбираемыми вызывающим кодом. Первоначальный маршрут: `extract_facts → build_search_query → validate_search_query → additional_search`. Для повторного поиска: `verify_analysis → build_search_query → validate_search_query → additional_search`. Сохранять проверяемый факт и назначение поиска между узлами.

**Согласованное уточнение от 2026-11-12 — универсальный помощник `build_prompt`:**

- `build_prompt` не должен знать о режимах `initial` / `follow_up` и не должен выбирать шаблоны внутри себя.
- Вызов функции явно передаёт **`template` (шаблон)** и данные для его заполнения.
- Шаблоны выбора первоначального и дополнительного поисков раздельные; их выбор и подготовка данных выполняются в вызывающем коде, а не в универсальном помощнике.
- Подход допускает повторное использование `build_prompt` в других LLM-узлах. Конкретная сигнатура, вид шаблона и возвращаемого значения уточняются при проектировании; код пока не изменён.
- Единый `build_search_query` как единственный узел формирования поисковых запросов согласован; универсальная функция `build_prompt` остаётся независимой от выбора шаблона.

**Согласованный маршрут исправления:** если `validate_search_query` отклонил запрос, передать причину отказа, исходный запрос и данные поисковой задачи обратно в `build_search_query` без повторного извлечения фактов. Исправленный запрос снова проходит через `validate_search_query` перед SearXNG.

**Дополнительно согласовано 2026-11-13 — ограничение повторов:**

1. На одну поисковую задачу допускается исходная генерация запроса и **не более одной повторной генерации** после замечаний валидатора.
2. `validate_search_query` выполняется **не более двух раз** для этой задачи — до и после исправления.
3. Если повторная валидация отклоняет запрос, **не обращаться к SearXNG с этим запросом**. Зафиксировать диагностическое сообщение с причиной и фактом исчерпания лимита.
4. **Не прерывать весь анализ новости** из-за этой неудачи: завершить только текущую попытку поиска и продолжить анализ с имеющимися сведениями, явно сохранив отсутствие подтверждения. Отказ поиска не трактовать как опровержение факта.
5. Ограничение действует отдельно для первоначальной и каждой новой поисковой задачи из `verify_analysis`. Счётчик повторных генераций не смешивать со счётчиком попыток поиска публикаций.

Технический формат диагностического статуса уточняется при проектировании; исходный код пока не изменён.

**Дополнительно согласовано 2026-11-13 — разделение фильтрации и суммаризации:**

- Добавить **один** новый узел LangGraph `filter_sources` между `additional_search` и существующим `prepare_sources`.
- В `filter_sources` LLM классифицирует до **10** полученных HTML-статей по трём ранее согласованным категориям: прямое подтверждение, полезный контекст, нерелевантно.
- После классификации **внутри того же `filter_sources`** Python исключает нерелевантные и детерминированно выбирает не более **5** публикаций. Отдельный узел Python-отбора не создавать.
- `prepare_sources` выполняет **только суммаризацию выбранных** публикаций (без повторного определения релевантности); `analyze_result` получает результат суммаризации с сохранёнными категориями и происхождением фактов.
- Переходы по этой части графа строго линейные и без новых условных маршрутов или возвратных циклов:
  `additional_search → filter_sources → prepare_sources → analyze_result`.
- Существующая логика последующего `verify_analysis` и повторных поисков не затрагивается этим соглашением. Обработка ошибок `filter_sources` и критерии сортировки пяти публикаций ещё не согласованы.
- Данное решение **заменяет** ранее записанное предложение выполнять классификацию непосредственно в `prepare_sources`. История предыдущего выбора сохранена выше для прозрачности; актуальная архитектура — отдельный `filter_sources`.


**Актуальное предложение по минимизации ответа LLM (ещё не согласовано полностью):** вместо отдельной классификации всех десяти публикаций LLM может сразу возвращать до пяти выбранных `{source_id, category}`; причина выбора не нужна. Для выбранных допустимы только русские категории `"прямое подтверждение"` и `"полезный контекст"`; нерелевантные не включаются в `selected`. Python проверяет существование и уникальность `source_id`, допустимые значения категории и лимит пяти. Переходы графа не усложняются. Этот вариант изменит ранее утверждённое распределение LLM-классификации и Python-отбора, поэтому его полное утверждение ещё требуется.

**Остаётся обсудить:** представление смешанных источников, формат возвращаемых статусов, правила приоритета и технический формат диагностики отклонённого поискового запроса.

**Статус:** архитектура пункта 02 согласована, но весь пункт ещё не закрыт. Изменений исходного кода нет.
