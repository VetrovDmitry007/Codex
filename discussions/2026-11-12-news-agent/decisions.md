## История решений

### 2026-11-12 — Пункт 01: исключение PDF

**Статус: полностью согласовано; реализация не начата.**

Согласовано изменить только слой `data_sources/additional_news`:

1. В `service.py` отфильтровывать URL, чей путь заканчивается на `.pdf` без учёта регистра (query и fragment не влияют), **до** дедупликации по домену. PDF не должен занимать слот HTML-статьи с того же сайта.
2. В `reader.py` проверять URL до GET при прямом вызове `read_sources`; каждый адрес перенаправления проверять до следующего GET.
3. Если сервер возвращает `Content-Type: application/pdf` или заголовок `Content-Disposition` явно указывает PDF, прекращать обработку **до чтения тела**. Для PDF по URL без расширения начальный запрос заголовков неизбежен.
4. Исключённые PDF не включать в `sources`, не передавать в `prepare_sources` и `analyze_result`, не считать технической ошибкой. Добавить агрегированное количество пропусков в лог.
5. Сохранить публичные контракты `AdditionalSearchResult`, `AdditionalSource`, `search_additional_news`, лимит пяти успешно загруженных HTML-источников и существующую обработку остальных HTTP-ошибок. Другие расширения (`.docx`, `.xlsx`) не входят в задачу.

**Приёмка:** тесты на `.pdf`, `.PDF`, query и fragment, PDF-редирект, PDF MIME, `Content-Disposition` и HTML-страницу с того же домена; для очевидного PDF URL GET не выполняется, для PDF MIME тело ответа не читается. После реализации запустить `pytest` и зафиксировать результат.

**Отдельное разрешение на изменение кода пока не дано.**

### 2026-11-12 — Пункт 02: метод проверки релевантности

**Статус: частично согласовано; пункт 02 ещё обсуждается, реализация не начата.**

Выбран **комбинированный подход Python + LLM**:

- Python выполняет быстрые структурные проверки (например, нормализацию URL, выявление дубликатов, проверку доступных идентификаторов и дат), не требующие смысловой оценки.
- LLM используется для оценки семантической релевантности неоднозначных публикаций, когда формальных правил недостаточно.
- Конкретные условия жёсткого исключения, влияние даты публикации на релевантность события и формат решения **ещё не согласованы**; лимиты числа источников согласованы ниже.
- Пока это решение **не означает** согласования всей схемы отбора источников и не разрешает правку исходного кода.

**Дополнительное согласование от 2026-11-12 — расположение и порядок обработки:**

1. В `data_sources/additional_news` **не добавлять LLM**: оставляем поиск SearXNG, техническую фильтрацию URL/PDF и извлечение HTML.
2. **Увеличить количество кандидатов для чтения**; отказаться от отбора только одной публикации с каждого домена. Разные статьи одного сайта не считать дубликатами по домену. Точные дубликаты URL продолжить исключать.
3. **Увеличить количество успешно прочитанных HTML-публикаций**, передаваемых в `prepare_sources`: ограничение пяти загрузок до проверки релевантности может потерять полезные статьи.
4. В существующем `agents/analysis_news.prepare_sources` использовать LLM для проверки релевантности событию/эмитенту/дате и суммаризации, без добавления самостоятельного LLM-узла. В `analyze_result` отправлять только релевантные источники.
5. Независимость подтверждения от первоисточника не определять по одному лишь домену; правила этой оценки обсуждаются отдельно.

**Дополнительно согласовано 2026-11-12 — числовые лимиты:**

- Не более **20 кандидатов** после фильтрации PDF и устранения точных дубликатов URL; правило «один домен — одна статья» не применять.
- Не более **10 успешно прочитанных HTML-статей** для обработки в `prepare_sources`.
- Не более **5 публикаций, признанных релевантными**, передавать в `analyze_result`; если релевантных меньше пяти, не дополнять нерелевантными.
- Значения 20 → 10 → 5 являются согласованными начальными лимитами. Правила выбора лучших кандидатов при превышении лимита и критерии релевантности будут обсуждаться отдельно. Лимит пяти загрузок из изолированной PDF-правки пункта 01 при совместной реализации уступает утверждённому для пункта 02 лимиту десяти HTML-загрузок.

**Дополнительно согласовано 2026-11-12 — категории релевантности `prepare_sources`:**

1. **Прямое подтверждение** — публикация описывает исходное событие; передавать в `analyze_result` как доказательство, не подменяя независимость источников количеством URL.
2. **Полезный контекст** — значимая информация об эмитенте, не подтверждающая непосредственно исходное событие; передавать аналитику как контекст без статуса подтверждения.
3. **Нерелевантная публикация** — не относится ни к событию, ни к значимому контексту; исключать из входа `analyze_result`.

Из первых двух категорий передавать в `analyze_result` не более пяти статей суммарно. **Согласованные значения `category` на русском:** `"прямое подтверждение"`, `"полезный контекст"`, `"нерелевантная"`. Технический механизм выбора пяти публикаций, приоритизация и классификация смешанных публикаций ещё обсуждаются.

**Согласовано 2026-11-12:** добавить отдельный LLM-узел `validate_search_query` перед `additional_search` для смысловой проверки поискового запроса на соответствие проверяемому факту, эмитенту, дате события и поисковой задаче. Это относится и к первоначальному, и к повторному поиску.

**Согласовано 2026-11-12:** удалить генерацию поискового запроса из `extract_facts_and_query` (узел оставить для извлечения фактов; новое имя `extract_facts` допустимо как проектное обозначение). Для первоначального и повторного поиска использовать один узел `build_search_query` с разными шаблонами, выбираемыми вызывающим кодом. Первоначальный маршрут: `extract_facts → build_search_query → validate_search_query → additional_search`. Для повторного поиска: `verify_analysis → build_search_query → validate_search_query → additional_search`. Сохранять проверяемый факт и назначение поиска между узлами.

**Согласованное уточнение от 2026-11-12 — универсальный помощник `build_prompt`:**

- `build_prompt` не должен знать о режимах `initial` / `follow_up` и не должен выбирать шаблоны внутри себя.
- Вызов функции явно передаёт **`template` (шаблон)** и данные для его заполнения.
- Шаблоны выбора первоначального и дополнительного поисков раздельные; их выбор и подготовка данных выполняются в вызывающем коде, а не в универсальном помощнике.
- Подход допускает повторное использование `build_prompt` в других LLM-узлах. Конкретная сигнатура, вид шаблона и возвращаемого значения уточняются при проектировании; код пока не изменён.
- Единый `build_search_query` как единственный узел формирования поисковых запросов согласован; универсальная функция `build_prompt` остаётся независимой от выбора шаблона.

**Согласованный маршрут исправления:** если `validate_search_query` отклонил запрос, передать причину отказа, исходный запрос и данные поисковой задачи обратно в `build_search_query` без повторного извлечения фактов. Исправленный запрос снова проходит через `validate_search_query` перед SearXNG.

**Дополнительно согласовано 2026-11-13 — ограничение повторов:**

1. На одну поисковую задачу допускается исходная генерация запроса и **не более одной повторной генерации** после замечаний валидатора.
2. `validate_search_query` выполняется **не более двух раз** для этой задачи — до и после исправления.
3. Если повторная валидация отклоняет запрос, **не обращаться к SearXNG с этим запросом**. Зафиксировать диагностическое сообщение с причиной и фактом исчерпания лимита.
4. **Не прерывать весь анализ новости** из-за этой неудачи: завершить только текущую попытку поиска и продолжить анализ с имеющимися сведениями, явно сохранив отсутствие подтверждения. Отказ поиска не трактовать как опровержение факта.
5. Ограничение действует отдельно для первоначальной и каждой новой поисковой задачи из `verify_analysis`. Счётчик повторных генераций не смешивать со счётчиком попыток поиска публикаций.

Технический формат диагностического статуса уточняется при проектировании; исходный код пока не изменён.

**Дополнительно согласовано 2026-11-13 — разделение фильтрации и суммаризации:**

- Добавить **один** новый узел LangGraph `filter_sources` между `additional_search` и существующим `prepare_sources`.
- В `filter_sources` LLM классифицирует до **10** полученных HTML-статей по трём ранее согласованным категориям: прямое подтверждение, полезный контекст, нерелевантно.
- После классификации **внутри того же `filter_sources`** Python исключает нерелевантные и детерминированно выбирает не более **5** публикаций. Отдельный узел Python-отбора не создавать.
- `prepare_sources` выполняет **только суммаризацию выбранных** публикаций (без повторного определения релевантности); `analyze_result` получает результат суммаризации с сохранёнными категориями и происхождением фактов.
- Переходы по этой части графа строго линейные и без новых условных маршрутов или возвратных циклов:
  `additional_search → filter_sources → prepare_sources → analyze_result`.
- Существующая логика последующего `verify_analysis` и повторных поисков не затрагивается этим соглашением. Обработка ошибок `filter_sources` и критерии сортировки пяти публикаций ещё не согласованы.
- Данное решение **заменяет** ранее записанное предложение выполнять классификацию непосредственно в `prepare_sources`. История предыдущего выбора сохранена выше для прозрачности; актуальная архитектура — отдельный `filter_sources`.


**Актуальное упрощение от 2026-11-13 (заменяет прежнюю схему классификации десяти и отдельного Python-ранжирования):** один вызов LLM в `filter_sources` **сразу выбирает до пяти** наиболее релевантных публикаций и возвращает только `selected: [{source_id, category}]`, без объяснений. Для выбранных допустимы русские значения `"прямое подтверждение"` и `"полезный контекст"`; категория `"нерелевантная"` остаётся в понятийной классификации, но не включается в `selected`.

**Python не выполняет повторную смысловую проверку и не запускает отдельный набор валидаций.** Он только получает оригинальные записи по указанным `source_id` для передачи дальше; отсутствие указанного ID нельзя компенсировать выдуманным источником. Ограничение `≤ 5` задаётся контрактом структурированного ответа LLM; при обработке результата оно соблюдается без отдельного этапа проверки. Ручные повторные проверки формата JSON, всех категорий и дубликатов не добавлять. Обработка невалидного ответа модели и техническая диагностика остаются предметом проектирования.

**История:** ранее планировалось классифицировать все 10 статей и выбирать 5 средствами Python. Это заменено более простым вариантом по согласованию пользователя; топология графа остаётся линейной.

**Дополнительно согласовано 2026-11-13 — ограничение объёма входа `filter_sources`:**

- Для предварительного LLM-отбора передавать **сокращённый текст** каждой из десяти публикаций вместе с `source_id`, заголовком, датой и URL, а не полный исходный текст.
- Оригинальный полный текст хранить без изменений и использовать в `prepare_sources` после выбора источников; сокращённый текст не должен подменять оригинал.
- **Согласовано 2026-11-13:** на каждую публикацию передавать не более **3000 символов текста**: первые **2000** символов + последние **1000** символов. Для более короткой статьи использовать её текст без дублирования фрагментов. `source_id`, заголовок, дата и URL передаются отдельно и в лимит текста не входят.
- Не добавлять отдельный узел или переход графа ради сокращения текста.

**Дополнительно согласовано 2026-11-13 — главный критерий отбора:**

- `filter_sources` выбирает до пяти **наиболее полезных для финансового анализа эмитента** публикаций. В приоритете сведения о долговой нагрузке, ликвидности, финансовом положении, способности обслуживать долг, существенных рисках и изменениях; без требования набрать определённое количество подтверждений исходной новости.
- Публикации, **противоречащие исходной новости** либо содержащие негативные факты, нельзя исключать из-за противоречия или отрицательной тональности. Их финансовая значимость может быть выше, чем у подтверждающей публикации.
- Информация о самом событии остаётся полезной, но подтверждение исходной формулировки **не является самоцелью отбора**. Сравнение и оценка достоверности противоречий относятся к дальнейшему анализу, не к механическому удалению источников.
- Структура ответа остаётся минимальной (`source_id` и русская `category`), без объяснения выбора.
- **Решение по названиям принято ниже:** прежние категории заменены двумя допустимыми значениями в ответе LLM.

**Дополнительно согласовано 2026-11-13 — два значения категории выбранного источника:**

- `"сведения о событии"` — публикация касается исходного события, включая его подтверждение, уточнение или противоречие.
- `"финансовая информация"` — финансовое положение, долги, ликвидность, риски и другие значимые сведения об эмитенте, даже без прямой связи с событием.
- Нерелевантные публикации **не включаются** в `selected`; отдельное значение `"нерелевантная"` в выходном контракте не требуется.
- Формат ответа LLM не меняется: `selected: [{source_id, category}]` с максимум пятью записями. Никаких пояснений выбора и дополнительных Python-проверок не добавлять.
- Это решение **заменяет** ранее утверждённые три категории только в актуальном выходном контракте `filter_sources`; историческая запись сохранена выше.

**Дополнительно согласовано 2026-11-13 — сбой `filter_sources`:**

- Если LLM не вернула корректный список выбранных публикаций либо вызов завершился ошибкой, **не делать повторный вызов LLM** ради исправления этого ответа.
- Зафиксировать диагностическую запись об ошибке `filter_sources` с причиной, если она доступна; технические детали не должны включать секреты.
- Не передавать в `prepare_sources` непроверенные или выдуманные `source_id` и не представлять отсутствующие дополнительные источники как подтверждение.
- **Продолжить анализ исходной новости** с уже имеющейся достоверной информацией; сбой отбора дополнительных источников не означает опровержение новости. Не добавлять обходных переходов или циклов в граф.
- Формат диагностики уточнён ниже: обычный лог узла с причиной ошибки; дополнительных полей в `AgentState` и отдельного механизма диагностики не требуется.

**Дополнительно согласовано 2026-11-13 — смешанные публикации:**

- Если в одной статье одновременно есть сведения об исходном событии и **существенная финансовая информация об эмитенте**, в `filter_sources` назначать категорию **`"финансовая информация"`**.
- Категория `"сведения о событии"` используется, если финансовое содержание не является существенным.
- Категория не обрезает содержание статьи: `prepare_sources` получает **полный исходный текст** выбранной публикации и может отразить как финансовые сведения, так и факты о событии.
- Не создавать отдельную третью категорию или дополнительные переходы графа.

**Дополнительно согласовано 2026-11-13 — минимальное логирование ошибок `filter_sources`:**

- При ошибке узла использовать **обычный лог**: указать `filter_sources` и краткую причину ошибки, например `filter_sources: не удалось получить корректный ответ LLM`.
- Не создавать отдельную систему диагностики, дополнительную структуру статусов, новые поля `AgentState` или отдельный переход графа.
- Не записывать в лог токены, секреты и полные тексты публикаций.
- Ранее согласованное поведение остаётся: без повторного LLM-вызова продолжить анализ исходной новости без непроверенных дополнительных источников.

**Дополнительно согласовано 2026-11-13 — два направления поисковых запросов (пункт 03):**

- Внутри **одного** узла `build_search_query` формировать два запроса: (1) о событии, (2) о финансовом состоянии и рисках эмитента.
- Использовать **два разных шаблона промпта**, каждый формировать через ранее запланированный универсальный `build_prompt(template, data)`; новый LangGraph-узел генерации не добавлять.
- На вход слоя дополнительного поиска передавать **список словарей** с двумя согласованными полями: `purpose` и `query`. При первоначальном поиске значения `purpose` — `"событие"` и `"финансы"`; при повторном — `"уточнение"`. Дополнительные параметры в словарь не вводить.
- Результаты обоих запросов собрать в **единый пул** публикаций и передать в один ранее согласованный `filter_sources`. Приоритет релевантности — финансовая ценность, включая сведения, противоречащие исходной новости.
- Существующий `validate_search_query` применять к поисковым запросам перед их отправкой; правила повторной корректировки запроса остаются в силе.
- **Согласовано 2026-11-13:** для **обоих запросов вместе** сохранить единый бюджет: не более **20 кандидатов** после исключения PDF и точных дубликатов URL → не более **10 успешно загруженных HTML-публикаций** → не более **5 источников**, выбранных одним `filter_sources`. Бюджет не удваивать, не вводить квоту пять публикаций на каждое направление.
- **Согласовано 2026-11-13:** отбирать **по 10 кандидатов на каждый поисковый запрос**: до десяти по исходному событию и до десяти по финансам эмитента. После объединения выполнять общую дедупликацию URL; пересечения могут уменьшать фактическое число уникальных кандидатов. Общий потолок 20 → 10 HTML → 5 выбранных сохраняется.
- **Согласовано 2026-11-13 — без перераспределения:** для каждого из двух запросов действует независимый предел **до 10 кандидатов**. Если один запрос нашёл меньше десяти, его неиспользованные места **не передаются** второму. Например, при 6 и 10 найденных кандидатах общий набор содержит не более 16 до общей дедупликации URL. Общий лимит 20 → 10 HTML → до 5 итоговых источников сохраняется.
- **Согласовано 2026-11-13 — повторный поиск:** если `verify_analysis` инициирует дополнительный поиск из-за конкретного замечания, `build_search_query` формирует **только один целевой запрос по этому замечанию** — не повторяет две первоначальные поисковые задачи. Для него используется отдельный шаблон, который вызывающий код передаёт в ранее согласованный `build_prompt(template, data)`. Один `build_search_query` остаётся общим для первоначального и повторного поиска.
- Повторный запрос также проходит `validate_search_query` с ранее согласованной одной возможной корректировкой. В слой поиска допускается передавать список словарей с **одним** запросом; результаты обрабатываются тем же `filter_sources`.
- **Согласовано 2026-11-13 — отдельный бюджет повторного поиска:** на **одну попытку** повторного поиска по одному замечанию допускается не более **10 кандидатов → 10 успешно прочитанных HTML-статей → 5 публикаций, выбранных `filter_sources`**. Этот бюджет самостоятельный и не уменьшает лимиты первоначального поиска. Повторный поиск не запускает оба первоначальных направления заново; ограничение на одну корректировку поискового запроса в `validate_search_query` сохраняется.
- **Согласовано 2026-11-13 — накопление результатов поиска:** после первоначального `filter_sources` узел `prepare_sources` добавляет саммари выбранных публикаций с происхождением источника в `state["messages"]` (существующие сообщения `verified_source`). При повторном поиске `filter_sources` обрабатывает **только новые найденные публикации**, а `prepare_sources` **добавляет** новые саммари, сохраняя уже добавленные. `analyze_result` использует сообщения с обоих проходов; после завершения графа они доступны в `result["messages"]`.
- Не создавать отдельное хранилище выбранных публикаций в `AgentState`; в `messages` хранятся подготовленные саммари, не обязательно полные тексты исходных статей.
- **Согласовано 2026-11-13 — исключать ранее обработанные URL при повторном поиске:** собрать URL публикаций, саммари которых уже сохранены в существующих сообщениях `verified_source` в `state["messages"]`; исключать совпавшие URL из нового списка кандидатов **до загрузки полного текста**, передачи в `filter_sources` и повторной суммаризации. Саммари ранее обработанных публикаций остаются в `messages`; новые источники добавляются к ним. Не создавать новое постоянное хранилище или узел дедупликации. Технический способ извлечения URL из существующих сообщений проверить при реализации.
- **Согласовано 2026-11-13 — контракт поискового слоя:** список словарей вида `[{"purpose": "событие", "query": "..."}, {"purpose": "финансы", "query": "..."}]` для первоначального поиска и `[{"purpose": "уточнение", "query": "..."}]` для повторного. Только два поля `purpose` и `query`; назначение хранится на русском языке. Валидатор проверяет каждый сформированный запрос до передачи в SearXNG; новый графовый узел не требуется.
- **Согласовано 2026-11-13 — совместимость API:** публичную функцию `search_additional_news(query: str)` **сохранить с прежним интерфейсом**. Список словарей `{purpose, query}` обрабатывает LangGraph-узел `additional_search`: последовательно вызывает существующую функцию для каждого `query`, собирает ответы, исключает PDF и дубликаты URL по согласованным правилам и направляет общий пул в `filter_sources`.
- `purpose` используется внутри агентного слоя и **не передаётся** как новый обязательный параметр в `search_additional_news`. Не создавать публичный метод поиска по списку без отдельного согласования.
- При реализации проверить, что фактические внутренние ограничения `search_additional_news` не нарушают согласованный общий бюджет первого прохода: до 10 кандидатов **на направление**, до 10 успешно прочитанных HTML **суммарно**, до 5 публикаций после `filter_sources`. Сохранение публичной сигнатуры не означает обязательного изменения лимитов для существующих внешних вызовов.
- **Уточнение 2026-11-13 — без дополнительных квот загрузки:** отклонено предложение разделять 10 HTML-публикаций по схеме **5 + 5** между запросами. Сохранять один ранее утверждённый предел **до 10 успешно загруженных HTML-публикаций суммарно на первоначальный поисковый проход**, без новых лимитов по направлениям или типам события. Для повторного одиночного поиска также действует ранее согласованный предел до 10 HTML на попытку. Разбиение по 10 относится **только к кандидатам** каждого первоначального запроса, а не к загруженным HTML.

**Согласовано 2026-11-13 — пункт 04: детерминированные `source` и `published_date`:**

- **Согласовано 2026-11-13 — отсутствующий издатель:** если в метаданных исходной публикации **нет названия издателя**, программно извлекать домен URL этой публикации и записывать его в `source` (например, `https://www.rbc.ru/...` → `rbc.ru`).
