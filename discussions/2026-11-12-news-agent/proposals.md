# Список предлагаемых улучшений новостного агента BondNavigator

**Тип документа:** спецификация для поэтапного обсуждения  
**Версия:** 0.5 (архитектура и лимиты пункта 02 согласованы)  
**Дата:** 12.11.2026  
**Область:** `agents/analysis_news/`, `data_sources/additional_news/`  
**Основание:** лог анализа новости № 5474 о ГК «Самолет» и предоставленные `agent.py`, `nodes.py`, `models.py`, `prompts.py`, `validation.py`, `schemas.py`, `reader.py`, `service.py`.

## 1. Цель и ограничения

Сделать анализ новостей более достоверным, сбалансированным и экономным по контексту, исключить лишние повторные вызовы LLM и ненужную загрузку PDF.

**Границы проекта:** изменения обсуждаются по одному пункту. До согласования не считать предложения решениями к реализации. Существующие публичные интерфейсы (`NewsAnalysisResult`, `search_additional_news` и др.) сохранять, если отдельным решением не согласовано обратное. Не терять значимые исходные факты, числа, даты и диагностические сообщения. Ошибки поиска не трактовать как отрицание события. Сохранять независимость подтверждений: другой URL не равен новому независимому первоисточнику.

**Статус:** пункт 01 полностью согласован; по пункту 02 согласованы архитектура и лимиты 20 → 10 → 5, критерии релевантности и схема статусов ещё обсуждаются; пункты 03–10 — предложения. Реализация не начата. Итоги решений: [decisions.md](decisions.md).

## 3. Карточки для обсуждения и критерии приёмки

### 01. Исключение PDF в `data_sources/additional_news`

**Статус: полностью согласовано 2026-11-12; реализация не начата.** Подробности утверждённого решения — в [decisions.md](decisions.md).

**Сейчас:** `service.py` сначала отбирает один результат на сайт и передаёт его в `read_sources`. В `reader.py` `_get_html` допускает только `text/html` и `application/xhtml+xml`, поэтому PDF с корректным MIME уже не читается как статья, **но HTTP GET выполняется**. PDF-кандидат, оказавшийся первым для сайта, может вытеснить подходящую HTML-статью того же сайта.

**Меняем:**
1. В `service.py` до дедупликации по сайту пропускать URL, у которых путь (без query/fragment, регистронезависимо) оканчивается на `.pdf`.
2. В `reader.py` до сетевого запроса повторять эту защиту для прямых вызовов `read_sources`; при переходе по редиректу проверять новый URL **до** следующего GET.
3. По HTTP-заголовкам отклонять `application/pdf` и явный PDF в `Content-Disposition` **до** чтения тела. Для неизвестных URL, возвращающих PDF под HTML-подобным адресом, предварительный GET до ответа сервера полностью исключить невозможно, но тело PDF загружаться не должно.
4. Не включать исключённые PDF в `sources` и не передавать их в `prepare_sources`/`analyze_result`. Предусмотреть агрегированный счётчик пропущенных PDF; не маркировать ожидаемый пропуск как техническую ошибку.

**Проверка:** `.pdf`, `.PDF`, `.pdf?download=1`, `#fragment`, PDF-редирект, `Content-Type: application/pdf`, обычная HTML-статья на том же домене после отброшенного PDF. Замокировать сеть: по URL с очевидным `.pdf` GET не выполняется; при PDF-MIME тело ответа не читается. Проверить, что обычный HTML и модель результата не сломаны.

**Открыто:** надо ли также исключать другие документы (`.docx`, `.xlsx`) — **пока нет, вне задачи**.

### 02. Отбор релевантных публикаций

**Согласовано (частично, 2026-11-12):** расширить пул кандидатов и успешно прочитанных HTML-статей, отказаться от правила одного домена; Python в `data_sources/additional_news` исключает PDF и точные дубликаты URL; LLM уже существующего `prepare_sources` оценивает релевантность событию/эмитенту/датам и суммаризирует. В `analyze_result` передавать только релевантные публикации. Новый LLM-узел не нужен. **Согласованы лимиты 20 → 10 → 5**; критерии релевантности и отбора при превышении лимитов ещё обсуждаются. См. [decisions.md](decisions.md).

**Сейчас:** сайт выбирается до загрузки; затем ограничиваются только успешно прочитанные статьи. Тематически близкие, но не относящиеся к дате и событию публикации могут попасть к аналитику.

**Меняем:** разделять техническую доступность, релевантность событию, принадлежность периоду и независимость. При выборе учитывать не только домен; не отдавать нерелевантную статью только ради заполнения лимита источников. Сохранять причины исключения.

**Критерий:** публикация о другом торговом дне не подтверждает точную внутридневную котировку исходной даты; лимит не приводит к потере более релевантной публикации того же домена.

**Вопрос (следующий):** какие категории релевантности должен присваивать `prepare_sources` публикациям (прямое подтверждение события, полезный контекст, нерелевантная публикация), и какие из них передавать аналитику?

### 03. Два направления информационного поиска

**Сейчас:** `extract_facts_and_query` формирует запрос, подтверждающий главное событие; контекст финансовых рисков обнаруживается случайно.

**Меняем:** сохранять обязательную проверку события, но при наличии содержательных триггеров (реструктуризация, просрочки, рейтинг, долговая нагрузка, санация) строить отдельную задачу контекстного поиска рисков и противодействующих факторов. Строго связывать найденные сведения с датой/периодом и эмитентом.

**Критерий:** при новости о росте акций на фоне переговоров с кредиторами итог учитывает и рост, и незавершённость договорённостей; не выдаёт непроверенные причины за доказанные. Отсутствие негативных материалов не считается подтверждением отсутствия рисков.

**Вопрос:** какой узел инициирует второй поиск и как ограничивается его бюджет?

### 04. Детерминированное происхождение фактов

**Сейчас:** `source` и `published_date` генерирует LLM, из-за чего эксперт повторно отправляет всё на анализ ради исправления этих полей.

**Меняем:** хранить внутри состояния связи `fact_id → origin_source_id → publisher/date`; отдельно вести ссылки на подтверждающие материалы и признаки перепечатки. Публичные `source` и `published_date` заполнять из нормализованных метаданных, при неизвестном издателе — из домена.

**Критерий:** факт из исходной новости не получает в поле `source` издателя независимой проверки; его дата не подменяется датой события или подтверждения. Публичная схема не меняется.

**Вопрос:** как определяем редакционное название издателя, если сайт/страница указывает несколько брендов?

### 05. Компактный контракт `analyze_result`

**Сейчас:** модель получает `HumanMessage` с исходной новостью, историей поиска, всеми подготовленными источниками и метаданными.

**Меняем:** входной пакет из структурированных фактов с `source_id`, цитируемой опорой/фрагментом, датами, доступными подтверждениями и ограничениями. Полные тексты остаются в `state["sources"]` и доступны для адресной проверки, но по умолчанию не дублируются в каждом вызове.

**Критерий:** можно для каждого суждения проследить источник; вход аналитика заметно компактнее базового запуска, существенные числа/даты не теряются; при нехватке фрагмента предусмотрена эскалация к оригиналу.

**Вопрос:** какой набор полей является обязательным для доказательства?

### 06. Точечная доработка вместо полной генерации

**Сейчас:** `revise_analysis` добавляет `analysis_revision`, но предыдущий `parsed_result` не входит в повторный запрос аналитика. Значимость события менялась `+18 → +20 → +17` без новых публикаций.

**Меняем:** передавать `previous_analysis` и `revision_issues` вместе с исходными доказательствами; требовать сохранять непомеченные поля. Для чисто метаданных ошибок по возможности применять детерминированное исправление без LLM.

**Критерий:** коррекция имени источника не изменяет `summary_value`, `summary_category`, перечень других фактов; содержательные изменения допускаются только с пояснением.

**Вопрос:** возвращать полный исправленный JSON или стандартный JSON Patch внутри узла?

### 07. Разделение проверок

**Сейчас:** `verify_analysis` пересматривает и содержание, и публикационные метаданные, и формат; исчерпание лимита ревизий влияет на дальнейшие решения.

**Меняем:** структурно-метаданные ошибки обрабатывать Python-проверками, экспертную LLM оставить для фактов, конфликтов, независимости и адекватности выводов. По исчерпании лимита не превращать нерешённое существенное противоречие в `complete` только по причине ограничения.

**Критерий:** чистая ошибка в `source` не вызывает повторного содержательного анализа; существенное противоречие не маскируется успешным статусом.

**Вопрос:** какой статус назначать при исчерпании бюджета и нерешённой существенной ошибке?

### 08. Рыночный эффект против кредитного риска

**Сейчас:** рост акций рассматривается как положительный фактор; его связь с финансовым состоянием эмитента может быть недостаточно отделена.

**Меняем:** внутри анализа явно различать `market_reaction`, `credit_implications` и `unknowns`. Текущие публичные поля категории/балла сохранить до отдельного согласования методологии итоговой оценки.

**Критерий:** позитивная динамика цены не выдаётся за улучшение способности эмитента обслуживать облигационный долг; для `mixed` явно показываются обе стороны.

**Вопрос:** общий скор должен описывать рыночное событие или влияние на держателя облигаций?

### 09. Контроль качества суммаризации

**Сейчас:** `_summary_matches_source()` сверяет числовые значения и некоторые слова дат; отвергнутый пересказ приводит к отправке оригинального текста.

**Меняем:** проверять сохранение значимых причинно-следственных и разнонаправленных сведений, не теряя источник и точные формулировки; отдельно учитывать ошибки суммаризации и требовать восстановление оригинала только для нужного участка.

**Критерий:** неопределённость реструктуризации и оговорки первоисточника не исчезают из сводки; ошибочные пересказы не становятся доказательствами.

**Вопрос:** реализовать проверку правилами, второй LLM-проверкой или гибридно с лимитом затрат?

### 10. Наблюдаемость и объём логов

**Сейчас:** DEBUG фиксирует полный запрос/ответ LLM, включая технические поля; трудно сравнивать итерации и причины возвратов.

**Меняем:** для каждого узла логировать идентификатор анализа, длительность, число источников, символы/токены (если API возвращает), причину перехода и число ревизий. Не раскрывать секреты, не писать технические `encrypted_content`; подробные тексты — только при явном управляемом режиме диагностики.

**Критерий:** по логу можно восстановить маршруты и расходы контекста без дублирования огромных текстов и без утечки чувствительных данных.

**Вопрос:** нужен ли отдельный JSONL-трейс или достаточно структурированных полей текущего logger?

## 4. Рекомендуемый порядок обсуждения

**Первый этап — безопасные и ограниченные изменения:** 01 → 07 → 06 → 04.  
**Второй этап — качество доказательств и объём контекста:** 02 → 09 → 05.  
**Третий этап — полнота финансовой оценки:** 03 → 08.  
**Сквозной этап — диагностика:** 10.

Порядок — предложение, не обязательство. Пункты 04, 06 и 07 связаны: технический контракт происхождения фактов нужно согласовать перед окончательным разделением проверки и исправлений.

## 5. Обязательные проверки при реализации каждого пункта

1. Изучить вызывающие функции, модели, API и связанные тесты.
2. Внести минимальное изменение с сохранением публичных контрактов, если не согласовано иное.
3. Создать временные тесты: основной сценарий, пограничные случаи, ожидаемые ошибки.
4. Запустить `pytest`, исправить выявленные дефекты и повторить тесты.
5. Отдельно проверить отсутствие потери исходных фактов, неверных подтверждений, дублирования и ненужных повторных вызовов модели.
6. Для воспроизводимости использовать фикстуру новости № 5474 (без реального сетевого доступа и действующих API-ключей).
7. В итоговой сводке указать затронутые файлы, команду `pytest`, число прошедших тестов и ограничения.

**Эта версия — спецификация для обсуждения, не выполненный патч. Изменения в исходный код данным документом не внесены.**
