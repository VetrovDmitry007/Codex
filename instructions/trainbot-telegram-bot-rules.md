# Правила проектирования Telegram-бота TrainBot (aiogram)

> Специализированная инструкция для обсуждения, проектирования, аудита и модификации Telegram-бота TrainBot. Для этих задач используется вместо общих instructions/interaction-rules.md. Не подменяет SEO-регламент instructions/trainbot-seo-rules.md и не заменяет техническую документацию специализированного Skill.

2. **Специализированный Skill [telegram-aiogram-widgets](../.agents/skills/telegram-aiogram-widgets/SKILL.md)** — **обязательно читай полностью** для проектирования, реализации и аудита Telegram HTML Widgets на aiogram: календаря, выбора станций, мест, карточек подписки и брони, новых событий widget_query, FSM и fallback. Не подменяй его своим пересказом. Для задач, не связанных с Widgets, этот Skill факультативен.
3. **GitHub** — https://github.com/VetrovDmitry007/Codex — чтение, создание и обновление инструкций, навыков, утверждённых спецификаций и планов.
4. **Первоисточники**: https://core.telegram.org/bots/widgets, https://core.telegram.org/bots/api, https://docs.aiogram.dev/ — сверять с фактически установленной версией aiogram; изменения API не угадывать.

Если нужный Skill недоступен, прямо скажи; не утверждай, что применил его.

## 2. Цели и ограничения TrainBot

TrainBot ищет, отслеживает и бронирует железнодорожные места. Улучшай **понятность пути пользователя, скорость выбора параметров и стабильность**, сохраняя логику подписок, брони, тарификации и интеграций.

- Основной стек — Python, aiogram 3, Router, FSM, сервисы и БД. Текущие версии и контракты всегда устанавливай по реальному коду проекта.
- По ранее предоставленным материалам bot.py содержит Dispatcher/Long Polling и MemoryStorage, handlers/subscrib.py — StSubscr, dt_depart, DepName/DepCode, DestName/DestCode, prm_sub_otslej(), core/util_bot.py — проверку дат и поиск станций. Это **исторические сведения**, не доказательство актуальности.
- Не переписывай существующую FSM, бизнес-правила, баланс, Hold, API РЖД, платёжный контур или обработку пассажирских данных без конкретной необходимости и разрешения.
- Работа с сайтом, SEO и AEO/GEO подчиняется отдельной инструкции instructions/trainbot-seo-rules.md.

## 3. Порядок проектирования

Для новой **крупной архитектурной** задачи представь режимы: (1) проектирование с нуля, (2) аудит, (3) модификация. Предложи подходящий и попроси выбор, если он ещё не сделан явно. Для небольшой правки или прямо запрошенного готового артефакта не создавай искусственную процедуру.

1. Изучи исходники, сценарий и **указанные точные пути**. Если пользователь ссылается на прежнюю конкретную спецификацию без пути — запроси путь; если файл не найден — предложи кандидата для подтверждения.
2. **В начале обсуждения** найди существующие спецификации по теме. Предложи продолжить одну из них либо создать новую. **Согласуй точный путь до записи**; уже выбранный файл повторно не согласовывай.
3. Сразу после выбора создай/открой **живую функциональную спецификацию**: запиши цель, границы, ранее утверждённые UX/бизнес-требования, отдельно — предложения и открытые вопросы. Для задач Telegram Widgets веди **самостоятельный документ технической архитектуры**, где технические предложения и решения отделены от требований.
4. Опиши проблему, ожидаемый результат, ограничения и критерии готовности. Сравни реальные альтернативы: чат + inline-кнопки, HTML Widget, Mini App; выбирай простейшую достаточную.
5. Согласовывай по одному UX, FSM, контракты, проверки, ошибки и fallback. **После каждого утверждённого решения обновляй соответствующий документ в GitHub**: функциональные требования — в функциональной спецификации, техническую архитектуру — в отдельном архитектурном документе. До следующего вопроса проверь запись.
6. Для Telegram Widgets **утверждение технической архитектуры проводи по отдельному документу**, не смешивая с согласованием UX. После её утверждения подготовь отдельный план реализации. **Production-код изменяй только по отдельному явному поручению**; создание документа/Skill не разрешает правку кода.

Обсуждай один спорный вопрос за раз, предлагай свою рекомендацию и кратко раскрывай компромисс. Не повторяй согласованное. Если пользователь определил задачу целиком, выполняй без лишних уточнений.

## 4. Обязательные правила Widgets

Если задача включает HTML Widget, **загрузи telegram-aiogram-widgets до проектирования** и сверяй первоисточники.

- Widgets — интерактивное содержимое сообщения, не обычный WebView; не обещай произвольные текстовые поля, fetch, изменение HTML после отправки или работу всех клиентов без проверки.
- Для календаря: локальный выбор даты, один запрос при подтверждении, ISO YYYY-MM-DD, серверная проверка диапазона и часового пояса.
- Для станции: популярные/недавние — Widget-кнопки, произвольный поиск — чат или Mini App. Сохраняй серверный идентификатор станции.
- Путь: меню подписки -> sendWidget -> TelegramWidget.request -> widget_query -> контроль прав/состояния -> FSM/сервис -> answerWidgetQuery и обновление данных/меню.
- В aiogram используй native API **только если они есть в установленной версии**. Иначе проверенный адаптер raw Update с allowed_updates, не затрагивающий старые маршруты.
- На сервере проверяй владельца, state, допустимость даты/станции, повторы, просроченный виджет. Не считать нажатие кнопки успешной бронью. Не помещать секреты или пассажирские данные в HTML.
- Проверяй ограничения размера/сжатия HTML, время ответа, rate limit, последствия перезапуска FSM, клиент без поддержки Widgets.

Одно согласование расположения файлов действует на последующие обновления; повторно спрашивать разрешение на изменение этих же документов не нужно.
- После **каждого** явно принятого решения прочитай актуальный **соответствующий** документ, измени только относящийся раздел, сделай коммит GitHub, повторно прочитай файл и проверь запись. Кратко дай ссылку и переходи к следующему вопросу. UX и поведение пользователя — в спецификацию; контракты, FSM/Telegram API и технические решения — в архитектуру.
- Предложения не выдавай за утверждённые требования: отмечай статус, нерешённые вопросы и существенные изменения ранее принятого.
- При ошибке записи сообщай о ней; не утверждай, что документ сохранён. Ведение спецификации не заменяет отдельного одобрения архитектуры и реализации.

- Перед записью прочитай текущие файлы, после записи повторно проверь содержимое и коммит. Сохраняй чужие изменения; не изменяй SEO или LangGraph документы без цели.
- Не предполагай, что репозиторий Codex содержит runtime-исходники TrainBot. Путь к фактическому коду и его ветку нужно проверить отдельно.
- Репозиторий публичный: запрещено коммитить токены Telegram, cookies, session, прокси-ключи, пассажирские и платёжные данные.

## 6. Заключение и принцип «Ленивый Сеньор»

Архитектурная спецификация должна объяснять: цель и путь пользователя, альтернативы и выбор, UI/события, FSM и зависимости, безопасность, ограничения, fallback, проверки, открытые риски. Для крупных изменений добавь Mermaid-схему процесса.

Отдельно различай **архитектурная готовность**, **готовность кода**, **результаты локальных тестов** и **проверку на реальном Telegram**. Не заявляй о проверках без фактических результатов. Сообщай ссылки на подтверждённые GitHub-файлы и коммиты.

Предпочитай минимальное изменение, повторное использование существующих обработчиков и сервисов. Не экономь строки за счёт безопасности, идемпотентности и обратной совместимости.
