# Слой поиска дополнительных новостей `data_sources/additional_news` — архитектурная спецификация

**Проект:** BondNavigator  
**Компонент:** `data_sources/additional_news`  
**Дата начала:** 2026-11-07  
**Статус:** черновик; записаны согласованные решения, открытые вопросы отмечены отдельно. Программный код не изменён.

**Спецификация потребителя:** [контракт отдельной LangGraph-ноды и инструмента `additional_search`](../analysis_news/additional-search-node-2026-11-07.md). Граф, `AgentState`, `SourceData`, суммаризация, валидация и маршрутизация находятся **только в спецификации интеграции**, не в этом документе. Отдельная нода вызывает инструмент-обёртку `additional_search`, который обращается к публичному сервису.

## 1. Назначение и границы

Создать независимый от LangGraph пакет получения **дополнительных публикаций** для проверки факта о конкретном эмитенте. Слой принимает проверяемое утверждение и готовый поисковый запрос, сформированный вызывающей LLM, ищет источники через MCP SearXNG, выбирает подходящие публикации, самостоятельно получает их **полные тексты** и возвращает структурированные данные и диагностические сообщения.

В пакет **не входят** LLM-суммаризация, экспертная оценка достоверности факта, управление состоянием графа и маршрутизация агента. Эти функции реализует потребитель. Пакет должен быть пригоден для вызова из других частей проекта и для ручного тестирования без LangGraph.

## 2. Архитектура файлов

```text
data_sources/
└── additional_news/
    ├── config.py                 # Константы SEARXNG_MCP_URL и MCP_TIMEOUT = 30.
    ├── models.py                 # Модели публикаций и результата поиска.
    ├── service.py                # Только публичная функция search_additional_news(fact, query).
    └── providers/
        └── searxng.py            # MCP-клиент к Docker mcp-searxng: поиск и чтение URL.
```

В `models.py` размещать только `AdditionalSource` и `AdditionalSearchResult`; не дублировать модели агента. **Все обращения к развёрнутому Docker-сервису `mcp-searxng` выполняет `providers/searxng.py` через MCP Streamable HTTP**: поиск через `searxng_web_search` и получение текста через `web_url_read`. В `service.py` реализуется **только одна публичная функция `search_additional_news(fact, query)`**: она координирует провайдер, отбирает публикации и формирует `AdditionalSearchResult`. Не создавать в `service.py` дополнительные внутренние функции для поиска или отдельную `run_test()`. Прямых MCP/HTTP-вызовов к Docker из `service.py` не делать. Не создавать дополнительные архитектурные слои, повторные обходы отказов или самостоятельные механизмы суммаризации без обоснования.

Пакет первоначально назывался `additional_sources` и проектировался внутри `agents/analysis_news`. Согласованное имя и расположение — **`data_sources/additional_news/`**. Путь этой спецификации — `specs/additional_news/spec-2026-11-07.md`.

## 3. Согласованные модели данных

```python
"""Модели дополнительных публикаций и результата поиска."""

from datetime import date
from typing import Literal, TypedDict


class AdditionalSource(TypedDict):
    """Содержит загруженную публикацию, найденную дополнительным поиском."""

    url: str  # Адрес найденной публикации.
    title: str | None  # Заголовок публикации, если доступен.
    text: str  # Полученный полный текст публикации.
    published_date: date | Literal["unknown"]  # Дата публикации либо «unknown», если достоверно неизвестна.


class AdditionalSearchResult(TypedDict):
    """Объединяет полученные публикации и сообщения об ошибках."""

    sources: list[AdditionalSource]  # Успешно загруженные публикации.
    errors: list[str]  # Ошибки поиска или загрузки отдельных публикаций.
```

**Принятые ограничения:**

- `AdditionalSearchResult` содержит **ровно два поля** `sources` и `errors`. Отдельное поле `status` не требуется; ошибки не добавлять в `AdditionalSource`.
- Публичная функция `service.py` возвращает **`AdditionalSearchResult`**, а не `list[AdditionalSource]` напрямую. Ранее обсуждавшийся отказ от контейнера отменён по решению пользователя.
- В `AdditionalSource.text` сохраняется именно полученный **полный текст**, а не поисковый сниппет. Публикацию без доступного полного текста нельзя выдавать как успешно загруженную.
- Значение `published_date` — `date | Literal["unknown"]`; если достоверную дату определить нельзя, использовать строку `"unknown"`, **не `None` и не текущую дату**. При JSON-сериализации известную дату передавать как строку `YYYY-MM-DD`, неизвестную — как `"unknown"`. Исходное время и временную зону преобразовывать явно.
- **Порядок получения даты (согласовано):** сначала использовать дату публикации из метаданных конкретного поискового результата SearXNG (например, `publishedDate`) при условии достоверной интерпретации; если дата отсутствует или недостоверна — попробовать извлечь дату из доступных метаданных самой загруженной страницы. Если дату достоверно установить невозможно, использовать `"unknown"`. Не подменять дату публикации датой индексации, получения или текущей датой и не привлекать LLM для её определения.

## 4. Вход и публичный сервис

Входное поисковое задание содержит два смысловых поля:

- **`fact: str`** — утверждение, которое необходимо подтвердить или опровергнуть, с указанием конкретного эмитента.
- **`query: str`** — готовый запрос для SearXNG, сформированный вызывающей LLM с учётом эмитента и проверяемого факта.

**Публичный интерфейс согласован (уточнение):** асинхронная функция `search_additional_news(fact: str, query: str) -> AdditionalSearchResult` в `service.py`. Оба параметра обязательны. **LLM-эксперт вызывающей стороны формирует готовый `query`; слой передаёт его в `searxng_web_search` без самостоятельного составления нового запроса и без дополнительной LLM.** `fact` служит контекстом для оценки соответствия найденных публикаций проверяемому утверждению, но не заменяет готовый `query`. Функция вызывается как агентом, так и вручную; слой не импортирует `VerifyTask` из агента и не зависит от LangGraph.

```python
async def search_additional_news(fact: str, query: str) -> AdditionalSearchResult:
    """Ищет дополнительные публикации для проверки факта.

    :param fact: Проверяемое утверждение о конкретном эмитенте.
    :param query: Готовый поисковый запрос, сформированный вызывающей LLM.
    :return: Полученные публикации и сообщения об ошибках.
    """
    ...  # Реализация определяется после согласования поиска и загрузки текстов.
```

**Простая проверка входа (согласовано):** если `fact` или `query` пустые либо состоят только из пробелов, **не обращаться к SearXNG** и сразу возвращать `{"sources": [], "errors": ["Не указан проверяемый факт или поисковый запрос."]}`. Достаточно одного условия `if not fact.strip() or not query.strip(): ...` в существующей публичной функции. Не создавать отдельный валидатор, дополнительные исключения, классы или уровни абстракции только ради этой проверки. Если оба значения заполнены, передавать готовый `query` без переформулирования.

**Решение о формировании запроса:** `query` генерируется заранее LLM-экспертом потребителя и должен содержать достаточный контекст эмитента и финансовой темы. `additional_news` выполняет этот запрос, выбирает релевантные публикации с учётом `fact` и получает полные тексты; отдельного вызова LLM для составления поисковых фраз здесь нет.

**Ручной запуск той же публичной функции** (без отдельной `run_test()`):

```python
if __name__ == "__main__":
    import asyncio

    asyncio.run(search_additional_news(
        fact="АО «ГТЛК» увеличило чистый долг по итогам последнего отчётного периода.",
        query="ГТЛК чистый долг динамика последняя отчётность МСФО",
    ))
```

Утверждение о ГТЛК — **предмет проверки**, а не установленный финансовый факт. Поисковую строку в ручном сценарии задаёт разработчик; при вызове из графа её формирует LLM-эксперт. Ручной запуск реализуется **прямым вызовом единственной публичной функции** с параметрами, как в других сервисах проекта; `if __name__ == "__main__"` содержит только пример вызова, а не дополнительный метод. Отдельный CLI, `argparse`, параметры командной строки и отдельный CLI-`main()` **не нужны**. Ручная функция и вызывающий агент используют одну общую реализацию поиска; генерация поисковой строки остаётся ответственностью вызывающей стороны.

## 5. Провайдер и получение публикаций

**Выбранный MCP-провайдер:** [ihor-sokoliuk/mcp-searxng](https://github.com/ihor-sokoliuk/mcp-searxng), транспорт **Streamable HTTP**. **Адрес Docker MCP задаётся константой `SEARXNG_MCP_URL` в `data_sources/additional_news/config.py`**, откуда его импортирует `providers/searxng.py`; не передавать адрес через переменную окружения `SEARXNG_MCP_URL` и не дублировать адрес внутри провайдера или сервиса. Конкретное значение адреса пока не указано и должно соответствовать фактическому развёртыванию. **Таймаут клиентского MCP-вызова `MCP_TIMEOUT = 30` секунд также хранится в `config.py` и используется для поиска и чтения страниц.** Не вводить дополнительные таймауты без реальной необходимости.

**Аутентификация (согласовано):** Docker MCP ещё не развёрнут; **для планируемого развертывания обязательно использовать статический Bearer-токен**. У самого SearXNG нет обязательного коммерческого API-ключа, а Docker MCP `mcp-searxng` поддерживает защищённый HTTP-режим (`MCP_HTTP_HARDEN=true`, серверный секрет `MCP_HTTP_AUTH_TOKEN`; дополнительные необходимые настройки защиты задаются при развёртывании). В Python-клиенте токен **обязательно читать из переменной окружения `SEARXNG_MCP_TOKEN`**, не хранить в `config.py`, исходниках, URL, спецификации или журнале. Провайдер передаёт `Authorization: Bearer <token>` с каждым MCP-запросом. **Если токен не задан или пустой, не начинать MCP-соединение**: вернуть диагностическое сообщение в `AdditionalSearchResult.errors` и `sources=[]` без раскрытия секрета. При отказе авторизации (например, HTTP 401/403) возвращать диагностическую ошибку, не переходить в незащищённый режим. OAuth не использовать в текущей реализации.

**Отдельная граница:** если сам SearXNG за MCP дополнительно защищён HTTP Basic Auth, это другая аутентификация между Docker MCP и поисковым сервером. Её настройки задаются в окружении Docker MCP (например, `AUTH_USERNAME`/`AUTH_PASSWORD` либо учётные данные в серверном `SEARXNG_URL`), а не в `data_sources/additional_news/config.py`. Не путать `SEARXNG_URL` Docker-процесса с константой адреса **MCP endpoint** `SEARXNG_MCP_URL` в Python-клиенте.

Документация: [Configuration Reference — Authentication и HTTP transport](https://github.com/ihor-sokoliuk/mcp-searxng/blob/main/CONFIGURATION.md), [HTTP server — authentication choices](https://github.com/ihor-sokoliuk/mcp-searxng/blob/main/docs/http-server.md).

Проверенные возможности `searxng_web_search`:

- Принимает `query` (без дополнительной LLM-генерации внутри сервиса), `num_results`, а также параметры `response_format="json"` и `result_detail="full"`. Последняя комбинация — изученная возможность, но конкретные параметры вызова ещё не утверждены как публичный контракт.
- JSON-выдача может включать `results[]` с `title`, `url`, `content`, а также необязательные дату `publishedDate`, `score`, `engines`, `category` и другую поисковую метаинформацию.
- `content` внутри поискового результата — **сниппет**, а не полный текст статьи. Режим `result_detail="full"` не означает скачивание полного содержимого сайта.
- JSON содержится в текстовом MCP-блоке `content[].text`, поэтому провайдеру необходим разбор ответа. Для JSON-поиска нужен корректно настроенный экземпляр SearXNG; MCP-сервер и сам SearXNG — разные компоненты.

**Согласованный цикл сервиса (уточнён):** `service.py` передаёт готовый `query` провайдеру → `providers/searxng.py` вызывает `searxng_web_search` через развёрнутый Docker `mcp-searxng` → сервис выбирает публикации → **этот же провайдер вызывает MCP-инструмент `web_url_read` того же Docker-сервиса** для каждого выбранного URL → результат в текстовом/Markdown-представлении нормализуется в `AdditionalSource.text` → сервис формирует `AdditionalSearchResult`. Отдельный Python HTTP-загрузчик и HTML→Markdown-парсер **не создавать**. MCP-инструмент `web_url_read` возвращает читаемый Markdown для HTML и поддерживает также другие текстовые форматы и извлечение текста PDF; он **не гарантирует**, что страница доступна, текст статьи полностью извлечён или что `maxLength` не обрезает результат. При недоступности полноценного текста источник не подменять поисковым сниппетом, причину указывать в `errors`.

**Объём нормализованного текста (согласовано):** слой `additional_news` **не устанавливает собственного ограничения длины** `AdditionalSource.text` и **не обрезает нормализованный текст** публикации, полученный от `providers/searxng.py`. Сохраняется весь доступный структурированный текст в Markdown/текстовом представлении; последующая суммаризация выполняется в существующих нодах LangGraph и не относится к слою получения данных. При обращении провайдера к Docker MCP не вводить искусственно малое ограничение длины ради экономии контекста. Технические ограничения и возможная обрезка на стороне Docker MCP остаются внешним фактором. **Если MCP явно сообщает, что текст страницы обрезан или возвращён частично, такой результат не считается успешной публикацией: не добавлять его в `sources`, указать URL и причину в `errors`, после чего продолжить загрузку со следующего допустимого сайта.** Неполный текст не подменять поисковым сниппетом. Если MCP не даёт признака обрезки, не придумывать его; проверка полноты ограничена фактически доступными сигналами провайдера.

**Лимиты поиска и чтения (согласовано):** один готовый `query` передаётся в `searxng_web_search` с `num_results=10` (максимум 10 результатов поиска). Из выдачи последовательно выбираются **первые публикации с разных сайтов** в исходном порядке SearXNG. **Дубликат — любая следующая публикация с того же сайта, даже если URL и заголовок отличаются.** От каждого сайта допускается не более одной публикации: выбирается первый встретившийся URL этого сайта; остальные пропускаются. Сервис вызывает провайдерский `web_url_read` до получения **5 успешно загруженных публикаций с разных сайтов** или до исчерпания кандидатов из исходных десяти результатов. Если чтение страницы не удалось, причина добавляется в `errors`, а сервис переходит к **следующему сайту**, не повторяя запрос для уже обработанного сайта. Успешные публикации сохраняются в `sources` в порядке выдачи. Таким образом, **максимум 5 успешных публикаций**, **до 10 попыток чтения** (если все 10 результатов относятся к разным сайтам). **Дополнительная оценка релевантности по `fact`, собственное ранжирование и LLM-отбор в текущую версию не входят**: первичный порядок полностью задаёт SearXNG. **Не усложнять обработку доменов и субдоменов на этапе проектирования**: сначала использовать возможности выдачи SearXNG и минимальную проверку повторения сайта в сервисе. Специальные правила объединения `www`, поддоменов и иных доменных вариантов сейчас не проектировать; к ним возвращаться только при обнаружении реальных дублей в тестах. Не предполагать без проверки, что SearXNG гарантированно исключает все публикации с одного сайта.

**Кэширование (согласовано):** собственный кэш результатов поиска и текстов публикаций в `data_sources/additional_news` **не использовать**. Каждый вызов `search_additional_news(fact, query)` запускает новый поиск через SearXNG и чтение выбранных страниц. Не добавлять TTL, хранилище, фоновые обновления или конфигурацию кэша. Это ограничение касается реализации слоя; поведение внутренних механизмов стороннего Docker MCP здесь не переопределяется.

**Пометка на будущее (не согласованная текущая функциональность):** предусмотреть возможность позднее добавить **LLM-отбор наиболее подходящих публикаций** из поисковой выдачи с учётом `fact`, не меняя публичный контракт `search_additional_news(fact, query)`. Для текущей реализации LLM-отбор **не выполнять** и не вводить преждевременно дополнительные классы, интерфейсы или конфигурационные переключатели.

**Разделение инструментов и нод:** существующий инструмент чтения основной новости внутри `agents/analysis_news` **не используется** для дополнительных публикаций. В LangGraph вызов реализован как `additional_search()` → `search_additional_news(fact, query)` → `providers/searxng.py` → Docker MCP SearXNG. **Только внутри провайдера** используется одноимённый MCP-инструмент Docker `web_url_read` для чтения выбранных URL; это не вызов инструмента основной новости и не операция ноды. Не передавать дополнительные URL в `assistant` / общий `ToolNode`. Название MCP-операции приводится здесь исключительно как технический контракт провайдера, а не интерфейс агента.

Сервис не вызывает LLM и не выполняет суммаризацию. Извлечение проверяемых фактов и проверка точности сокращений относятся к анализирующему агенту, а не к слою получения данных.

Ссылки на изученные исходники MCP: [types.ts](https://github.com/ihor-sokoliuk/mcp-searxng/blob/main/src/types.ts), [search.ts](https://github.com/ihor-sokoliuk/mcp-searxng/blob/main/src/search.ts), [описание инструментов](https://github.com/ihor-sokoliuk/mcp-searxng/blob/main/docs/tools.md).

**Проверенный внешний контракт Docker MCP:** согласно документации [`mcp-searxng` — инструменты](https://github.com/ihor-sokoliuk/mcp-searxng/blob/main/docs/tools.md), `searxng_web_search` возвращает результаты поиска и сниппеты, а `web_url_read(url, ...)` считывает выбранную страницу и представляет HTML как Markdown; доступность отдельных страниц и полнота извлечения требуют проверки по фактическому ответу. Эти два инструмента вызываются одним провайдером через MCP, а не напрямую из LangGraph.

## 6. Результаты и обработка ошибок

Результаты различаются без отдельного поля `status`:

| `sources` | `errors` | Значение |
|---|---|---|
| Не пуст | Пуст | Успешно получены публикации |
| Не пуст | Не пуст | Частичный результат с ошибками |
| Пуст | Пуст | Поиск завершён без найденных публикаций |
| Пуст | Не пуст | Поиск/загрузка не дали публикаций и сопровождались ошибками; это **не** подтверждает отсутствие сведений |

**Согласованный подход к ошибкам:** ошибки подключения к MCP, таймауты, некорректные ответы и ошибки загрузки страниц фиксировать строками в `AdditionalSearchResult.errors`, без отдельного поля `status` и без собственной иерархии исключений. Если поисковый запрос полностью завершился ошибкой, возвращать `sources=[]` с соответствующей диагностикой в `errors`; успешную пустую выдачу отличать от технического отказа. Если некоторые публикации получены успешно, возвращать их в `sources` вместе с накопленными ошибками. При невозможности получить полную публикацию не формировать фиктивный `AdditionalSource` и переходить к следующему допустимому сайту, пока не исчерпаны кандидаты или не получены пять успешных текстов. Ошибки провайдера обрабатывать **минимально необходимым способом**, без избыточных обёрток, дополнительных классов и дублирующих механизмов. Диагностика должна содержать контекст операции и URL при наличии, но не раскрывать секреты или токены. Конкретный формат строки ошибки остаётся деталью реализации.

## 7. Открытые вопросы реализации слоя

1. Формирование `query` вынесено в вызывающую LLM. Пустой `fact` или `query` (в том числе только пробелы) приводит к немедленному `AdditionalSearchResult` с пустыми `sources` и диагностикой в `errors` без обращения к провайдеру (согласовано). Проверка — одно простое условие внутри публичной функции; заполненный `query` передаётся без переформулирования.
2. Чтение страниц выполняет `providers/searxng.py` через MCP `web_url_read` в Docker `mcp-searxng` (согласовано). **Собственное ограничение длины нормализованного текста не вводить.** Если MCP явно пометил текст как частичный/обрезанный, публикацию пропускать, записывать причину в `errors` и переходить к следующему допустимому сайту (согласовано). При реализации определить, какие признаки обрезки реально доступны в MCP-ответе.
3. Согласовано брать первые публикации **с разных сайтов**, не более одной публикации на сайт, до пяти успешных текстов либо исчерпания десяти результатов. Сложную нормализацию субдоменов не разрабатывать заранее; возможные реальные дубли проверить при тестировании SearXNG. **Собственный кэш не использовать (согласовано)**. LLM-отбор — только возможное будущее расширение.
4. Адрес Docker MCP — константа `SEARXNG_MCP_URL` в `config.py`; таймаут клиента — константа `MCP_TIMEOUT = 30` секунд (согласовано). **Статическая Bearer-авторизация обязательна**, хотя Docker MCP пока не развёрнут: серверный секрет `MCP_HTTP_AUTH_TOKEN` передаётся контейнеру через окружение, клиент читает `SEARXNG_MCP_TOKEN` из своего окружения. Без клиентского токена соединение не выполнять, возвращать ошибку. При развёртывании ещё установить фактический URL MCP и параметры защищённого HTTP-режима; отдельно согласовать обработку `429` и журналирование. Общий подход к ошибкам: диагностические строки в `errors`, сохранение успешных источников, без иерархии исключений.
5. Порядок извлечения даты согласован: сначала метаданные SearXNG, затем метаданные страницы; если надёжной даты нет — `"unknown"`. При реализации проверить допустимые форматы дат и корректную обработку недостоверных/неоднозначных значений.
6. Тесты сервиса: пустая выдача, частичная загрузка, повреждённый ответ, ошибки сети и отсутствие даты.
