# Инструмент `additional_search` для LangGraph-агента — архитектурная спецификация

**Проект:** BondNavigator  
**Компонент:** `agents/analysis_news`  
**Предмет:** инструмент-обёртка над слоем поиска дополнительных новостей  
**Дата начала:** 2026-11-07  
**Статус:** черновик; отражает согласованные решения, программный код не изменён.

**Спецификация сервиса:** [слой `data_sources/additional_news`](../additional_news/spec-2026-11-07.md) — источник истины для поиска, получения текстов, моделей `AdditionalSource` / `AdditionalSearchResult`, MCP-провайдера и ручного запуска. Здесь эти механизмы не дублируются.

**Базовая спецификация агента:** [AI-агент анализа новостей эмитентов](issuer-news-agent-2026-11-02.md) — существующий контракт, который не меняется автоматически.

## 1. Назначение и граница инструмента

**Уточнение пользователя (согласовано):** `additional_search` — это **tool-обёртка** над публичной функцией `data_sources.additional_news.service.search_additional_news(fact: str, query: str)`. **`additional_search` не является самостоятельной нодой LangGraph**. Инструмент вызывается **внутри существующей ноды** агента; какую именно ноду использовать и каким образом вызывать инструмент (непосредственный вызов или LangChain tool dispatch), требуется согласовать отдельно.

Инструмент не выполняет MCP-запросы, чтение URL, HTML-преобразование, отбор публикаций, повторное составление запросов или суммаризацию. Это обязанности слоя `data_sources/additional_news`. `agents/analysis_news` зависит от `data_sources/additional_news`, но не наоборот.

## 2. Расположение и ответственность

```text
agents/analysis_news/
├── agent.py                 # Сборка существующего графа.
├── nodes.py                 # Существующие ноды, одна из которых вызовет tool.
├── models.py                # VerifyTask, SourceData, AgentState и другие модели.
└── tools.py                 # Предполагаемое место обёртки additional_search (подлежит уточнению).

data_sources/additional_news/
├── service.py               # search_additional_news(fact, query).
├── models.py                # AdditionalSource, AdditionalSearchResult.
└── providers/searxng.py     # Docker MCP SearXNG; реализация скрыта от агента.
```

**Важно:** добавление `additional_search` в список нод и рёбер графа **не требуется** только из-за наличия инструмента. Изменения графа зависят от выбранной ноды-хозяина и механизма вызова инструмента; пока они не утверждены.

## 3. Вход и выход инструмента

Вход согласован с публичным сервисом:

```python
async def additional_search(fact: str, query: str) -> AdditionalSearchResult:
    """Вызывает сервис поиска публикаций для проверки факта.

    :param fact: Проверяемое утверждение о конкретном эмитенте.
    :param query: Готовая строка поиска, сформированная LLM-экспертом.
    :return: Структурированный результат сервиса с публикациями и ошибками.
    """
    return await search_additional_news(fact=fact, query=query)
```

Это **иллюстрация контракта**, а не готовый код: импорты, декоратор инструмента, механизм вызова внутри ноды и размещение обёртки уточняются отдельно. Никакая дополнительная LLM внутри обёртки не требуется.

Внешний результат — **`AdditionalSearchResult`** с двумя согласованными полями: `sources: list[AdditionalSource]` и `errors: list[str]`. Описание этих моделей — только в [спецификации слоя данных](../additional_news/spec-2026-11-07.md).

## 4. Состояние и задачи агента

LLM-эксперт формирует `fact` (проверяемый факт о конкретном эмитенте) и **готовый `query`** для поиска. Целевая модель задания:

```python
class VerifyTask(TypedDict):
    """Задание эксперта для дополнительной проверки факта."""

    fact: str  # Утверждение, требующее независимого подтверждения.
    query: str  # Готовый поисковый запрос для SearXNG, составленный LLM-экспертом.
```

Существующее поле `VerifyTask.question` в исходном коде необходимо совместно заменить на `query` в промпте, структурированной схеме ответа LLM и точках использования при реализации. Модель находится в `agents/analysis_news/models.py`, не в слое `data_sources`.

Согласованная общая модель источника для агента:

```python
from datetime import date
from typing import Literal, TypedDict


class SourceData(TypedDict):
    """Содержит публикацию и результат валидации её суммаризации."""

    title: str | None  # Заголовок, если доступен.
    text: str  # Полный текст публикации.
    published_date: date | None  # Дата публикации, если установлена.
    summary: str | None  # Предварительная или проверенная суммаризация.
    summary_status: Literal["pending", "validated", "rejected"]  # Статус её проверки.
```

Ранее **для отдельной ноды** было согласовано добавление `AgentState.search_task: VerifyTask | None` и его очистка после выполнения поиска. При новом варианте — инструмент вызывается **внутри** ноды — потребность в этом поле **требует повторной оценки**; автоматически ни удалять его из согласованных планов, ни вводить в реализацию без нового решения не следует.

## 5. Обработка результата внутри агента

Результат инструмента обрабатывает вызывающая нода (либо её существующая логика обновления состояния) после получения `AdditionalSearchResult`. Успешно полученные дополнительные публикации должны попадать в существующий `AgentState.sources: dict[str, SourceData]`, а не в отдельное хранилище. Для новых публикаций сохраняются `title`, `text`, `published_date`, `summary=None`, `summary_status="pending"`. Ключ — URL публикации; правила нормализации и исключения дублей ещё открыты.

`errors` не превращать в фиктивные публикации или подтверждение отсутствия информации. Внешний поиск может вернуть успех без результатов, частичный результат или ошибки; точная реакция вызывающей ноды требует отдельного согласования.

Дальше используются **существующие** `summarize` и `validate_summary`. Первый записывает предварительный текст непосредственно в `summary`, второй проверяет его против оригинала. Для LLM-эксперта берётся только `summary` со статусом `validated`, URL и заголовок; при `rejected` допустим исходный `text` с явной пометкой, при `pending` предварительную суммаризацию не считать доказательством.

Полные тексты дополнительных публикаций получает **сервис** через Docker `mcp-searxng`, вызывая инструменты из собственного `providers/searxng.py`. Общий инструмент чтения основной новости в `agents/analysis_news` не используется для дополнительных ссылок. Подробнее — [спецификация сервиса](../additional_news/spec-2026-11-07.md).

## 6. Точка вызова в графе — открытое архитектурное решение

Зафиксировано только: **инструмент `additional_search` вызывается внутри существующей LangGraph-ноды**, а не посредством отдельной ноды `additional_search`. Конкретная нода (например, `verify_analysis` либо другой существующий узел), способ выполнения асинхронного инструмента и последующий переход к суммаризации пока **не согласованы**.

При пересмотре маршрута нужно изучить существующие `verify_analysis`, `assistant`, `ToolNode` и их текущие переходы. Новых рёбер или `Command(goto="additional_search")` не планировать по инерции: это прежнее решение для отдельной ноды и оно **отменено**.

Схема ответственности (не утверждённая схема переходов графа):

```text
Существующая нода LangGraph [уточнить какая]
    ↓ внутри ноды
tool additional_search(fact, query)
    ↓ вызывает
data_sources.additional_news.service.search_additional_news(fact, query)
    ↓ обращается
data_sources/additional_news/providers/searxng.py → Docker MCP mcp-searxng
    ↓
AdditionalSearchResult → вызывающая нода → AgentState.sources
```

**Mermaid-диаграмма переходов графа** и итоговая маршрутизация будут составлены после согласования ноды-хозяина и реакций на результаты.

## 7. Открытые вопросы интеграции

1. В какой существующей ноде вызывается инструмент `additional_search` и как технически устроить вызов.
2. Сохранять ли `AgentState.search_task`, если инструмент выполняется внутри ноды, а не передаётся отдельной ноде.
3. Как передавать `AdditionalSearchResult` в `AgentState.sources` и учитывать `errors` без нового хранилища и дублирования сообщений.
4. Переходы графа после успешного поиска, пустого ответа и ошибки; границы числа повторов.
5. Совместная миграция `VerifyTask.question` → `VerifyTask.query`, изменения промптов, схемы ответа и существующих тестов.
