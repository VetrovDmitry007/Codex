# Дополнительные источники для анализа новостей — архитектурная спецификация

**Проект:** BondNavigator  
**Компонент:** `agents/analysis_news/additional_sources`  
**Режим:** 3 — модификация архитектуры существующего LangGraph-агента  
**Дата начала:** 2026-11-07  
**Статус:** черновик; фиксируются только согласованные решения. Архитектура не утверждена и код не изменён.

## 1. Назначение и исходные материалы

Выделить получение дополнительных сведений об одном событии эмитента в самостоятельный пакет с MCP-провайдером поиска. Интегрировать его с существующим графом анализа новости, не превращая дополнительные публикации в отдельные анализируемые события.

Материалы:
- [Существующая архитектурная спецификация агента](../issuer-news-agent-2026-11-02.md) — исходный контекст; не изменять без отдельного согласования.
- Приложенные пользователем файлы `agent.py`, `nodes.py`, `models.py`, `tools.py`, `prompts.py`, `schemas.py`, `validation.py` и описание структуры проекта.
- [mcp-searxng](https://github.com/ihor-sokoliuk/mcp-searxng) — выбранная основа MCP-поиска.

## 2. Принятые решения

1. **Exa исключается** из целевой архитектуры `agents/analysis_news`; новый поиск не должен зависеть от Exa.
2. **Отдельный пакет:** `agents/analysis_news/additional_sources/`.
3. **MCP-провайдер:** поиск дополнительной информации реализуется через сервер проекта `ihor-sokoliuk/mcp-searxng`.
4. **Транспорт MCP:** **Streamable HTTP**. Конкретный адрес сервера и способ его конфигурирования будут определены при детализации.
5. **Публичная граница:** модуль `agents/analysis_news/additional_sources/service.py` предоставляет публичную функцию для инструмента агента. Название и входной/выходной контракт функции ещё не согласованы.
6. **Отдельная нода:** дополнительный поиск выполняется самостоятельным узлом LangGraph, запуск которого определяется решением **LLM-эксперта** проверки анализа.

Путь этой спецификации согласован отдельно: `specs/analysis_news/additional_sources/spec-2026-11-07.md`. Файлы плана и задания не создаются до согласования архитектуры.

## 3. Текущее состояние (по предоставленному коду)

- `get_graph()` подключает `fetch_web_page` и `find_additional_sources` к общему `ToolNode`.
- Узел `assistant` запрашивает инструменты через `bind_tools`; `route_assistant` направляет вызовы в `tools`.
- Узел `verify_analysis` при решении `continue_search` передаёт `fact` и `question` обратно `assistant`, а не в самостоятельную поисковую ноду.
- `tools.py` содержит Exa-адаптер, обработку MCP-ответа и проверку прогресса поиска; часть ограничителей и диагностики Exa-зависима.
- `sources` содержит полученные тексты и статус суммаризации, `messages` использует `add_messages`.

Эти сведения описывают существующую реализацию, **а не утверждают способ её изменения**.

## 4. Проверенные внешние возможности

`mcp-searxng` поддерживает Streamable HTTP и инструмент `searxng_web_search`, принимающий `query` и необязательный `num_results`. В проекте также есть `web_url_read` для чтения страниц. Подключение к MCP-серверу не заменяет необходимость работающего экземпляра SearXNG с доступным поиском; сервисы различаются. Режим чтения страниц пока не выбран.

## 5. Архитектурные разделы, подлежащие согласованию

### Architecture
Разделение обязанностей нового пакета, взаимодействие с основным графом, удаление устаревшего поиска из `tools.py`.

### State
Контракты задания эксперта, результатов поиска, накопления источников, предотвращения повторов и лимитов. Отдельно проверить сохранение совместимости существующего `AgentState`.

### Nodes
Ответственность `verify_analysis`, новой ноды поиска, `assistant`, `summarize`, `validate_summary`; публичный интерфейс `service.py` и интерфейс MCP-провайдера.

### Edges
Маршруты вызова поиска экспертом, возвращения результатов, переходов к проверке и завершению. Исключить конфликт статических рёбер с `Command(goto=...)`.

### Execution
Последовательность поиска/чтения/суммаризации; идемпотентность, кэширование, ограничение числа запросов и циклов.

### Termination
Критерии успешного завершения, отсутствия новых доказательств, исчерпания лимитов и технической ошибки.

### Error Handling
Различить пустую выдачу, недоступность SearXNG/MCP, таймаут, 429, повреждённый ответ и ошибки загрузки страниц. Не считать ошибку MCP доказательством отсутствия фактов.

### Validation
Проверить достижимость нод, неизменность значимых контрактов, согласованность `sources` и `messages`, завершение циклов и отсутствие необоснованного `success`.

**Mermaid-диаграмма и архитектурное заключение:** добавить после согласования маршрутов и контрактов; до этого окончательная схема не утверждена.

## 6. Открытые вопросы

1. Оставить ли текущий защищённый `fetch_web_page` для загрузки найденных публикаций или поручить чтение страниц MCP-инструменту `web_url_read`?
2. Как передавать `VerifyTask` в отдельную ноду и возвращать результаты, сохранив историю доказательств и ограничения повторов?
3. Какие статусы, таймауты, лимиты и диагностика должны быть публичной частью контракта `service.py`?
4. Как именно вернуть собранные источники в существующие `summarize` / `verify_analysis`, не создавая бесконечного цикла?

Решения из этого раздела нельзя считать принятыми до явного согласования.
