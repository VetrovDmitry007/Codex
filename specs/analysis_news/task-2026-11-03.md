## 2. Цель и результат

Реализуй отдельный LangGraph-процесс анализа одной новости эмитента. Агент собирает и проверяет сведения, анализирует финансовое влияние, формирует структурированный `NewsAnalysisResult`, сохраняет в `public.news_analysis` только успешно проверенный анализ и корректно завершает работу при ограничениях и отказах.

Обязательные исходные решения:

- **10 узлов** `StateGraph`, как в архитектуре. ReAct только для исследования; детерминированные валидация, маршрутизация и сохранение.
- `AgentState(TypedDict)` и `add_messages`; не добавлять поля или узлы без согласования.
- **3 экземпляра LLM / 4 SystemMessage / 2 read-only веб-инструмента** из утверждённой спецификации.
- `max_iterations=8`, `recursion_limit=128`; A7 о прекращении бесполезного поиска.
- Проверка A1/A2/A8, `NewsNotFoundError` до запуска графа при отсутствующей новости, `skipped` для `screening`.
- Сохранение через существующий `PostgresStorage`: единственная строка на `news_id`, `INSERT/UPSERT` на **том же соединении**, которое удерживает session-level advisory lock.
- Публичный вызов `run_news_analysis(...)` возвращает только `NewsAnalysisResult`; полный `AgentState` не покидает внутреннюю границу.
- Безопасная загрузка URL: DNS/IP и редиректы, защита от SSRF/rebinding, лимиты времени, типов и размеров по спецификации.

## 3. Строго обязательная организация разработки

Используй реальный **Superpowers: subagent-driven-development**, не имитируй его одним исполнителем или формальным саморевью.

1. Создай **отдельную рабочую ветку и изолированный git worktree**. Запрещено начинать реализацию в `main`.
2. Запусти Superpowers SDD для **`specs/analysis_news/plan-2026-11-03.md`**. Используй его скрипт `sdd-workspace` и ledger `progress.md`. Если ledger уже существует — сначала прочитай `references/resuming.md`, сверяй выполненные коммиты с `git log`.
3. Прочитай `references/preflight.md`, выполни conflict scan и задокументируй решения в ledger.
4. Выполни **этап 0** плана: изучи текущие методы PostgreSQL, реальные модели новостей, версии LangGraph, LLM-адаптеры, схему миграций и тестовую инфраструктуру. Зафиксируй исходный результат `python -m pytest -q`. Не начинай разработку узлов до завершения этого этапа.
5. Далее последовательно выполни **Task 1–10**. Для каждой задачи создай отдельный brief через `task-brief` и передай его **новому исполнительному субагенту** с изолированным контекстом. Не отправляй параллельно исполнителей, изменяющих один код.
6. Каждый исполнитель пишет тесты **до** реализации, фиксирует RED, реализует минимум, добивается GREEN, делает самопроверку и коммит. Он не запускает собственных субагентов-ревьюеров.
7. После отчёта исполнителя сформируй **review-package** с полным diff от записанного BASE до HEAD; запусти **другого независимого субагента-ревьюера** с brief, отчётом исполнителя и пакетом diff.
8. От каждого ревьюера обязательны **два отдельных вердикта**: `spec compliance` и `code quality`, а также классифицированные замечания. Самопроверка исполнителя не считается независимым ревью.
9. При критичных и существенных замечаниях следуй `references/fix-loop.md`: исправления через исполнительного агента, затем повторная независимая проверка. Соблюдай лимиты и правила фиксации решений Superpowers.
10. В ledger фиксируй задачи, base/head-коммиты, тесты, заключения, исправления и ограничения. Не повторяй завершённые этапы после потери контекста.
11. После Task 10 выполни **`references/final-review.md`**: независимый аудит **всей ветки**, затем процедуру завершения рабочей ветки согласно Superpowers.

Не останавливайся между успешно проверенными задачами ради формального «продолжать?». Останавливайся при необходимости разрешения на необратимое, небезопасное или выходящее за пределы worktree действие, а также если план не позволяет безопасно продолжить.

Если реальные субагенты или нужный Superpowers Skill недоступны, **сообщи об ограничении, не заявляй о выполнении независимой проверки** и не подменяй её собственной.

## 4. Обязательные тесты

Тестируй как основной маршрут, так и отказы. Подробные сценарии и ожидаемые результаты заданы в плане. Не исключать следующие случаи:

- Нормальный анализ `success` и сохранение только после валидации и SQL commit.
- `screening` и ранее обработанная новость → `skipped`; при `force_reanalysis=True` — безопасное обновление без дубликатов.
- Неизвестный `news_id` → `NewsNotFoundError` **до** `AgentState`, lock, графа, LLM и инструментов; ошибка PostgreSQL — не `NewsNotFoundError`.
- `impact_unknown` при недостаточности фактов; ни `impact_unknown`, ни `error`, ни `skipped` не записываются в аналитическую таблицу.
- Некорректная структура LLM, ложные идентификаторы, неверное сочетание `summary_category`/`summary_value`, пропуск существенного финансового факта; только разрешённые повторные попытки.
- Таймауты, 429, 5xx, невосстановимые 4xx, недоступные дополнительные источники и fallback суммаризации без искажения чисел.
- SSRF/DNS rebinding, приватный IP, перенаправление на запрещённый адрес, MIME/размер/таймаут; сетевые тесты используют контролируемый transport.
- Две последовательные безрезультатные операции поиска, повтор из кеша и запрещённый `continue_search` после A7.
- Исчерпание `max_iterations` и `GraphRecursionError` с корректной реакцией внешней обёртки.
- Одновременная обработка одного `news_id`; loss of lock, отмена, rollback, защита `UPSERT` от записи через другое соединение.
- Внешний `NewsAnalysisResult` без `messages`, `sources`, `raw_result` и других внутренних полей.
- Регрессия существующих модулей BondNavigator.

Выполни и отчитай **фактические** команды:

```bash
python -m pytest -q tests/analysis_news
python -m pytest -q tests/analysis_news -m postgres
python -m pytest -q
```

Для PostgreSQL-интеграционных тестов используй **только изолированную тестовую БД**. Если зависимость/тестовая инфраструктура отсутствует, честно перечисли SKIP и доступные альтернативные проверки. Не объявляй не запущенные тесты успешными.

## 5. Ограничения и безопасность

- **Не изменяй** утверждённые спецификацию и план реализации без отдельного согласования; найденные существенные противоречия опиши в ledger.
- Не применяй миграции к рабочей PostgreSQL, не изменяй реальные данные, не развёртывай сервис, не публикуй релиз.
- Не объединяй изменения в `main` и не выполняй push в общий репозиторий без отдельного разрешения.
- Не удаляй существующую рабочую функциональность ради упрощения. Не создавай лишние подсистемы, узлы, таблицы или новый пул PostgreSQL.
- Сохраняй PEP 8, типизацию, содержательные docstring на русском языке; для денежных вычислений, где это актуально, используй `Decimal`. В логах не должно быть секретов.
- Создавай отдельный осмысленный коммит после каждого проверенного этапа; каждый следующий этап начинает работу от подтверждённого состояния.
- Поскольку соответствие DDL фактической рабочей схеме PostgreSQL заранее не подтверждено, проверяй миграцию **только на тестовой БД** и сообщай о выявленных несовместимостях.

## 6. Формат отчёта

После реализации предоставь:

1. Сводку по этапам 0–10: сделано, какие файлы изменены, коммиты.
2. Для **каждого** этапа — результаты RED/GREEN, команду pytest, количество PASS/FAIL/SKIP и два вердикта независимого ревьюера.
3. Перечень найденных критичных/существенных дефектов, исправлений, повторных проверок и оставшихся рисков.
4. Отдельный отчёт о работе PostgreSQL-транзакций, advisory lock, миграций и их тестовой среде.
5. Результаты **whole-branch final-review** и итоговый вердикт.
6. Имя рабочей ветки, HEAD SHA, ссылки/пути к ledger и итоговым отчётам.
7. Что **не выполнялось** (например, применение миграции к production, push, merge), какие шаги требуют разрешения.

**Критерий завершения:** все задачи плана реализованы с проверками, независимыми review-gates и итоговым аудитом; обнаруженные важные замечания исправлены либо документированно обработаны по правилам Superpowers. До фактического прохождения проверок готовность не утверждать.
