# Специализированный Skill `langgraph-agent-architect` — проектная спецификация

> **Статус:** рабочая спецификация. Здесь зафиксированы только решения, явно согласованные с пользователем. Документ описывает создание самого Skill, а не архитектуру какого-либо конкретного LangGraph-агента. Не является разрешением на реализацию.

## 1. Назначение — согласовано

Создать универсальный специализированный Skill `langgraph-agent-architect` для **архитектурного проектирования AI-агентов**, прежде всего на основе LangGraph.

Skill помогает проанализировать требования, сравнить обоснованные архитектурные варианты, спроектировать граф и подготовить архитектурную спецификацию, пригодную для дальнейшей реализации.

Skill **дополняет Superpowers, но не заменяет его**:
- **Superpowers** управляет обсуждением требований, согласованием решений и подготовкой плана реализации.
- **`langgraph-agent-architect`** предоставляет специализированную методику архитектурного выбора и проектирования.
- **GitHub** используется для версионирования и хранения спецификаций согласно действующим правилам взаимодействия.

Архитектурные решения обсуждаются и согласовываются с пользователем; не следует безосновательно навязывать готовые паттерны.

## 2. Границы ответственности — согласовано

### Входит в область Skill

- Оценка применимости LangGraph к поставленной задаче.
- Сравнение архитектурных вариантов и обоснование выбора.
- Проектирование State и правил его обновления.
- Определение узлов и границ их ответственности.
- Проектирование переходов и условной маршрутизации.
- Проектирование циклов выполнения (включая ReAct, **если он действительно нужен**), вызовов инструментов и параллельной работы.
- Проектирование критериев успешного и аварийного завершения, обработки ошибок и восстановления.
- Проверка целостности и обоснованности архитектуры до начала реализации.

### Не входит в область Skill

- Написание Python-кода или иной непосредственной реализации графа.
- Тестирование уже реализованного программного кода.
- Развёртывание и эксплуатация приложения.
- Замена процесса обсуждения, согласования и планирования, предусмотренного Superpowers.

Реализация после согласования архитектуры выполняется отдельным процессом с Codex и соответствующими техническими навыками.

## 3. Оценка целесообразности LangGraph — согласовано

Перед выбором архитектуры Skill должен уметь оценить, оправдано ли использование LangGraph, и при необходимости рассмотреть:
- LangChain (`create_agent`);
- LangGraph (`StateGraph`);
- Deep Agents;
- гибридные сочетания этих инструментов.

Сравнение должно учитывать требования конкретной задачи. **Если пользователь уже выбрал LangGraph, этот выбор следует уважать** и сосредоточиться на проектировании графа, а не переубеждать пользователя без существенного основания.

Не следует усложнять простые задачи архитектурой, функциональность которой не требуется.

### 3.1. Выбор архитектурного подхода — согласовано

На этапе архитектурного проектирования Skill должен рассматривать **несколько архитектурных вариантов**, если задача допускает разные разумные решения. Варианты выбираются по требованиям, а не для заполнения формального списка; возможные примеры — последовательный граф с условными переходами, агент с циклом ReAct, многоагентная схема или иные применимые архитектуры LangGraph.

Для каждого существенного варианта Skill объясняет **преимущества, ограничения и соответствие целям агента**, рекомендует наиболее подходящее решение и **получает согласие пользователя перед детальным проектированием**.

Если по условиям задачи очевидно одно рациональное решение, Skill может представить только его с кратким обоснованием: искусственно создавать альтернативы запрещено.

В режиме аудита это правило применяется при необходимости предложить альтернативную архитектуру, а в режиме модификации — при выборе способа изменения существующего решения; оно не обязывает без причины перепроектировать уже работающую архитектуру.

## 4. Результат архитектурного проектирования — согласовано

Результат работы Skill — **структурированная архитектурная спецификация** со стандартизированными разделами и глубиной проработки, соответствующей сложности проектируемого агента.

| Раздел | Содержание |
| --- | --- |
| **Architecture** | Выбранная архитектура и обоснование решения |
| **State** | Структура состояния, правила чтения, обновления и объединения |
| **Nodes** | Узлы графа и ответственность каждого узла |
| **Edges** | Переходы, ветвления, условия маршрутизации |
| **Execution** | Циклы, вызовы инструментов, параллельное выполнение |
| **Termination** | Условия успешного и аварийного завершения |
| **Error Handling** | Обработка ошибок, повторы и восстановление |
| **Validation** | Критерии проверки корректности предложенной архитектуры |

Разделы должны быть содержательными, а не заполняться формально. Необязательные для конкретной задачи механизмы не нужно добавлять ради соблюдения шаблона.

### 4.1. Архитектурные контракты узлов — согласовано

Для режимов **«Проектирование с нуля»** и **«Модификация архитектуры»** Skill должен задавать для каждого узла LangGraph архитектурный контракт, достаточный для последующей реализации без повторного выяснения архитектурных решений:

- **Назначение:** ответственность узла и ожидаемый результат его работы.
- **Чтение из State:** входные данные и необходимые предпосылки.
- **Обновление State:** изменяемые поля и смысл выходных данных.
- **Зависимости:** инструменты, внешние сервисы и иные взаимодействия, если они нужны.
- **Маршрутизация:** условия перехода к следующим узлам или завершения; согласованность с разделом Edges.
- **Ошибки:** ожидаемые сбои и архитектурная политика их обработки.

Детализация соразмерна роли узла; несуществующие зависимости и ненужные механизмы не добавляются. В режиме **«Аудит архитектуры»** имеющиеся контракты используются для проверки, а при их отсутствии описываются выявленные пробелы, без выдумывания отсутствующих сведений.

Skill описывает **поведение и интерфейс узла на уровне архитектуры**, но **не пишет программную реализацию**.

### 4.2. Архитектурный контракт State — согласовано

Для режимов **«Проектирование с нуля»** и **«Модификация архитектуры»** Skill должен формировать отдельный **архитектурный контракт состояния графа (State)**. Для каждого поля состояния контракт определяет:

- **Назначение и тип** хранимых данных на архитектурном уровне.
- **Доступ узлов:** какие узлы читают поле и какие его обновляют.
- **Семантику обновления:** правила перезаписи или объединения значений; необходимость и назначение `reducers`, особенно при параллельном выполнении.
- **Сохранение и восстановление:** необходимость сохранения поля между запусками либо при приостановке и возобновлении выполнения, если это требуется сценарием.

Контракт State должен быть согласован с контрактами узлов и архитектурой выполнения. Не следует требовать reducers или сохранения данных, если они не нужны конкретному графу.

В режиме **«Аудит архитектуры»** Skill оценивает имеющуюся структуру State по тем же применимым аспектам, фиксируя пробелы и риски, но не выдумывая неизвестные поля или правила.

Skill определяет структуру и семантику State **без написания Python-кода**.

### 4.3. Архитектурный контракт переходов (Edges) — согласовано

В режимах **«Проектирование с нуля»** и **«Модификация архитектуры»** Skill должен формировать архитектурный контракт переходов графа. Для каждого перехода необходимо определить:

- **Исходный и целевой узлы** (либо завершение выполнения).
- **Условие срабатывания**: безусловный переход или проверяемое условие.
- **Механизм маршрутизации**: обычный `Edge`, условный переход, `Command` или `Send` — когда соответствующий механизм действительно нужен.
- **Альтернативные маршруты** и условия выбора между ними, если они предусмотрены.
- **Циклы и возвраты**: основания для повторного перехода, условия продолжения и достижения завершения.

Контракт должен согласовываться с архитектурными контрактами узлов и `State`. При проверке переходов Skill оценивает достижимость узлов, полноту маршрутизации, корректность выбора механизмов и риск бесконечных циклов; учитывает особенности LangGraph, включая возможность одновременно задать разные пути выполнения при сочетании управляющей маршрутизации и статических переходов.

В режиме **«Аудит архитектуры»** Skill проверяет существующую маршрутизацию на тех же основаниях, не придумывая отсутствующих связей. Описываются **архитектурные решения, а не реализация на Python**.

### 4.4. Контракт процесса выполнения (Execution) — согласовано

В режимах **«Проектирование с нуля»** и **«Модификация архитектуры»** Skill должен описывать **процесс выполнения агента**, то есть как граф обрабатывает задачу и достигает согласованной цели. Описание включает, когда применимо:

- **Последовательность выполнения:** стартовые узлы, этапы обработки, зависимости и порядок прохождения графа.
- **Вызовы LLM и инструментов:** какие узлы и для каких целей обращаются к модели или внешним инструментам.
- **Циклы ReAct и другие итерации:** что инициирует повторное действие, какие данные используются при выборе следующего шага и как оценивается прогресс.
- **Ограничения повторов:** условия продолжения и прекращения, допустимые лимиты итераций и поведение при их достижении.
- **Параллельное выполнение:** независимые ветви, ожидание и синхронизация результатов, правила объединения данных в State.
- **Завершение:** условия успешного окончания, остановки без результата и аварийного завершения; согласование с критериями достижения цели.

Описание **обязательно**, но не следует добавлять LLM, инструменты, ReAct, параллельность или иные механизмы без архитектурной необходимости. Контракт Execution должен быть согласован с описанием узлов, State, переходов, Termination и Error Handling.

В режиме **«Аудит архитектуры»** Skill анализирует существующий процесс выполнения, выявляя разрывы между фактической логикой и заявленными целями; неизвестные детали отмечаются как пробелы, а не придумываются.

Skill описывает **архитектурное поведение**, не разрабатывая исполняемый код.

### 4.5. Политика обработки ошибок и восстановления (Error Handling) — согласовано

Во всех трёх режимах Skill обязан **анализировать возможные сбои** применительно к архитектуре графа. В режимах **«Проектирование с нуля»** и **«Модификация архитектуры»** он описывает архитектурную политику Error Handling, включающую, где применимо:

- **Ошибки:** существенные ожидаемые ошибки узлов, обращений к LLM, инструментам и внешним сервисам.
- **Повторные попытки:** при каких ошибках они допустимы, ограничения количества повторов и условия прекращения.
- **Исчерпание повторов:** выбор между альтернативным маршрутом, корректным завершением с ошибкой, передачей человеку либо иным согласованным исходом.
- **Восстановление:** необходимость checkpoints и возобновления исполнения после сбоя или прерывания; условия, при которых сохранение состояния обосновано требованиями.
- **Побочные эффекты:** риск дублирования внешних операций при повторах и восстановлении, необходимость идемпотентности или другой защиты.

**Анализ ошибок обязателен**, но checkpoints, HITL, повторные попытки и другие механизмы устойчивости добавляются **только при наличии обоснованной необходимости**, а не по шаблону. Политика должна согласовываться с контрактами Nodes, State, Edges, Execution и условиями завершения.

В режиме **«Аудит архитектуры»** Skill проверяет имеющуюся политику, выявляет пробелы, риски отказов и повторных побочных эффектов. Неизвестные факты фиксируются как неопределённость.

Skill проектирует эти механизмы **на архитектурном уровне, без реализации или испытаний кода**.

## 5. Официальные LangGraph Skills — согласовано

Выбран вариант **интеграции с официальными навыками**, а не копирования их технической документации в собственный Skill.

Техническая основа: [langchain-ai/langchain-skills](https://github.com/langchain-ai/langchain-skills).

В зависимости от задачи использовать:
- `ecosystem-primer` — выбор уровня фреймворка;
- `langgraph-fundamentals` — архитектурные основы графа, состояние, узлы, переходы;
- `langgraph-persistence` — сохранение состояния и восстановление выполнения;
- `langgraph-human-in-the-loop` — участие человека, приостановка и продолжение.

**Порядок обращения:** в первую очередь использовать доступные установленные официальные Skills; если они не установлены или недоступны, получать актуальные инструкции из официального репозитория GitHub. При недоступности и того и другого не выдавать непроверенные сведения за актуальные.

Собственный Skill отвечает за **методику архитектурного проектирования**, а официальные Skills — за техническую основу конкретного фреймворка. Не следует дублировать их содержимое без необходимости.

## 6. Разделение спецификаций — согласовано

**Эта спецификация** описывает проектирование и создание самого `langgraph-agent-architect`. Она создаётся для разработки Skill и может обновляться при его развитии.

**Спецификации будущих AI-агентов** — самостоятельные документы, создаваемые отдельно для каждого проекта/агента при использовании нового Skill. Их архитектурные решения не должны смешиваться с этой спецификацией.

**Разделение требований и архитектуры конкретного агента — согласовано:** если архитектурное проектирование основано на ранее подготовленной спецификации требований, Skill **не изменяет исходную спецификацию**. Результат архитектурного проектирования оформляется **отдельным документом архитектуры**, содержащим прямую ссылку или точный путь к исходной спецификации. Это сохраняет историю требований и позволяет развивать архитектуру независимо; любые предлагаемые изменения требований отдельно согласуются с пользователем.

### 6.1. Актуализация архитектурной спецификации при модификации — согласовано

В режиме **«Модификация архитектуры»** по умолчанию Skill **обновляет существующую архитектурную спецификацию**, сохраняя историю версий через коммиты Git. Это не должно затрагивать отдельную исходную спецификацию требований.

**Новая архитектурная спецификация** создаётся вместо обновления прежней, когда проект предполагает существенную переработку архитектуры либо пользователь прямо просит отдельный документ. Skill предлагает такой вариант и объясняет причину; конкретный файл для обновления или создания новой спецификации выбирается **по согласованию с пользователем** согласно правилам взаимодействия.

Изменение документа фиксирует только согласованные архитектурные решения; несогласованные предложения не подменяют действующую архитектуру.

Репозиторий для хранения спецификаций: [VetrovDmitry007/Codex](https://github.com/VetrovDmitry007/Codex), ветка `main`, каталог `specs/`. Правила ведения спецификаций определены файлом `instructions/interaction-rules.md`.

## 7. Режимы работы и их обнаружение — согласовано

Skill должен явно поддерживать **три режима архитектурной работы**:

| Режим | Когда применяется | Основной результат |
| --- | --- | --- |
| **Проектирование с нуля** | Для нового AI-агента, когда архитектура ещё не определена | Предложение и согласование новой архитектуры графа |
| **Аудит архитектуры** | Для уже существующей архитектуры или графа, когда требуется оценить качество решения | Выявленные недостатки, риски и обоснованные рекомендации; без изменений без согласования |
| **Модификация архитектуры** | Для существующей архитектуры, которую нужно адаптировать к новым требованиям | Предлагаемые изменения, их влияние на State, Nodes, Edges, исполнение и критерии завершения |

**Обязательная обнаруживаемость режимов:** создаваемый `SKILL.md` должен содержать легко находимый раздел **«Режимы работы»** с названиями, назначением и условиями применения каждого режима. При вопросе пользователя о возможностях или режимах Skill ассистент должен кратко перечислять все три и объяснять разницу понятным языком.

**Выбор режима — только пользователем.** При начале работы над новой архитектурной задачей Skill обязан перечислить три доступных режима, кратко объяснить их назначение, **предложить рекомендуемый режим на основании запроса пользователя с обоснованием** и прямо спросить, какой режим пользователь выбирает. Автоматически назначать и запускать режим запрещено. До получения ответа не приступать к действиям внутри режима. После согласованного выбора продолжать работу в нём без повторного вопроса на каждом шаге; при явном запросе пользователя на смену режима снова согласовать выбор.

### 7.1. Работа с исходными материалами — согласовано

После того как пользователь **явно выбрал режим**, Skill определяет, какие исходные материалы нужны для выбранной задачи, и **прежде всего изучает уже доступные** сведения и артефакты (например, описание требований, архитектурную спецификацию, существующий граф/код, описание известных проблем — в зависимости от режима). Нельзя запрашивать повторно информацию, которую можно получить из предоставленных материалов.

Только после знакомства с доступными источниками Skill переходит к архитектурному анализу. Если выявлены существенные пробелы, Skill запрашивает недостающую информацию у пользователя **по мере необходимости**, объясняя, зачем она нужна; не следует автоматически требовать полный набор документов для любой задачи. Непроверенные предположения не выдаются за установленные факты.

Точный **минимально необходимый** набор исходных данных для каждого режима и формат фиксации неопределённостей пока остаются открытыми вопросами.

### 7.2. Обязательная архитектурная проверка — согласовано

Перед финальным архитектурным решением во всех трёх режимах Skill выполняет проверку архитектуры. Проверяются применимые к выбранному решению аспекты: переходы между узлами, согласованность State, завершение циклов, тупиковые ветви, обработка ошибок и восстановление после сбоев.

Проверка учитывает особенности выбранной архитектуры и не сводится к единому универсальному шаблону. Обнаруженные недостатки и рекомендации фиксируются в результате. Точные критерии и формат проверки остаются открытым вопросом.

### 7.3. Архитектурное заключение по результатам проверки — согласовано

Для каждого из трёх режимов Skill обязан формировать **архитектурное заключение** как результат проверки из раздела 7.2. В заключении отражаются:

- обнаруженные проблемы и их критичность;
- возможные последствия каждой существенной проблемы;
- обоснованные рекомендации по устранению;
- **итоговый вердикт:** архитектура готова к реализации либо требует доработки, с кратким объяснением.

Глубина заключения зависит от сложности архитектуры и обнаруженных рисков. Если существенных проблем не выявлено, это указывается явно; не нужно искусственно придумывать недостатки. Вердикт относится к **архитектурной готовности**, а не подтверждает корректность ещё не написанного или непроверенного кода.

### 7.4. Диаграммы архитектуры Mermaid — согласовано

В архитектурных спецификациях использовать **Mermaid**, чтобы граф можно было визуализировать непосредственно в Markdown на GitHub. Диаграммы должны отражать существенные узлы, переходы, условные ветвления и циклы, не противоречить текстовому описанию архитектуры.

- **Проектирование с нуля:** диаграмма обязательна.
- **Модификация архитектуры:** диаграмма обновлённой архитектуры обязательна.
- **Аудит архитектуры:** диаграмма создаётся при наличии достаточных исходных данных для достоверного восстановления графа; если данных недостаточно, это явно указывается вместо выдумывания схемы.

Диаграмма — часть архитектурной спецификации, а не исполняемый код LangGraph.

### 7.5. Цели агента, критерии успешности и предыдущая спецификация — согласовано

Прежде чем проектировать или изменять архитектуру, Skill должен определить **цель агента**, ожидаемый результат и **проверяемые критерии достижения цели**. Для ReAct-циклов и других итеративных процессов эти критерии служат основой проектирования условий продолжения, успешного завершения и прекращения при недостижении цели.

Источником целей и критериев **может служить спецификация, подготовленная на предыдущем этапе** (например, результат обсуждения требований через Superpowers). Если такой документ доступен, Skill сначала изучает его и повторно использует уже сформулированные требования и согласованные решения, не заставляя пользователя описывать их заново.

**Правило поиска предыдущей спецификации:** если пользователь хочет использовать документ, подготовленный на предыдущем этапе, **он обязан указать его точное расположение** (полный путь в репозитории либо прямую ссылку на файл). Skill сначала пытается прочитать документ **строго по указанному пути**. Если путь или ссылка не предоставлены, Skill запрашивает точное расположение и **не запускает самостоятельный поиск**. **Только если по указанному пути спецификация не найдена**, Skill ищет возможный соответствующий документ в доступном GitHub-репозитории, представляет наиболее подходящий найденный вариант (или несколько кандидатов) и **обязательно запрашивает подтверждение пользователя**, что выбранный документ является нужной спецификацией. До подтверждения нельзя принимать найденный документ за источник согласованных требований. Если предыдущей спецификации не существует, требования выясняются и согласовываются в ходе обсуждения.

При отсутствии предыдущей спецификации или при существенных пробелах Skill уточняет недостающие цели и критерии у пользователя. Не следует приписывать спецификации требования, которых в ней нет. **Ранее согласованная спецификация — основной источник требований.** Если обнаружено противоречие с новыми предложениями или архитектурными ограничениями, Skill обязан показать расхождение, объяснить причину предполагаемого изменения и запросить согласие пользователя. **Самостоятельно изменять исходные требования запрещено.** До согласования изменений действуют ранее утверждённые требования; невозможность выполнить их в предложенной архитектуре нужно обозначить как открытый вопрос, а не скрыто корректировать.

### 9.1. Проверочные сценарии самого Skill — согласовано

До завершения разработки `langgraph-agent-architect` необходимо проверить, что он применим **к разным архитектурам LangGraph**, а не оптимизирован лишь для одного типа графа. Обязательные проверочные сценарии:

1. **Последовательный граф** с обычными и условными переходами.
2. **Агент с циклом ReAct**, выбором инструментов и условиями остановки.
3. **Параллельное выполнение** с корректным объединением состояния.
4. **Многоагентная архитектура** с передачей управления и разграничением ответственности.
5. **Human-in-the-Loop (HITL)** с прерыванием и продолжением.
6. **Сохранение и восстановление через checkpoints**, включая риски повторного выполнения побочных эффектов.

В сценариях проверять не только корректность архитектурных решений, но и способность Skill **выявлять архитектурные ошибки**, обосновывать выбор, соблюдать согласованные ограничения и **не усложнять простые задачи** без оснований. Проверить применение всех трёх режимов работы к подходящим примерам.

Методика проверки — `superpowers:writing-skills`, включая подход **RED–GREEN–REFACTOR**: подготовка сценариев и фиксация исходного поведения без нового Skill, проверка с Skill и корректировка его инструкций по результатам. Не объявлять Skill полностью проверенным, если практические испытания не проводились или не удалось выполнить их в доступной среде.

Точные формализованные критерии прохождения сценариев и форма протокола проверок остаются для дальнейшего согласования.
