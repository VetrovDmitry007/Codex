### 8.23. Ограничение предметных MCP-вызовов до `capability_check` (30.10.2026)

Для MCP Tools допускать `tool_calls` лишь по разрешённым идентификаторам; для MCP Resources (включая зарегистрированные шаблоны URI) и MCP Prompts — чтение/получение лишь по разрешённым идентификаторам и корректным параметрам. Служебные MCP discovery-вызовы самого клиентского инструмента семантического поиска через `Capability Router` не являются предметными вызовами `Assistant` и сохраняют ранее согласованное право получать актуальный полный каталог.

**Область действия:** список разрешённых объектов относится к текущей подзадаче и текущему выполнению; серверный Skill не изменяется. Не добавлять новые узлы LangGraph или отдельный агент. **План проверок после разрешения на реализацию:** разрешённый объект исполняется; объект вне списка отклоняется; новые принятые объекты становятся доступны после `ready`; преждевременный предметный вызов запрещён; внутренний MCP discovery сохраняет возможность чтения полного каталога. Python-код не изменялся, `pytest` не запускался.


### 8.34. Отклонение MCP-вызова вне разрешённого списка (30.10.2026)

**Статус: согласовано пользователем.** Если `Assistant` попытается вызвать MCP Tool, прочитать Resource или получить Prompt, отсутствующий в актуальном разрешённом списке `mcp_objects` текущей подзадачи в `AgentState`, **клиент отклоняет операцию до обращения к MCP-серверу**. Ограничение действует при `ready` и не ослабляет ранее согласованный запрет предметных вызовов до `ready`.

**Обратная связь в существующем ReAct-цикле:** вернуть в `Assistant` диагностический результат отклонённого вызова с указанием причины («объект вне разрешённого списка»), чтобы LLM могла выбрать другой разрешённый объект. Для вызова через `tool_calls` обеспечить корректное соответствие результата идентификатору исходного вызова. Отклонение не должно маскироваться под успешное получение данных и не должно автоматически пополнять `mcp_objects`.

**Ограничения:** попытка и последующая корректировка учитываются в общем лимите `max_react_iterations = 20`; не создавать дополнительный бесконечный цикл, новый узел графа или отдельный агент. Если в пределах лимита добиться выполнения обязательных `success_criteria` нельзя, завершить подзадачу со статусом `blocked` и общей диагностикой; к пользователю не обращаться. Режим `debug: bool = False` по-прежнему управляет только подробными причинами отбора кандидатов и не отключает сообщение об отклонённом неразрешённом вызове.

**Проверки после разрешения на реализацию:** запрет MCP-обращения при неразрешённом идентификаторе; диагностика в ответе `Assistant`; выбор альтернативы из рабочего списка; сохранение пределов ReAct; корректное завершение `blocked` при исчерпании лимита. Исходный Python-код не изменён; `pytest` не запускался.


### 8.35. Продолжение независимых подзадач после `blocked` (30.10.2026)

**Статус: согласовано пользователем.** Если отдельная подзадача завершилась со статусом `blocked`, **не останавливать весь пользовательский запрос автоматически**. `Task Evaluation` фиксирует статус и причину блокировки в `AgentState`, а `Task Selection` продолжает выбор и выполнение оставшихся подзадач, **не зависящих от заблокированной**. Сохранённый `blocked` не считать успешным результатом и не подменять отсутствующие данные предположениями.

Для подзадач, которым необходим результат заблокированной, требуется отдельно оценить достижимость их обязательных `success_criteria` по реально имеющимся данным; не объявлять их выполненными только потому, что независимая работа продолжилась. Общий ответ должен отражать результат каждой подзадачи и ограничения частичного выполнения. Новые узлы LangGraph и статусы не вводятся, прежний общий лимит ReAct сохраняется.

**Проверки после разрешения на реализацию:** одна подзадача `blocked`, независимая выполняется; причина блокировки сохраняется; зависимая подзадача не получает вымышленных данных; финальный ответ обозначает частичный результат. Исходный Python-код не изменялся, `pytest` не запускался.


### 8.36. Выполнение подзадачи при частичной доступности результатов заблокированной зависимости (30.10.2026)

**Статус: согласовано пользователем.** Если предшествующая подзадача получила `blocked`, но часть нужных данных доступна из `AgentState` или других фактически полученных результатов, зависимую подзадачу **разрешается выполнять**, если её обязательные `success_criteria` достижимы на этих данных. Формальная зависимость сама по себе не означает обязательную блокировку.

**Порядок:** `Task Selection` рассматривает возможность продолжения зависимой подзадачи с имеющимися фактическими входами; после загрузки соответствующего дочернего Skill существующий `capability_check` оценивает достаточность входных данных и `mcp_objects`. При `ready` подзадача выполняется, иначе применяется согласованная ветка `Capability Router` или `blocked`. В выводе явно сохраняется информация об ограничениях предшествующего результата. Не подставлять недостающие сведения и не выдавать `blocked` предшественника за `completed`.

**Проверки при реализации:** частичные данные достаточны → выполнение продолжается; недостаточны для обязательных критериев → корректный статус и диагностика; отсутствует выдуманное значение; итоговый отчёт отражает частичное выполнение. Новые узлы графа и статусы не вводятся.

### 9.1. Хранение и публикация новых Skills в отдельных JSON-файлах (30.10.2026)
