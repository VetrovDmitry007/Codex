## Что уже согласовано

### Архитектура клиента

- LangGraph: `Task Selection` выбирает подзадачу, `capability_check` **перед** `Assistant` оценивает осуществимость `success_criteria` с текущими MCP-объектами; `Task Evaluation` отдельно определяет результат подзадачи. После каждого `ToolMessage` повторно вызывать `capability_check` **не нужно**.
- `capability_check` различает недостаток MCP-возможностей (`missing_mcp`) и недостаток данных (`missing_data`). При нехватке возможностей `Capability Router` пользуется семантическим поиском по актуальному каталогу MCP Tools, Resources и Prompts. Поисковый инструмент сам запрашивает каталог через MCP, возвращает несколько кандидатов; роутер поочерёдно проверяет пригодность, добавляя принятые объекты **только в `AgentState` текущего выполнения**. Серверные Skills не меняются.
- Не более **2 циклов `capability_check` на одну подзадачу**. После `ready` существующий `Assistant` использует актуальные `mcp_objects` из `AgentState`. Исполнять разрешено **только** объекты из списка текущей подзадачи; вызов вне списка отклонять до обращения к MCP-серверу с диагностикой в обычном ReAct-цикле. Общий предел `max_react_iterations = 20`.
- Невыполнимая подзадача завершается `blocked` с диагностикой. Независимые подзадачи можно продолжать; зависимые — тоже, если по фактически доступным данным всё ещё достижимы обязательные критерии. Не придумывать недостающие данные. Детальные причины принятия/отклонения MCP-кандидатов хранить **только при `debug: bool = True`** (по умолчанию `False` в `mcp_client/config.py`); общая диагностика ошибок обязательна.
- Транспорт MCP — **Streamable HTTP**, согласован и уже реализован. Настройки клиента в `mcp_client/config.py`, секреты из переменных окружения. Подключение LLM через CLIProxyAPI; таймаут LLM — 90 секунд, MCP — 30 секунд, **одна повторная попытка** для разрешённых временных ошибок. Не добавлять лишние узлы LangGraph.
- Новые Skills — **отдельные JSON-файлы** (основные без `sub_`, дочерние с `sub_`); сервер должен публиковать каталог по `bondnavigator://skills`, отдельные Skills — по `bondnavigator://get_skill/{url_name}`. Каталог читается с диска при запросе без кэша, на прототипе только минимальная проверка JSON. Старые `bondnavigator://instructions` и Markdown Skills — наследие, не образец новой архитектуры.

### Текущий комплект Skills

- Основной: `portfolio_cashflow`, `description` **«Анализ облигационного портфеля с учётом выплат до конца месяца»**. Корневые поля JSON: `name`, `description`, `subtasks`; не вводить дополнительные корневые поля без отдельного согласования.
- Две дочерние подзадачи: `sub_portfolio_analysis` (анализ портфеля) и `sub_month_cash_flow` (выплаты до конца месяца). В обеих `inputs: ["account_id"]`.
- Основному сценарию передаётся **либо `account_id`, либо `user_id`**. По известному `account_id` анализ начинается сразу. Если передан только `user_id`, сначала прочитать `bondnavigator://users/{user_id}/accounts`, показать варианты и **спросить пользователя, какой счёт анализировать**; до выбора предметные подзадачи не запускать. Не использовать устаревшее правило, по которому одновременно обязательны оба идентификатора, и не брать `user_id` только из конфигурации.
- `sub_portfolio_analysis.json`: **18 MCP-объектов**, исходный снимок `bondnavigator://accounts/{account_id}/portfolio`; `free_cash_rub` (свободные рубли) и `parking_value_rub` (рыночная стоимость парковки) берутся **из снимка** и показываются отдельно. Анализировать доходность к погашению/применимой оферте и отдельно текущую купонную доходность, риски, ликвидность, рыночный стресс, концентрации и состояние эмитентов; углублённые запросы только при основаниях.
- `sub_month_cash_flow.json`: **7 MCP Resources**. Основной календарь `bondnavigator://accounts/{account_id}/cash-flow/31?provider=db`: дата запуска — конец **текущего календарного месяца**, `provider=db` по умолчанию, без автоматического перехода на `t_invest`. Анализировать купоны, погашения, амортизации и оферты; **условную сумму оферты не считать гарантированным поступлением**. Оба дочерних Skill являются независимыми по результату: `sub_month_cash_flow` не требует предварительно завершённого `portfolio_analysis`.
- Три JSON пока **проектные файлы в Codex**, а не подтверждённая рабочая установка на BondNavigator MCP-сервере. Серверный механизм чтения новых JSON Skills и новый MCP Prompt ещё предстоит реализовать и проверить отдельно.

## Текущая точка обсуждения — новый MCP Prompt для качества портфеля

**Уже согласовано пользователем:**

1. Создать **отдельный MCP Prompt** с коротким именем `assess_portfolio_quality` (не путать с этим файлом передачи контекста).
2. Разместить его как `type: "prompt"`, `identifier: "assess_portfolio_quality"` в `mcp_objects` дочернего Skill `sub_portfolio_analysis` **после согласования методики и реализации/регистрации Prompt на MCP-сервере**. До тех пор дочерний JSON содержит 18 объектов; будущий состав — 19.
3. Итог анализа — **аргументированная оценка эффективности и качества всего портфеля**, а не просто список бумаг. Определять облигации, которые повышают общий риск, и бумаги, которые поддерживают устойчивость.
4. Не вводить третью подзадачу LangGraph. MCP Tools/Resources поставляют проверяемые данные и расчёты; MCP Prompt задаёт методику интерпретации и объяснения; Skill фиксирует сценарий и критерии выполнения.
5. Предварительные направления методики: доходность с учётом риска; неблагоприятные и устойчивые позиции; концентрация по выпуску/эмитенту/группе; денежные потоки и возможности реинвестирования до конца месяца; обоснованные выводы с неопределённостью и ограничениями. Не смешивать виды доходности и не выдавать качественное впечатление за численно рассчитанный риск.

**Ещё не согласовано:** конкретная методика вычисления/оценки вклада каждой бумаги в совокупный риск, классификация её роли, пороги и веса, аргументы и формат результата самого MCP Prompt, его точный текст и серверная регистрация. Нет утверждённой формулы `portfolio_quality_score`; не выдумывать её.

**Последний обсуждавшийся, но ещё не подтверждённый пользователем принцип:** раздельно оценивать **собственный риск выпуска** и **его влияние на риск всего портфеля** с учётом веса позиции и концентрации. Иллюстрация: рискованная бумага весом 1% может влиять на портфель меньше, чем умеренно рискованная бумага весом 25%. При этом вес×индивидуальный балл не обязательно является строгим измерением совокупного портфельного риска — различай обоснованный прокси-показатель и качественную оценку.
