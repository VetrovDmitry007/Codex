# Результаты поиска станций — рамки архитектуры

**Статус:** ЧЕРНОВИК; **не утверждён к реализации** (2026-11-13).  
**Утверждён только графический макет:** [station-search-results-approved.jpg](./station-search-results-approved.jpg) и [UX-требования](./requirements.md).

## Разделение ответственности — согласованный принцип (2026-11-13)

**Widget — только представление готовых результатов поиска.** Он получает от вызывающего обработчика список станций с исходными названиями и кодами и **отображает** их по утверждённому макету (до пяти на странице, локальные визуальные действия навигации). Нажатие на карточку лишь сообщает наружу идентификатор выбранного элемента; Widget **не ищет станции, не обращается к РЖД, не выполняет бизнес-валидацию, не принимает решений о сохранении, не изменяет FSM и не выбирает станцию автоматически**.

**Существующие обработчики и бизнес-логика TrainBot** формируют список по пользовательскому запросу, определяют, когда и какие результаты передавать виджету, обрабатывают событие выбора, проверяют код и контекст, сохраняют станцию и управляют сообщениями/возвратом в меню. **Условие запуска согласовано (2026-11-13):** существующий обработчик вызывает Widget **только после формирования непустого списка станций** (минимум один результат). Если список отсутствует или пустой, Widget **не создаётся и не отправляется**; сценарий нулевого результата остаётся за существующим кодом TrainBot. Поведение самого TrainBot при нулевом результате этой спецификацией не изменяется.

Это согласование **границы ответственности**, а не утверждение протокола передачи данных или реализации. Детали доставки списка, отправки события, пагинации и синхронизации состояния будут обсуждаться отдельно.

## Публичный интерфейс генератора — УТВЕРЖДЕНО 2026-11-13

Модуль Widget предоставляет **одну публичную Python-функцию**, принимающую **список строк `list[str]` и заголовок `str`** и возвращающую **готовый HTML Widget как `str`**. Обновлённый публичный контракт (утверждено 2026-11-13):

```python
def render_station_widget(stations: list[str], title: str) -> str:
    ...
```

- `stations` — весь готовый непустой список, сформированный существующим кодом TrainBot; генерируемый Widget отображает данные, не обращаясь к РЖД.
- `title` — **произвольный заголовок, переданный вызывающим кодом**, который выводится в шапке Widget. Заголовок **не захардкожен** под «Станция отправления» или «Станция назначения». Это позволяет **повторно использовать интерфейс отображения списка** в других сценариях.
- Возвращаемый `str` — HTML/JS для визуального списка с локальной пагинацией срезом массива по пять элементов, без вызова backend при перелистывании.
- **Отправка через Telegram API, получение событий, серверная проверка, FSM и сохранение значения — ответственность вызывающего кода.**

Имя `render_station_widget` пока **рабочее**, поскольку текущий сценарий — выбор станций; окончательное имя общего компонента можно согласовать позднее. **Универсальность структуры элементов и полезной нагрузки выбора отдельно не утверждена:** для текущего TrainBot формат `Название_Код` сохраняется и не должен ломаться при обобщении. Исходный поисковый запрос, предусмотренный в UX-макете, **пока не передаётся отдельным аргументом**; способ его отображения остаётся открытым вопросом.

### Формат элемента списка — ПОДТВЕРЖДЕНО ПРИМЕРОМ ПОЛЬЗОВАТЕЛЯ 2026-11-13

Каждый `str` имеет формат **`<название>_<код>`**, например `'Москва_2000000'`, `'Мосты_2101155'` или `'МстинскийМост_2004589'`. Это формат фактического списка, предоставленного пользователем; реализацию формирующего его обработчика отдельно ещё не исследовали.

- Разбирать строку **по последнему символу `_`**: `name, code = station.rsplit("_", 1)`. Это не ломает названия, которые сами могут содержать подчёркивания.
- Название отображать **как передано** в основной строке карточки (без самовольной нормализации), код — второй строкой мелким шрифтом. Код сохранять **строкой**, не приводить к `int`, чтобы не терять возможные ведущие нули.
- На этапе реализации обеспечить безопасное экранирование/сериализацию перед вставкой данных в HTML/JS; некорректные элементы не должны создавать ошибочную станцию или XSS.
- **Не согласовано:** источник исходного поискового запроса при параметрах `stations` и `title`; способ передачи события выбора и его полезная нагрузка; степень универсальности формата элемента для других списков.

## Передача списка и пагинация — УТВЕРЖДЕНО 2026-11-13

- Существующий обработчик TrainBot формирует **весь готовый непустой список** станций и **однократно передаёт его Widget при создании**. Widget не обращается к РЖД и не запрашивает дополнительные страницы у сервера.
- Внутри Widget доступен **полный переданный массив** станций. Текущая страница формируется **локальным срезом массива** по пять элементов, например `stations.slice(page * 5, (page + 1) * 5)` для нумерации страниц с нуля.
- Стрелки изменяют только **локальный индекс страницы**; для перелистывания **не отправляется widget_query** и не вызывается backend. Диапазон и активность стрелок рассчитываются по длине полного массива.
- Утверждённый UX сохраняется: фиксированная высота, постоянное место пагинации, пагинация видна даже при одной странице, обе стрелки на единственной странице неактивны.
- **Ограничение для следующего решения:** Telegram Bot API допускает HTML до 32768 байт UTF-8 и до 4096 байт после zlib(9), а `chat_data` — не более 1024 байт UTF-8. Поэтому способ упаковки полного списка (в HTML или в состоянии), проверку размера и действие при переполнении лимитов **ещё требуется согласовать**. Решение «передавать весь список» не отменяет платформенные ограничения. Источник: https://core.telegram.org/bots/widgets и https://core.telegram.org/bots/api.

## Предполагаемая граница изменения

```text
Старый ввод названия станции в чате
  -> существующий поиск РЖД / получение списка (имя, код)
  -> НОВОЕ: представление найденных результатов через Widget
  -> нажатие на кнопку станции (без отдельной кнопки подтверждения)
  -> проверка пользователя, FSM и кода на сервере
  -> существующая логика применения станции / возврат к параметрам
```

Это схема для обсуждения, **не утверждённая схема транспорта**. Прежний алгоритм поиска, FSM и бизнес-логика остаются неизменными по умолчанию. Требуется исследовать фактические обработчики выбора станции в `handlers/subscrib.py`, `handlers/booking.py`, `handlers/report_1.py` и других сценариях **по актуальным исходникам**, не изменяя их без отдельного поручения.

## Что согласовать до программирования

- Передача исходного поискового запроса (в UX-макете он присутствует), универсальный формат элементов/выбранного значения за пределами списка станций; способ встраивания полного списка в HTML, проверка лимитов и поведение при превышении; жизненный цикл данных для серверной проверки выбранного кода.
- Поддержку `sendWidget`, `widget_query`, `answerWidgetQuery` в реально установленной версии aiogram и Telegram Bot API; существующий транспорт календаря переиспользовать, если применимо.
- Формат события нажатия на станцию и защиту от подмены кода, повторных/просроченных событий; обновление FSM только после серверной проверки выбранной станции.
- Поведение `Отмена`, удаление сообщения Widget, ошибки обработки нажатия; **fallback** на исходные inline-кнопки. Кнопки `Подтвердить` нет.
- Тесты: 1/0/много результатов, одноимённые станции с разными кодами, пагинация, закрытие, быстрые повторные нажатия, рестарт FSM, реальные Telegram-клиенты.

Проверить официальные [Telegram Widgets](https://core.telegram.org/bots/widgets), [Bot API](https://core.telegram.org/bots/api), установленный aiogram и [telegram-aiogram-widgets Skill](../../../.agents/skills/telegram-aiogram-widgets/SKILL.md). Канонический путь Skill от корня репозитория: `.agents/skills/telegram-aiogram-widgets/SKILL.md`.
