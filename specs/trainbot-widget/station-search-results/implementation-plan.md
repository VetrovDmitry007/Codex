# Выбор станций в подписке «Отслеживание» — план реализации

**Статус:** Черновик — ожидает утверждения  
**Дата:** 2026-11-13

> **Для исполнителя:** после утверждения выполнять задачи последовательно, сверяясь с UX-требованиями, архитектурой и этим планом. До утверждения production-код не менять.

**Цель:** заменить выдачу результатов поиска станций в подписке «Отслеживание» на один переиспользуемый HTML Widget, сохранив поиск РЖД, FSM и существующие inline-обработчики.

**Подход:** новый модуль формирует автономный HTML и локальную пагинацию. Две функции поиска в `handlers/subscrib.py` отправляют его через текущий Telegram Widget транспорт; действующий обработчик `widget_query` получает отдельную ветку выбора станции. Проверки пользователя, FSM, сообщения и результата предшествуют записи прежних FSM-полей. Календарь и его ветка остаются без изменений.

**Технологии:** Python, aiogram 3 и уже используемые в проекте `send_widget()`, `answer_widget_query()`, общий update middleware.

**Основание:** `specs/trainbot-widget/station-search-results/requirements.md`, `architecture.md` и утверждённый макет `station-search-results-approved.jpg`.

## Границы и обязательные решения

- Production-файлы: `handlers/subscrib.py` и один новый модуль `widgets/station_widget.py`.
- Тесты: новые `test/station_widget/test_render.py` и `test/station_widget/test_flow.py`.
- Не менять `bot.py`, `widgets/telegram_api.py`, календарь, `core/util_bot.py`, `handlers/booking.py`, `handlers/report_1.py`, другие подписки и отчёты.
- Публичный интерфейс нового модуля — ровно `render_station_widget(stations: list[str], title: str) -> str`; параметр `search_query` не добавлять.
- Вызов существующего `get_expressCode_async(message.text)` остаётся в обоих обработчиках поиска. Widget отправлять только при непустом списке. Для пустого списка и ошибки отправки сохранить путь с прежними inline-кнопками.
- Станции отображать в стиле утверждённого макета: компактная светло-голубая форма, карточки с названием и кодом, без изображений, отметок выбора и «Подтвердить». Один результат тоже требует нажатия.
- Пагинация локальная, до пяти карточек по умолчанию. Диапазон, стрелки и их неактивные состояния отображаются всегда; высота формы не меняется из-за короткой последней страницы.
- Конфигурацию держать в `WIDGET_CONFIG`; каждый ключ снабдить коротким комментарием в той же строке. Минимально нужные параметры: `page_size` (значение по умолчанию 5) и `value_label` (значение по умолчанию «Код»).
- Элемент с подчёркиванием разбирается по последнему `_`; без подчёркивания вся исходная строка является названием. HTML/JS данные экранировать/сериализовать.
- Для выбора длиной до 64 байт UTF-8 отправлять всю исходную строку. Если длиннее — сократить текстовую часть перед последним `_` до первых пяти символов с точкой, сохранив суффикс; строку без `_` сокращать так же целиком. После сокращения повторно измерять UTF-8. Если всё ещё более 64 байт — пропустить элемент с `WARNING`, индексом и размером, не записывая полное значение. При совпадении подготовленных строк оставить первую, последующие пропустить.
- Использовать уже существующие `send_widget()`, `answer_widget_query()`, общий маршрут `widget_query` и паттерн защиты из календаря. Не строить новый Telegram API транспорт.
- Старые `select_DepName()` и `select_DestName()` оставить без изменений. Новая ветка выбора сохраняет `DepName`/`DepCode` либо `DestName`/`DestCode`, сбрасывает состояние ввода и вызывает возврат к `prm_sub_otslej()`.
- Отмена не меняет сохранённую станцию, удаляет сообщение Widget и возвращает прежнее меню параметров. Выбор проверяет пользователя, приватный чат, актуальное состояние, message_id и соответствие переданному сервером списку; повторные нажатия блокируются/идемпотентны. На ошибки выбора распространяется существующее поведение TrainBot.

## Review Focus

- Unicode-строка длиннее 64 байт, в том числе когда суффикс после последнего `_` сам превышает предел.
- Разные элементы, давшие одинаковую сокращённую строку; сохраняется только первый без неоднозначного выбора.
- Устаревший Widget, чужой пользователь/message_id, рестарт MemoryStorage и двойной запрос не меняют FSM.
- Страницы с 1–5 элементами и короткой последней страницей сохраняют видимый блок пагинации и фиксированную высоту.
- Ошибка отправки, пустые результаты, отмена и ошибка выбора сохраняют прежние сценарии TrainBot.

## Риски и расхождения, требующие разрешения до реализации

1. **Поисковый запрос в макете.** UX-требования требуют показывать исходную поисковую строку в шапке, а утверждённая функция имеет только `stations` и `title`; архитектура отдельно фиксирует это несоответствие. Не добавлять третий параметр и не выводить запрос эвристически. До реализации нужно определить, как сохранить/передать строку внутри уже существующего сценария либо принять отсутствие строки в шапке.
2. **Inline markup отправки.** Текущий локальный `widgets.telegram_api.send_widget()` требует `reply_markup`, хотя параметр `reply_markup` в Bot API для `sendWidget` необязателен. План запрещает менять этот транспорт; перед реализацией проверить допустимость вызова с пустой `InlineKeyboardMarkup`. Если API/сериализатор этого не принимает, объём затронутых файлов потребуется отдельно согласовать.
3. **Отмена и полные исходные строки.** Формат данных запроса выбора фиксирован исходной строкой, а отдельный зарезервированный payload отмены не зафиксирован. Перед реализацией определить код отмены, который не даст ошибочно интерпретировать реальное имя станции как отмену; проверять это пересечение тестом.
4. **Автоматический fallback для неподдерживаемых клиентов.** Telegram не сообщает боту, способен ли клиент отрисовать Widget. Сбой отправки можно обработать старым inline-списком, но способ гарантировать fallback после успешной отправки на клиенте без поддержки требует отдельного решения, не нарушающего утверждённый макет.
5. **Высота и конфигурация.** Требование фиксированной высоты утверждено, но конкретный размер `height` в архитектуре оставлен открытым; также `page_size` настраиваемый. Значение следует сверить с макетом и проверить для неполной страницы до финального утверждения реализации.
6. **Базовая версия исходников.** Точки подключения проверены в доступном локальном `RZD_COM` на ветке `widget-calendar`; перед реализацией сверить, что целевой checkout/production совпадает с этой версией. Ветка документации `Codex/main` не содержит runtime TrainBot.
