# Техническая архитектура виджета выбора станций TrainBot — черновик

- **Дата:** 2026-11-12
- **Статус:** предложение; НЕ утверждено; реализация не выполнялась
- **Требования:** [station-widget-2026-11-12.md](./station-widget-2026-11-12.md)
- **Связь с календарём:** отдельный компонент выбора станций; допустимо повторное использование общих Widget-транспортных адаптеров только после их реализации/проверки

## Исходная система и проверенность

- По приложенному `PROJECT_STRUCTURE.md`: `handlers/subscrib.py` содержит `StSubscr`, `select_sity_depart()`, `select_DepName()`, `select_sity_dest()`, `select_DestName()`, `prm_sub_otslej()`; `core/util_bot.py` содержит `get_expressCode_async()`.
- В ранее утверждённой архитектуре календаря упоминаются FSM-поля `DepName`, `DepCode`, `DestName`, `DestCode` и `TrainNumber`, `TimeDepart`; фактический текущий код `subscrib.py` в данной задаче отдельно не загружен, поэтому конкретные контракты и сигнатуры нужно сверить перед планом реализации.
- В приложенном `bot.py` присутствуют `Dispatcher(storage=MemoryStorage())` и long polling; реальная версия aiogram не установлена по этому файлу.
- `specs/trainbot-widget/calendar-widget-architecture-2026-11-12.md` утверждает архитектуру адаптера Telegram Widget, но его код ещё не подтверждён реализованным.
- Официальный Bot API 10.4 (2026-11-09): `sendWidget`, `widget_query`, `answerWidgetQuery`, `editMessageWidgetData`. В `sendWidget` параметр `width` задаёт логические пиксели и ограничивается клиентом снизу 200 и сверху шириной сообщения.

## Предложенный поток событий (не утверждено)

1. **Единая реализация Widget**, общий HTML/JS-шаблон, поиск и события как для «Откуда», так и для «Куда». В меню «Отслеживание» пользователь отдельно открывает виджет для одного из двух FSM-полей. Сервер передаёт назначение выбора (`departure` или `destination`) и соответствующий заголовок и сохраняет идентификатор активного сообщения, владельца и ожидаемое поле **на сервере**, чтобы не полагаться на выбор поля в JS. В один момент подтверждается только одна станция; два разных HTML-виджета не создавать.
2. При создании Widget сервер читает **текущее значение конкретного поля станции** из действительного контекста FSM/подписки (в зависимости от сценария создания или редактирования) и безопасно передаёт клиенту только отображаемое название и серверный идентификатор/код выбранной станции, если она уже определена. На первом экране сверху отображается текущий город, ниже четыре фиксированных варианта **Москва, Санкт-Петербург, Казань, Сочи** и кнопка «Другие станции»; текущая станция не должна извлекаться из ещё не реализованной истории выбора. Если станции нет, показывать **«Не выбрана»** и **«Выбрать станцию»** вместо «Заменить на»; пустое состояние не должно использовать фиктивный код.
3. «Другие станции» локально открывает алфавит из 33 букв; нажатия букв **локально дописывают слово** в строку ниже букв. Никаких запросов на переключение или каждую букву. Кнопка «Поиск» расположена справа от строки.
4. Только при нажатии «Поиск» Widget передаёт набранное слово в backend через `TelegramWidget.request` -> `widget_query` -> существующий сервис поиска станций РЖД -> ответ/передача доступных кандидатов в Widget. Контракт результатов, пагинации и способов обновления UI **пока не согласован**. Прямой `fetch` из Widget не закладывать. Учесть ограничение 1–64 байта UTF-8 для request (в частности кириллица занимает больше одного байта); лимит длины запроса/альтернативную схему передачи согласовать при проработке архитектуры.
5. При касании любого варианта замены Widget лишь **локально выделяет кандидата**; старое значение на первом экране и в FSM/подписке не меняется. Только кнопка **«Подтвердить»** отправляет `widget_query` с идентификатором кандидата -> сервер проверяет владельца, актуальное сообщение, FSM, ожидаемое поле, допустимость кода станции и отсутствие устаревших данных -> обновляет только соответствующие поля (`DepName/DepCode` или `DestName/DestCode`) через прежнюю бизнес-логику -> отвечает и возвращает пользователя в меню параметров. Конкретный порядок сохранения при редактировании должен быть уточнён по текущим обработчикам.
6. При смене ранее установленной станции предложено сбрасывать зависящие от маршрута `TrainNumber`/`TimeDepart`; требует проверки legacy-логики и отдельного утверждения.
7. **Отмена через «×» (UX согласован, реализация предлагается):** верхняя правая кнопка видна на всех экранах Widget. На клиенте не вызывать неподтверждённый `TelegramWidget.close()` — Widget встроен в сообщение, а не является окном Mini App. Предлагаемый путь: по нажатию инициировать `TelegramWidget.request("cancel")`; backend проверяет владельца, чат и message_id, помечает контекст выбора недействительным, отвечает на widget_query и **не меняет DepName/DepCode/DestName/DestCode, подписку и пользовательские параметры FSM**. Для удаления виджета из чата использовать `deleteMessage` для исходящего сообщения бота, когда разрешено Telegram (обычно до 48 часов после отправки). Если удалить сообщение не удалось — перевести виджет в неактивное состояние «Выбор отменён» через данные, обновлённые ботом, не принимая новых подтверждений. Реальную последовательность answer/delete, гонки и UX проверить на Telegram-клиентах до утверждения архитектуры.
8. На неподдерживающем Widgets клиенте сохранить штатный путь ввода/подбора станции через сообщения и inline-кнопки.

## Альтернативы и границы

- Inline-кнопки: совместимость выше, но алфавитный многошаговый выбор раздувает чат и создаёт больше событий.
- HTML Widget (предложено): быстрый компактный первый экран и алфавит в том же сообщении; список станций нельзя получать через обычный WebView/fetch.
- Mini App: уместна при необходимости длинных каталогов, полноценного поля поиска и HTTP, но для текущего UX избыточна.

## Безопасность, ошибки, совместимость

- Проверить фактическую версию aiogram; для неподдерживаемого `widget_query` придерживаться уже утверждённого календарём изолированного адаптера/outer middleware после проверки `Update.model_extra`.
- Не доверять станции/её коду и полю выбора из JS; server-side проверка, авторизация, идентификатор сообщения, текущий FSM/state, просроченные/дублированные запросы.
- Не класть в HTML секреты, пользовательские аккаунты РЖД или платёжные данные.
- Учитывать лимиты Telegram (HTML до 32768 UTF-8 байт и до 4096 после zlib max; request 1–64 байта; answer до 1024 байт; ответ ≤15 секунд; rate limit).
- На пустых результатах поиска по набранному слову — сообщение и возможность исправить запрос, без порчи FSM; при ошибке API — fallback в чат. Предлагаются локальные кнопки «⌫» и «Очистить», их вид и поведение ещё не утверждены.
- MemoryStorage теряет контекст после рестарта; старые запросы отклоняются.

## Следующий шаг

Согласовать UX списка станций после выбора буквы. Затем подтвердить точную FSM-интеграцию по актуальному `handlers/subscrib.py`, утвердить архитектуру и подготовить план; **production-код не менять**.
