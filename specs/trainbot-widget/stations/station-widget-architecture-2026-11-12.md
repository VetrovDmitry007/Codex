# Техническая архитектура виджета выбора станций TrainBot — черновик

- **Дата:** 2026-11-12
- **Статус:** исторический черновик; НЕ утверждено; актуальное согласование ведётся в [новом документе](./station-widget-architecture-review-2026-11-12.md). Упоминание нереализованного календаря ниже отражает прежнее состояние материалов и не заменяет сообщение владельца от 2026-11-12 о завершённой и проверенной реализации.
- **Требования:** [station-widget-2026-11-12.md](./station-widget-2026-11-12.md)
- **Связь с календарём:** отдельный компонент выбора станций; допустимо повторное использование общих Widget-транспортных адаптеров только после их реализации/проверки

## Исходная система и проверенность

- По приложенному `PROJECT_STRUCTURE.md`: `handlers/subscrib.py` содержит `StSubscr`, `select_sity_depart()`, `select_DepName()`, `select_sity_dest()`, `select_DestName()`, `prm_sub_otslej()`; `core/util_bot.py` содержит `get_expressCode_async()`.
- В ранее утверждённой архитектуре календаря упоминаются FSM-поля `DepName`, `DepCode`, `DestName`, `DestCode` и `TrainNumber`, `TimeDepart`; фактический текущий код `subscrib.py` в данной задаче отдельно не загружен, поэтому конкретные контракты и сигнатуры нужно сверить перед планом реализации.
- В приложенном `bot.py` присутствуют `Dispatcher(storage=MemoryStorage())` и long polling; реальная версия aiogram не установлена по этому файлу.
- `specs/trainbot-widget/calendar/calendar-widget-architecture-2026-11-12.md` утверждает архитектуру адаптера Telegram Widget, но его код ещё не подтверждён реализованным.
- Официальный Bot API 10.4 (2026-11-09): `sendWidget`, `widget_query`, `answerWidgetQuery`, `editMessageWidgetData`. В `sendWidget` параметр `width` задаёт логические пиксели и ограничивается клиентом снизу 200 и сверху шириной сообщения.

## Предложенный поток событий (не утверждено)

1. **Единая реализация Widget**, общий HTML/JS-шаблон, поиск и события как для «Откуда», так и для «Куда». В меню «Отслеживание» пользователь отдельно открывает виджет для одного из двух FSM-полей. Сервер передаёт назначение выбора (`departure` или `destination`) и соответствующий заголовок и сохраняет идентификатор активного сообщения, владельца и ожидаемое поле **на сервере**, чтобы не полагаться на выбор поля в JS. В один момент подтверждается только одна станция; два разных HTML-виджета не создавать.
2. При создании Widget сервер читает **текущее значение конкретного поля станции** из действительного контекста FSM/подписки (в зависимости от сценария создания или редактирования) и безопасно передаёт клиенту только отображаемое название и серверный идентификатор/код выбранной станции, если она уже определена. На первом экране сверху отображается текущий город, ниже четыре фиксированных варианта **Москва, Санкт-Петербург, Казань, Сочи** и кнопка «Другие станции»; текущая станция не должна извлекаться из ещё не реализованной истории выбора. Если станции нет, показывать **«Не выбрана»** и **«Выбрать станцию»** вместо «Заменить на»; пустое состояние не должно использовать фиктивный код.
3. «Другие станции» локально открывает алфавит из 33 букв; нажатия букв **локально дописывают слово** в строку ниже букв. Никаких запросов на переключение или каждую букву. Кнопка «Поиск» расположена справа от строки.
4. Только при нажатии «Поиск» Widget передаёт набранное слово в backend через `TelegramWidget.request` -> `widget_query` -> существующий сервис поиска станций РЖД -> ответ/передача доступных кандидатов в Widget. Контракт результатов, пагинации и способов обновления UI **пока не согласован**. Прямой `fetch` из Widget не закладывать. Учесть ограничение 1–64 байта UTF-8 для request (в частности кириллица занимает больше одного байта); лимит длины запроса/альтернативную схему передачи согласовать при проработке архитектуры.
5. При касании любого варианта замены Widget лишь **локально выделяет кандидата**; старое значение на первом экране и в FSM/подписке не меняется. Только кнопка **«Подтвердить»** отправляет `widget_query` с идентификатором кандидата -> сервер проверяет владельца, актуальное сообщение, FSM, ожидаемое поле, допустимость кода станции и отсутствие устаревших данных -> обновляет только соответствующие поля (`DepName/DepCode` или `DestName/DestCode`) через прежнюю бизнес-логику -> отвечает и возвращает пользователя в меню параметров. Конкретный порядок сохранения при редактировании должен быть уточнён по текущим обработчикам.
6. **Сброс зависимых полей при фактической смене станции — UX согласован, интеграция требует проверки кода.** После серверной проверки и успешного нажатия «Подтвердить», если новый проверенный код станции отличается от текущего кода для выбранного направления, в одном согласованном обновлении применить новое значение `DepName/DepCode` либо `DestName/DestCode` и очистить зависимые поля `TrainNumber` и `TimeDepart` (сверить точные имена и значения сброса по фактическому `handlers/subscrib.py` и модели сохранённой подписки). Для сценария редактирования уточнить существующую транзакцию/порядок записи в БД, чтобы частичная ошибка не оставила противоречивые параметры. При подтверждении прежней станции, отмене через «×», неуспешном подтверждении или простом выделении кандидата — ничего не сбрасывать. Не сбрасывать дату/прочие поля без отдельного согласования.
7. **Отмена через «×» (UX согласован, реализация предлагается):** верхняя правая кнопка видна и остаётся интерактивной **во всех состояниях Widget, в том числе при ожидании или ошибке сервиса РЖД**. Не привязывать её доступность к успешности поискового запроса, наличию списка или выбранной станции. Отмена должна быть независима от сервиса РЖД. На клиенте не вызывать неподтверждённый `TelegramWidget.close()` — Widget встроен в сообщение, а не является окном Mini App. Предлагаемый путь: по нажатию инициировать `TelegramWidget.request("cancel")`; backend проверяет владельца, чат и message_id, помечает контекст выбора недействительным, отвечает на widget_query и **не меняет DepName/DepCode/DestName/DestCode, подписку и пользовательские параметры FSM**. Для удаления виджета из чата использовать `deleteMessage` для исходящего сообщения бота, когда разрешено Telegram (обычно до 48 часов после отправки). Если удалить сообщение не удалось — перевести виджет в неактивное состояние «Выбор отменён» через данные, обновлённые ботом, не принимая новых подтверждений. Реальную последовательность answer/delete, гонки и UX проверить на Telegram-клиентах до утверждения архитектуры.
8. **Legacy fallback — UX утверждён, технический механизм требует проверки:** если Telegram-клиент не поддерживает HTML Widgets, сохраняется существующий путь ввода названия станции сообщением в чат, поиск через действующий сервис и выбор через прежние обработчики/кнопки. Не удалять/не изменять действующие Router, FSM-состояния и валидацию. При ошибке отправки Widget — предложить тот же текстовый путь. Нельзя без подтверждения Bot API считать, что backend заранее знает версию/поддержку конкретного Telegram-клиента; способ выявления и UX переключения определить после проверки реального клиента и официальной документации.

## Альтернативы и границы

- Inline-кнопки: совместимость выше, но алфавитный многошаговый выбор раздувает чат и создаёт больше событий.
- HTML Widget (предложено): быстрый компактный первый экран и алфавит в том же сообщении; список станций нельзя получать через обычный WebView/fetch.
- Mini App: уместна при необходимости длинных каталогов, полноценного поля поиска и HTTP, но для текущего UX избыточна.

## Безопасность, ошибки, совместимость

- Проверить фактическую версию aiogram; для неподдерживаемого `widget_query` придерживаться уже утверждённого календарём изолированного адаптера/outer middleware после проверки `Update.model_extra`.
- Не доверять станции/её коду и полю выбора из JS; server-side проверка, авторизация, идентификатор сообщения, текущий FSM/state, просроченные/дублированные запросы.
- Не класть в HTML секреты, пользовательские аккаунты РЖД или платёжные данные.
- Учитывать лимиты Telegram (HTML до 32768 UTF-8 байт и до 4096 после zlib max; request 1–64 байта; answer до 1024 байт; ответ ≤15 секунд; rate limit).
- На пустых результатах — сообщение и возможность исправить запрос, без порчи FSM. При **ошибке именно поиска РЖД** показать справа «Ошибка поиска. Попробуйте ещё раз», оставить набранное слово и алфавит, сохранить кнопку «Поиск» для повтора, сбросить кандидата на подтверждение и **не менять FSM/подписку**. Кнопка «×» остаётся активной даже во время ожидания ответа и при ошибке. На сервере обработчик отмены не должен зависеть от доступности РЖД; для зависшего запроса предусмотреть своевременный ответ `widget_query` и контроль устаревших результатов после отмены. При **ошибке самого Widget/Telegram API** — fallback в чат, согласно п. 8. Предлагаются локальные кнопки «⌫» и «Очистить», их вид и поведение ещё не утверждены.
- MemoryStorage теряет контекст после рестарта; старые запросы отклоняются.

## Следующий шаг

Согласовать UX списка станций после выбора буквы. Затем подтвердить точную FSM-интеграцию по актуальному `handlers/subscrib.py`, утвердить архитектуру и подготовить план; **production-код не менять**.

## История изменений

- 2026-11-12: после утверждения пользователем UX набора слова по буквам исправлено предложение о транспортном событии: запрос на backend отправляется только по кнопке «Поиск», не по каждой букве. Архитектура всё ещё не утверждена.

- 2026-11-12: подтверждена единая реализация Widget для «Откуда» и «Куда», разделение по назначению на сервере; это уточнение архитектурного проекта, не окончательное утверждение архитектуры.

- 2026-11-12: согласовано отображение **ранее установленной станции на первом экране** выше вариантов замены; её значение берётся из текущего поля подписки/FSM, не из истории. До «Подтвердить» сохранённое значение не изменяется; архитектура по-прежнему черновик.

- 2026-11-12: для пустого исходного значения утверждены «Не выбрана» / «Выбрать станцию». Кнопка «×» должна отменять без изменения FSM; cancel-query и удаление виджета предложены для будущей реализации, но не протестированы.

- 2026-11-12: утверждён сброс номера поезда и времени отправления при подтверждённой реальной смене одной из станций. Способ очистки FSM и, при редактировании, сохранённой подписки/БД должен быть сверён с действующим кодом до утверждения архитектуры.

- 2026-11-12: зафиксирован обязательный fallback на существующий текстовый выбор станции для клиентов без поддержки Widgets; конкретная проверка поддержки клиента и точка подключения к старым обработчикам ещё не согласованы.

- 2026-11-12: UX ошибки сервиса РЖД утверждён: ошибка выводится справа в том же Widget, повтор поиска без изменения сохранённых параметров; кнопка «×» остаётся активной в состоянии ошибки и во время поиска. Архитектурная реализация ещё требует проверки.
